# Mac 本机微信 Hook 路线：静态源码调研

调研日期：2026-09-18。目标是个人微信进入由企业微信创建、同时包含微信和企微成员的外部群，持续收普通消息、主动发送、真实 @ 两类成员、识别自己被 @。偏好本机或自建，RPA 仅备选。

## 结论

**Mac 本机 Hook 值得作为自研 PoC 路线，但本次审阅的三个项目均不能判定为“已满足外部混合群需求，可以直接安装使用”。** 最值得复用的是 `wechat_chatter` 的底层收发桥接和 `wechat-mac-hook-classic` 的版本锁定、Gadget 安装及普通群 @ 工程化处理。两个关键缺口分别是当前微信 build 适配，以及外部群/OpenIM 的收发语义验证与可能的协议补齐。

本机只读检查由主任务完成：macOS `26.6.2 (25G83)`，`arm64`，微信 `CFBundleShortVersionString=4.1.13`，`CFBundleVersion=269578`，SIP `enabled`。这些环境信息不是项目方的兼容性保证。本调研没有运行下载项目、注入微信、修改签名或读取本机聊天数据。

## 1. wechat_chatter：收发结构已存在，外部群不能外推

### 收普通消息与被 @

**A：** Frida 在 `buf2RespAddr` 捕获响应数据，非发送 ACK 的候选需首字节为 `0x08`，交给 Go protobuf 解析器。Go 假定 `wrapper(field2) -> body(field2) -> content.data` 的消息结构。未发现专用于外部群/OpenIM 的另一套接收解析。来源：[script.js 1132–1187](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/script.js#L1132-L1187)、[protobuf_handler.go 82–99](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/protobuf_handler.go#L82-L99)。

**A：** `buildWechatMessageJSON` 初始将消息设为 `private`；仅在 `strings.Contains(sender, "@chatroom")` 时设为群、提取群成员、解析 `<atuserlist>` 并写入群昵称缓存。发送者成员提取进一步优先查找 `wxid_`。同类判断还控制正文前缀剥离。来源：[protobuf_handler.go 171–231](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/protobuf_handler.go#L171-L231)、[254–273](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/protobuf_handler.go#L254-L273)。

**C：** `xxx@im.chatroom` 不包含连续子串 `@chatroom`。如果外部群的该种 ID 到达现有解析器且消息结构相同，会被误归为私聊，也不会进入其群 `atuserlist` 提取与昵称缓存路径；如果消息结构不同，则可能在更前面的 protobuf 解析阶段就被丢弃。全仓检索未找到 `im.chatroom`、`openim` 的显式处理。这是明确的静态兼容性缺口，但不等于证明所有外部群都必然使用同一种消息结构。

### 主动发送与真实 @

**A：** Go 将用户/群 ID 作为目标，统一调用文本构造器和 Frida 文本发送函数；Frida 的文本 CGI 固定为 `/cgi-bin/micromsg-bin/newsendmsg`。没有看到按外部群或 `@openim` 身份切换文本协议/CGI 的分支。来源：[worker.go 54–80](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/worker.go#L54-L80)、[script.js 432–447](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/script.js#L432-L447)。

**A：** 该实现并非仅拼接可见的 `@昵称`：文本 protobuf 会把被 @ ID 放入 `<msgsource><atuserlist>…</atuserlist>`。但 HTTP 接口只有在 `groupID_userID` 昵称缓存命中时，才同时添加可见名称和真实 ID；未命中时会跳过该 @。来源：[text_builder.go 14–45](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/text_builder.go#L14-L45)、[http.go 39–50](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/http.go#L39-L50)。

**C：** 源码证明“有真实 @ 元数据构造”，并不能证明企微成员 ID 在同一协议中会被服务器正确处理，也不能证明手机会触发提醒。仅修群后缀判断不足以解决整个需求；必须核验外部群协议、成员标识、入站被 @ 字段及服务器结果。

### 版本、架构与系统改动

**A：** 默认配置是 `4_1_11_53_mac.json`；其配置是硬编码地址偏移。已审阅版本目录没有 `4.1.13` 或 build `269578` 配置。默认构建固定 macOS arm64、Frida devkit 17.8.0，Go 模块声明 Go 1.25.0。来源：[main.go 57–67](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/main.go#L57-L67)、[版本目录](https://github.com/yincongcyincong/wechat_chatter/tree/04ae61400b9a5754431c10a1455e94c12c4b79e2/wechat_version)、[地址配置](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/wechat_version/4_1_11_53_mac.json)、[构建脚本 4–9、39–49](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/setup_frida_and_build.sh#L4-L49)、[go.mod](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/go.mod)。

**B/A：** 文档提供关闭 SIP 后 PID attach、或保留 SIP 但植入 Frida Gadget 两条路径。Gadget 路径实际会修改微信 Mach-O 加载命令、放入 dylib、重新签名；不是无修改的官方扩展接口。文档 Gadget 示例仍使用 17.5.2，和当前构建默认 17.8.0 不一致，实施需统一。来源：[onebot/readme.md 3–9](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/readme.md#L3-L9)、[frida-gadget/readme.md 12–24](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/frida-gadget/readme.md#L12-L24)、[sign.sh 30–39](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/frida-gadget/sign.sh#L30-L39)。

## 2. Classic：门禁更严格，仍未补齐外部群

## 5. 最小有意义 PoC 范围

下述为建议的下一阶段范围，**尚未实施**。无需先上 AI、长期记忆或完整机器人管理后台。

1. **先选受控客户端基线。** 可用项目锁定的 4.1.11.53/build 269109 作为比较基线，前提是能取得可信原版、校验签名/摘要并确认仍允许登录；不能默认旧版现在还能登录。或者针对本机 4.1.13/build 269578 重新定位和校验 ARM64 Hook 偏移、核心模块及消息结构。两条方案都不能通过修改版本字符串绕过门禁代替适配。
2. **先证明外部群接收。** 使用测试账号、测试用企微外部群，明确参与者为一个个人微信测试号、另一个微信成员和一个企微成员。先观察手工发送的普通文本与手工 @ 消息，保存最小、脱敏的消息样本与结构；确认群 ID、两类成员 ID、真实发送人和被 @ 字段，以及是否使用相同回调/解析外壳。未观察到数据时先定位接收路径，不先改后缀后宣称修好。
3. **再证明主动发送和真 @。** 对比原客户端手工发送普通文本、@ 微信成员、@ 企微成员时的任务/CGI/消息体结构；若不同则实现必要的外部群路径。分别验证发送成功响应、接收端内容和真实 @ 提醒。HTTP 返回 `ok`、可见 `@昵称`、Frida 返回 `1` 都不够构成完成证据。
4. **最后验证持续性。** 普通消息无需 @ 也应持续进入本地事件接口；被 @ 与非 @ 应准确区分。覆盖重启、断网恢复、短时消息批量到达，并验证去重和错误可见性。只在这些验收项通过后，接入上层业务逻辑。

验收最小矩阵：微信成员发普通文本、企微成员发普通文本、两类成员分别 @ 测试号、机器人主动发普通文本、机器人分别 @ 两类成员；每项同时记录客户端版本/build、真实收件端结果和桥接事件。该矩阵通过以前，应将方案标为“外部群待验证”。

对本机的直接影响是：现成配置与当前微信 build 不匹配；保留 SIP 的路线仍需要改应用并重签名。下一阶段若要动态验证，应先把应用备份、目标 build 和还原步骤做成具体可审阅方案，再实施；本轮只做公开源码和本机环境只读调查。
