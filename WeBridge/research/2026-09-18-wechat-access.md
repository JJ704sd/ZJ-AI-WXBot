# 个人微信接入企微外部混合群：方案探索

调研日期：2026-09-18。阶段：需求确认、公开一手资料调研、源码静态审阅、本机环境只读检查；尚未进行微信账号登录和群消息实测。

**2026-09-21 补充：**用户要求继续探索 Linux。新增[Linux 专项报告](2026-09-21-linux-paths.md)，覆盖原生 Linux 客户端容器、数据库读取与 UI 发送、无桌面协议服务，以及 Wine 路线。此前平台偏好保持不变；新增候选仍需同一混合群验收。

**结论**

按用户最新要求，优先级为：**微信接入层可在 Mac/Windows 部署的自建协议方案优先；无法通用时，优先 Windows 接入节点；RPA 仍作为备选。** 当前还没有候选在实际企微外部混合群完成验收，也没有确认完整、可独立维护、现成可用的免费跨平台实现。

应先筛选当前有维护、可提供混合群试用的协议核心；若其自建条件不成立，优先验证 Windows 4.x 客户端接口，再考虑 Mac 单独适配。付费 API 的调用代码与微信协议核心必须分开判断，复制前者不能替代后者。

这次比原聊天增加了几个实质发现：Windows 已有公开可读的 4.x C++ 收发核心，但外部群与 @ 仍需开发；Mac 也有 4.x Hook 基础，但不适配当前本机版本；WeChatPadPro 当前公开仓库不含可独立构建的协议核心；旧 Gewechat 已停止维护和分发；官方智能机器人明确不支持外部群。对应证据见下文及专项笔记。

**已经对齐的需求**

个人微信账号进入由企业微信创建的外部混合群，保留个人号身份；主动发言；真正 @ 个人微信和企业微信成员；识别机器人被 @；接收对方后续回复，保留上下文交给既有 Agent。原始需求把“一直监控普通群消息、理解完整上下文”表述为期望能力，因此评估分别标注基础双向交互与持续消息覆盖，不能把仅能应答的方案写成已具备全量监听。

用户偏好：本机或自建优先，减少第三方依赖；协议或客户端接口优先，RPA 可备选。最新澄清为 **Mac 与 Windows 通用优先，无法通用则优先 Windows**，不要求只在当前 Mac 实现。用户表示可以准备专用个人微信测试号和企微外部测试群。账号数、群数、消息峰值、图片/语音是否为首轮必需项尚未明确，本轮按一个账号、一个混合群及一个普通群对照设计验证。

原始需求来自用户指定的[聊天](https://chatgpt.com/c/6aaa0266-bec4-83ea-8e02-da5b6ae019a0)。该聊天用于确认需求，其中的技术结论均重新核查。

**本机实际环境**

| 项目 | 只读检查结果 | 对选型的影响 |
|---|---|---|
| 操作系统 | macOS 26.6.2，build 25G83 | 可以研究 Mac 原生方案 |
| 处理器架构 | arm64 | 需确认 Apple Silicon 支持 |
| 微信安装版本 | WeChatBundleVersion 4.1.13.10；CFBundleShortVersionString 4.1.13；CFBundleVersion 269578 | 不可直接套用其他小版本的 Hook 偏移 |
| 微信主程序 | 同时有 arm64、x86_64 slice | 本机优先核查 arm64 路径 |
| SIP | enabled | 不以关闭 SIP 为现成部署前提 |
| Docker | 已安装 darwin/arm64 客户端 29.6.2 | 本轮沙箱无法访问 daemon socket，未验证服务端；不据此判断 Docker 故障 |

读取来源为本机 `sw_vers`、`uname -m`、微信 `Info.plist`、`file`、`csrutil status`、`docker version`。没有改签、降级或重启微信，没有读取聊天数据库，也没有发送消息。

**“跨平台”需要分别验收哪一层**

| 所谓跨平台 | 实际含义 | 是否满足用户优先条件 |
|---|---|---|
| 完整接入层跨平台 | 同一套核心可在 Windows 与 Mac 各自构建/运行，或在两边的 Linux 容器中部署 | 最符合；仍要逐平台核验原生库、镜像架构、授权依赖与混合群能力 |
| Agent/API 客户端跨平台 | Mac/Windows 都能发 HTTP 请求，但协议核心在供应商服务器 | 不等于独立自建，不能单独据此通过 |
| Windows 接入节点 + 通用业务服务 | 微信和 Hook/RPA 固定在 Windows；消息网关与 Agent 可在 Mac、Windows 或服务器运行 | 符合用户“无法通用时优先 Windows”的备选方向 |

Mac/Windows Docker 中运行 Linux 服务，也不等于能直接运行 Windows 微信 DLL。Apple Silicon 上的 Windows ARM 与原生 Windows x64 也要分开验收，不能仅凭虚拟机能打开微信就判断注入兼容。

**候选方案比较**

“有接口/代码”表示值得验证，不代表账号能在今天成功登录，也不代表实际混合群完整通过。

| 路线与代表项目 | Mac / 自建情况 | 当前证据与主要缺口 | 本轮定位 |
|---|---|---|---|
| 私有化协议服务：WeChatPadPro 等 | 公开 release 有 macOS/Windows 多架构包，另有 Docker | 当前公共目录只有部署/文档等，较新版本经赞助群交付；混合群专项能力未确认 | 优先核验跨平台交付物与试用能力，不能直接定案 |
| Windows Hook：mosheng/aixed 4.1.10.27 源码；miloira 新 pywechat | Windows x64 接入节点；Agent 可留在 Mac/服务器 | 前者有可读核心但外部群/@ 不完整、复用许可未明；后者核心非公开、作者宣称有企业群接口 | 跨平台核心不能成立时的优先方向：自研小 PoC 或供应商同群试用 |
| Mac 原生 Hook：wechat_chatter、wechat-mac-hook-classic | 可研究本机接入；核心代码公开 | 已看到收发和原生 @ 构造，但未覆盖本机 build，外部群识别也有缺口 | 保留为自主研发/跨端补齐路线，不再作为首轮主线 |
| Wechaty + PadLocal | SDK 可在 Mac 运行；仍依赖 Token 和服务端 | 源码识别外部群和企微成员标识，但当前服务/Token 可获得性待确认 | 可作为能力对照，不符合完全独立自建 |
| GeWe API | 可从 Mac 调用；供应商声称支持私有化 | 有消息回调、发送和 @ 接口；实际企微外部群双身份收发仍未证明 | 可用试用做对照，暂不据文档购买长期服务 |
| 源码交付型协议供应商 | 交付源码才有机会独立构建 | 有公开售卖源码的项目，但构建完整性、原生依赖、外部授权和实际群能力都未验证 | 评估完整源码交付，避免只拿到 API 包装层 |
| Windows RPA：pyweixin、wxautox4 Plus 等 | Windows 接入节点，业务服务可跨平台 | 有通过成员候选列表完成真实 @ 的实现，但入站真实 @、外部群及持续覆盖待测 | 优先的 RPA 后备；先查 UI 树与免费/付费边界 |
| Mac RPA：wechat-mac-rpa 等 | 本地 GUI 可研究；需桌面会话及相应权限 | 视觉轮询不自动保证忙群全量、稳定消息 ID 或真实 @ | 较低优先级后备 |
| 官方机器人 / 客服 / 会话存档组合 | 部分服务可从 Mac 调用，存档 SDK 有平台限制 | 智能机器人明确不支持外部群；客服不是群；存档只补读取 | 只有接受改变身份/交互入口或混合接入时再考虑 |

Mac 方案来源：[wechat_chatter](https://github.com/yincongcyincong/wechat_chatter)、[Classic](https://github.com/xiaoguiwucan/wechat-mac-hook-classic)。其余路线的直接证据分列如下。

**Mac Hook：保留为跨端补齐路线，已有明确阻塞**

静态审阅发现，wechat_chatter 当前版本配置到 4.1.11.53，未找到本机 4.1.13 / build 269578 的配置。多处收消息逻辑只识别普通群标识 `@chatroom`；企微外部群形态 `@im.chatroom` 不会被这项匹配覆盖。昵称缓存还参与原生 @ 生成，因此群类型漏判可能继续影响真实提及。

这意味着后续需要验证两层：当前微信 build 的收发 Hook 点，以及外部群自身的收发/成员/提及格式。不能仅替换群后缀或照搬偏移，就宣称已修复。Classic 的 Gadget 方案会涉及微信应用修改和重签；保持 SIP 开启不等于完全不修改客户端。详细源码位置、提交和许可见 [Mac Hook 专项笔记](2026-09-18-mac-hook.md)。

此外，[lovezm/wechat-hook-macos](https://github.com/lovezm/wechat-hook-macos) 的当前 Rust 发送函数存在占位实现；不能因为 README 展示接收效果就把它当作完整双向通道。

**WeChatPadPro：能下载本机包，不等于可以自己维护核心**

本轮通过 GitHub API 核查 main 的完整目录，提交为 `5cf4fc76c5457691798079bd921e09f60cf5afd7`，目录没有被 API 截断；未见协议核心源码、`go.mod` 或源码构建入口。[目录快照](https://github.com/WeChatPadPro/WeChatPadPro/tree/5cf4fc76c5457691798079bd921e09f60cf5afd7)

部署配置直接使用维护者的预构建镜像。README 将 v875 的获取放在赞助群；GitHub API 返回的最新公开 release 则是 `v2.01`，发布日期 **2025-08-22**，包含 macOS ARM64 包。这里的“8 月 22 日”不能误读为 2026 年的近期更新。[部署配置](https://github.com/WeChatPadPro/WeChatPadPro/blob/5cf4fc76c5457691798079bd921e09f60cf5afd7/deploy/docker-compose.yml)、[README](https://github.com/WeChatPadPro/WeChatPadPro)、[公开 release](https://github.com/WeChatPadPro/WeChatPadPro/releases/tag/v2.01)

所以它是“可能自部署的闭源协议核心”候选，而不是本轮已确认的“完整开源、无后续依赖”方案。尚未确认赞助费用、当前包是否能登录、是否能独立断开供应商服务运行，以及企微混合群接收和双身份 @。本轮没有执行其二进制或 Docker 镜像。

**商业服务与源码交付的差别**

GeWe API、旧 Gewechat、PadLocal 的当前状态及源码边界，见 [商业方案专项笔记](2026-09-18-commercial-paths.md)。核心判断是：SDK 开源、能本地运行 SDK、能本地部署核心、能从源码独立构建，是四件不同的事。

当前 GeWe 快速开始说明提供 7 天试用，具体有效价格未核实；这可作为后续对照测试入口。旧 Gewechat 则明确停止维护、运行服务和镜像分发，不能等同于新 GeWe 的当前服务。[GeWe 试用说明](https://doc.geweapi.com/doc-3146201)、[Gewechat 停维说明](https://github.com/Devo919/Gewechat)

PadLocal 的公开代码确实识别 `@im.chatroom` 与 `@openim`，这是比一般“支持群聊”更有价值的证据。但客户端仍通过 Token 获取远端 gRPC 服务，当前 Token 获取与实际可用性未核实，不能直接作为完全独立自建方案。[ID 判断代码](https://github.com/wechaty/puppet-padlocal/blob/main/src/padlocal/utils/is-type.ts)、[服务发现代码](https://github.com/padlocal/padlocal-client-ts/blob/master/src/utils/ServerInfo.ts)

有源码销售路线，例如 [wechat2ipad/wechat-ipad-protocol](https://github.com/wechat2ipad/wechat-ipad-protocol)。供应商页面公开了按号租用、部署包和源码交付，但价格与维保条款存在新旧段落及未来生效日期冲突；本轮不将页面金额当成已确认报价。即使购买“源码”，也要先确认它包含实际微信收发核心、构建脚本、架构依赖和可维护代码，而不是远端服务的调用示例。

还检查了 [meteor-nb/Ipad860](https://github.com/meteor-nb/Ipad860)：它确实公开较多 Go 文件，但 README 明示关键 `v08.dll` 源码不明。本轮对固定提交 `4d567bd6ee3206b5f112768225d7498abfc442b1` 的小型库做静态文件头检查：`lib/v08.dll` 是 Windows x86-64 PE DLL，`lib/libv08.so` 是 Linux x86-64 ELF 动态库；没有取得对应 Darwin/ARM 核心库。其 `Init.go` 中的 `Model == "MAC"` 是协议设备模式选择，不是 Mac 服务端构建证明。公开 Go 文件不能保证整个协议链路都可审阅、可跨平台构建。[库目录](https://github.com/meteor-nb/Ipad860/tree/4d567bd6ee3206b5f112768225d7498abfc442b1/lib)、[协议设备初始化](https://github.com/meteor-nb/Ipad860/blob/4d567bd6ee3206b5f112768225d7498abfc442b1/Algorithm/Init.go)

上述库仅下载到临时目录并使用 `file` 查看格式，没有执行或加载；该仓库只留作研究参考，不作为本轮推荐部署物。

**Windows 接入与 RPA 备选**

值得继续的 Windows Hook 只收敛到两条，具体源码证据见 [Windows Hook 专项笔记](2026-09-18-windows-hook.md)。

1. **公开可读核心用于自研研究：**[mosheng20205/WechatHook4.1.10.27](https://github.com/mosheng20205/WechatHook4.1.10.27)，上游是 [aixed/WeChat-Hook](https://github.com/aixed/WeChat-Hook)。它有微信 4.1.10.27 x64 的 C++ 收发、HTTP 与回调实现，适合研究原生客户端通道。但群识别只覆盖 `@chatroom`，发送没有接通 `atlist`，回调也缺失可靠 mention 数据及真实服务端消息 ID。项目自身未见明确许可证，准确称为可读源码研究基础，不按 MIT/完整开源可商用成品处理。
2. **当前功能的供应商对照：**miloira 推广的新 pywechat。作者列出微信 4.x、企业联系人、企业群和群 @ 能力；新版核心没有公开，是否收费、如何更新、能否完全本地运行仍需明确。本轮没有把宣传升级为混合群验收通过。应要求使用个人号在同一企微外部测试群演示，不能用企微账号或普通群替代。

[WeChatFerry](https://github.com/lich0821/WeChatFerry) 原仓库明确在 2026-07-10 归档。其接口适合研究收消息、发消息、提及及适配层，但当前登录、版本支持与维护应重新验证。[wxhelper](https://github.com/ttttupup/wxhelper) 同样依赖具体客户端版本。

[miloira/wxhook](https://github.com/miloira/wxhook) 把公开版本指向微信 3.9.5.81，README 中另有需进群获取的新版 pywechat。不能把仓库标题列出的 4.x 覆盖范围，全部当成当前公开代码已经支持。该 pywechat 名称也不应与其他同名 RPA 库混淆。

Windows GUI 后备优先研究 [Hello-Mr-Crab/pywechat](https://github.com/Hello-Mr-Crab/pywechat) 仓库里的 **pyweixin**：作者标明 4.1.6+，公开实现通过 @ 候选列表选择成员，有独立窗口监听。但账号 UI 树可能不可读；部分监听方法会在时段结束后才返回汇总，需改造成事件流；显示昵称也不等于稳定成员 ID。不能把这条 RPA 路线与 miloira 的同名 Hook 产品混淆。

[wxauto4 原仓库](https://github.com/cluic/wxauto4) 已停止更新。作者当前免费版文档列兼容上限为 4.1.8.107，独立窗口及监听等 API 带 Plus 标记；[作者适配说明](https://docs.wxauto.org/blog/A9dYFme8.html) 承认 4.x 可见消息 UI 的生命周期会使突发消息导致监听锚点丢失。因此它可测试基础交互，但不能凭轮询接口承诺持续全量。确切当前价格与目标版本可用性尚未核实。[版本及安装文档](https://docs.wxauto.org/docs/install.html)

上述 Windows RPA 库均无已确认的 Mac 原生通用实现，当前验证环境先按 Windows 11 x64 设计。详细源码、商业界线和监听条件见 [Windows RPA 专项笔记](2026-09-18-windows-rpa.md)。

[wechat-mac-rpa](https://github.com/wq19901103wq/wechat-mac-rpa) 是真正的 Mac GUI 路线，默认由截图/OCR/视觉判断驱动，另有历史数据初始化方式。推论：它可避免维护微信协议核心，但多群切换、长列表滚动和短时突发消息要单独验收；UI 上选择 @ 成员与输入一段 `@名字` 也要区分。配置外部视觉/模型服务时，所需截图或提示内容可能传给该服务，不能把“程序运行在本地”当作所有数据都留在本地。

本地数据库读取可以作为接收/历史补充的技术方向，却不提供主动发送能力。两个常见旧推荐也发生了变化：[chatlog](https://github.com/sjzar/chatlog) 已移除源码与历史；[WeFlow](https://github.com/hicccc77/WeFlow) 当前原仓库只有说明与图片，不能继续直接套用旧版部署教程。这是项目可获得性的核查，不是对所有同类技术可行性的否定。

**官方方案的范围**

官方能力应按真实身份和会话范围分开判断：智能机器人、Webhook 群机器人、微信客服、会话内容存档、ClawBot 各自解决不同部分。不能因为 SDK 有 `sendMessage` 或类型里有 `group_id`，就推断能接管个人微信原有的所有外部群。

企业微信官方帮助已经明确：智能机器人只支持企业内部群，外部群暂不支持添加，群里也只处理 @ 它的交互。因此这一路可直接排除，系统换成 Windows 也不解决该产品边界。[官方帮助](https://open.work.weixin.qq.com/help2/pc/21663)

腾讯官方 ClawBot 插件的固定发布包 2.4.9 仍只声明 direct 会话，不能作为既有群收发方案；官方会话存档有条件地提供读取，但 SDK 列的是 Linux x86/ARM 和 Windows，没有 macOS 原生包，且没有个人号发送能力。[腾讯官方实现](https://github.com/Tencent/openclaw-weixin)、[官方存档 SDK](https://developer.work.weixin.qq.com/document/path/91774)

具体官方原文、当前 SDK 与消息触发范围见 [官方方案专项笔记](2026-09-18-official-paths.md)。结论限于本轮核查范围：没有找到同时保留个人号身份、覆盖既有企微混合群、持续收普通消息并主动真实 @ 的完整官方路径。若以后允许改变账号身份，可以重新评估官方存档接收加受控发送的混合方案，但存档本身不是发消息接口。

**怎样评估“逆向出来，减少订阅”**

| 目标 | 技术判断 | 有效的下一步 |
|---|---|---|
| 自建接入服务、消息存储、群成员映射、Agent 适配 | 可独立实现，不需要复制供应商核心 | 等通道格式明确后做最薄适配层 |
| 研究 Mac 官方客户端的收发接口 | 已有公开研究基础；本机 build 和外部群仍需适配 | 先验证单号、单混合群的文本双向通道 |
| 仿写商业 SDK / HTTP 请求格式 | 只能代替客户端包装层 | 先追踪请求最终落到哪里 |
| 替代供应商远端协议服务 | 需独立完成登录、会话、加解密、消息同步及版本兼容 | 仅拿接口文档无法确认工期或可行性 |
| 取得能私有化、独立构建的协议源码 | 可能降低研发门槛，仍有维护成本 | 用干净环境构建与实际混合群验收交付物 |

因此，目前更合理的是先验证跨平台完整交付；不能成立时，在 Windows 上验证实际混合群通道，并评估已公开客户端实现能复用到哪一层。Mac 适配可以后续补齐。现在还没有付费方案完成实际混合群验收，不能宣称已经证明某订阅可替代，更没有完成付费核心逆向。

**首轮实测设计与停止条件**

测试资源：一个专用个人微信号 B；一个企业微信创建的外部测试群 G；G 中至少一个其他个人微信成员 W 和一个企业微信成员 E；另建普通微信群 H 作对照。扫码登录需要测试号持有人操作。测试信息使用固定编号，不用真实业务数据。

| 编号 | 操作 | 通过证据 |
|---|---|---|
| T01 | W 和 E 分别在 G 发普通消息，不 @ B | 接入端均收到，群与发送人正确，有可核对的消息标识或原始字段 |
| T02 | G 无新消息时，由程序主动发编号文本 | 群内实际出现，发言身份是 B；接口返回不能替代客户端核验 |
| T03 | 程序分别 @ W 与 E | 两侧客户端均按真实提及处理，不只是展示文字 |
| T04 | W 与 E 分别真实 @ B，再发一条仅含其昵称的普通文本 | 接收端能区分真实提及与普通文字 |
| T05 | W/E 引用回复、直接回复、拆成多条回复 | 原始事件、发送人、原生引用关系被保留；无引用时不伪造关联 |
| T06 | 发送同样内容两次、成员改名、添加同名成员 | 不误去重、不凭昵称认错人 |
| T07 | 在约定时间内发至少 100 条带顺序编号的受控测试消息，速率按预期业务规模设置 | 对照发送记录统计漏收、重复、乱序和延迟，而非只看“日志有输出” |
| T08 | 暂停通道/断网再恢复，并在期间发编号消息 | 记录缺口和实际补齐范围，不承诺无限历史回补 |
| T09 | 发送请求超时、重启发送器 | 区分成功/失败/结果未知，不盲目重复发送 |
| T10 | 运行 24–72 小时低频测试 | 记录离线、重登、缺口和资源占用；不能由此推断长期账号风险为零 |

T01–T04 用于基础双向交互验收；连续覆盖还需 T07–T10。只通过前者的方案应标“可交互、持续覆盖未通过”，不能混成全功能通过。普通群 H 通过而混合群 G 失败时，停止接 Agent，先定位通道。选择 Mac Hook 时，在准备修改客户端之前先确定测试设备、目标 build、构建产物及还原方式；不将当前工作微信作为默认改签或降级对象。

对于协议/商业服务，另需确认：测试的确切版本、外部群专项接口、消息是否经过供应商、核心是否能独立构建、是否仍需远端授权。优先短期试用并保存原始回调，避免先购买长期服务再发现只支持普通群。

下一步按以下顺序收敛，不同时铺开全部项目：

1. **跨平台协议：**核验 WeChatPadPro 当前版本或源码交付方案能否给出 Mac/Windows 的真实产物、独立部署说明，以及同一外部混合群的测试能力。公共旧包本身不满足当前可用性证明。
2. **Windows 接入：**若第一项没有可靠交付，优先拿当前 4.x 接口做短期混合群验证；希望自主研发时，先用可读 4.1.10.27 核心作结构研究并厘清复用授权，范围仅到接收、主动文本及两类真实 @。
3. **RPA 后备：**先验证 pyweixin 的 UI 可读性和基础交互，只有实际缺失能力确由商业版本补齐时再评估 Plus/VIP。

在通道通过前，不需要建设完整 Agent 后端。付费方案必须先经过同一测试矩阵，再判断值得分析哪一层、能否独立实现；不先承诺能通过去掉 SDK 的授权字段替代远端核心。

系统资源方面，Windows 路线需要一台可运行指定微信版本的 Windows x64 测试机；具体设备目前尚未确认。普通 Hook 与 GUI 自动化都不能仅靠在 Mac 安装 Python 包就变成 Mac 通道。账号和混合群已由用户表示可以准备；选商业路线时，还需供应商提供对应版本的试用核心/Token，选自研路线时则需先完成确切客户端版本的适配与收发样本验证。
