# Windows 人工待办的负责人通知（2026-10-03）

本轮为已经分派到群负责人的新待办增加可配置的微信私聊通知。通知复用 Windows Hook 的纯文本发送和持久化请求账本，人工待办与通知分别记录状态。负责人标签仍是本机责任标签；收件人必须另选当前账号已勾选读取的私聊，按稳定会话 ID 保存，不通过姓名查找或自动猜测。

## 操作与批准范围

在人工待办页先配置“群负责人”，再打开“负责人通知”，选择原群、核对负责人标签和私聊收件人，明确勾选启用后保存。启用会核对本机数据源、本人身份及当前 Hook 实例，不会发送测试消息。通知内容使用固定模板，包含原群、发起人、时间、负责人、原因、消息摘要和待办标识。长内容明确截断，提醒在工作台和原群核对；本机待办本身仍沿用最多保存 2000 字符的约定。

配置只作用于之后创建的新待办，不补发已有任务。群收到符合现有入站规则的新结构化 @ 时，同一 SQLite 事务创建事件、待办及通知队列记录。无负责人或未启用通知时，继续进入本机待办队列。通知故障不阻止入站待办创建，不向原群发送“已转交”等确认消息。

每次保存通知配置产生新的批准版本，并取消该群旧版本尚在排队的通知；重新启用也不会恢复旧队列。群负责人标签保存为相同值时则不改变负责人版本，也不关闭既有通知。

新通知从待办创建起有效期为 10 分钟。超过期限、重启、暂停、切换负责人、原群或收件会话取消读取后，未开始提交的队列不会补发。领取、释放、完成、重新打开或撤回导致任务版本变化，也会取消尚未开始提交的通知。变更后的新配置仍只适用于后续新任务。

## 提交与结果

通知由独立线程逐条处理。固定回复、定时发送、手动确认和通知共用进程内发送占用，再使用原 Hook 文件锁作最终跨进程互斥。发送占用忙时，自动任务在持久化尝试前让出，不消耗消息事件或计划次数，也不因此暂停规则。

上述忙时让出保证针对本工作台进程内的共同准入。外部进程争用原 Hook 文件锁时，既有自动回复和定时任务仍沿用原保守处理，不回滚已经保存的尝试。本轮没有改写它们的账本或增加未知结果重试。

Hook 状态查询和发送不持有通知的数据库副本锁、订阅锁或引擎锁。最后一次 Hook 探测后，提交前短暂核对账号、读取范围、规则、配置版本、任务版本及撤回记录，并把通知从排队改为已开始尝试，关联原生草稿 ID；之后才提交到 Hook。该持久化尝试是取消截止点：此后点击暂停或领取不能撤回已开始的调用。

通知结果区分未配置、排队、取消、过期、阻止、结果未知、原生入口已调用和服务器受理等阶段。结果未知不会自动重试。Hook 请求账本中已经存在的结果可以只读核对，不通过重新发送恢复。原生提交、服务器受理和本机存档都不是负责人接收端回执，界面不据此显示“负责人已收到”或“已转交”。

副本正常刷新期间只让出尚未提交的通知，不因此永久暂停配置。Hook 账本暂不可读时，待办仍可查看和处理，通知区域明确显示上次保存的结果及核对失败提示。线程发生非预期程序错误时暂停通知并保留错误，阻止在已经退出的线程上假装重新启用；本机待办继续独立接收，通知需重启服务后核对。

通知请求使用 `handoff_` 前缀，避免在全局执行历史中误标为手动发送。本轮在每条待办详情查看通知目标、状态、说明及关联请求；全局执行历史的人工、回复、定时分类保持原范围。

## 接口与兼容

| 接口 | 内容 |
| --- | --- |
| `GET /api/handoffs/notifications?account=…` | 当前可配置群的通知配置，以及已勾选读取的有效私聊收件人 |
| `POST /api/handoffs/notifications` | 保存 `{account,groupId,version,routeVersion,targetId,enabled}`，返回配置 |
| 原人工待办列表、详情及操作接口 | 每条记录新增 `notification`，与任务处理状态分开 |

通知配置与负责人配置使用独立版本。保存同时核对通知 `version` 和负责人 `routeVersion`，冲突返回 409，页面保留编辑草稿并要求明确重新加载。客户端不能提供消息正文、原生身份或数据源路径来扩大通知授权。设置通知不调用保存自动回复规则，不重建入站基线。

新增通知表存放于原 `windows-auto-reply.sqlite`，不回填旧任务，不改变原待办主表的字段。新页面仅在 `runtime.capabilities.handoffNotifications` 为真时启用配置与状态展示；旧服务和 Demo 隐藏入口，旧客户端仍能读取原任务字段。

## 验证与运行边界

本轮验证使用临时 SQLite、合成账号和群、录制 Hook 替身以及浏览器模拟接口。未向真实联系人发送消息，未更改实际通知配置，未重启现有工作台。

完整 Python 回归 **493 项通过、无跳过**，耗时 133.921 秒，使用 Anaconda Python 并将 `ResourceWarning` 作为错误；日志为 `.runtime/workbench-handoff-notifications-20261003-tests.log`。相比前一轮增加 37 项，覆盖通知配置、同事务入队、过期、重启、未知结果、发送准入、最终授权回调、HTTP 和实际入站并发。

最终复核将截断提示改为“在本机待办和原群核对”，避免承诺已经被 2000 字符上限截断的完整内容；该提示调整后，18 项通知专项回归再次通过，耗时 11.457 秒。

关键并发验收在最后一次 Hook GET 返回时禁用配置，确认没有 POST；将 POST 用同步事件阻塞时，另一线程仍能创建和激活新 SQLite 副本，并经原 `WindowsAutoReply.tick()` 接收新的结构化 @、建立第二条待办和通知队列。该检查没有用直接插入待办代替入站。账本写入故障、Hook 账本缺失、历史负责人控制字符、副本刷新暂态及线程程序错误均有针对性反例。

12 组 Node 界面检查通过，其中新增通知配置检查 19 项。Chrome 新通知检查 48 项、既有人工待办 19 项、负责人配置 31 项、历史查询 14 项通过，共 **112 项**。所有业务 API 都为模拟，覆盖同名 ID、独立批准、双版本冲突、11 种结果、迟到响应、旧服务和 Demo；对正文示意、选择器、启用及保存按钮进行边界和元素命中验证。桌面及 390 像素截图已查看，位于 `output/playwright/handoff-notification-{desktop,mobile}.png`、`output/playwright/handoff-notification-state-mobile.png`。浏览器日志为 `.runtime/handoff-notifications-browser-20261003.log` 和 `.runtime/notification-regression-{handoff,handoff_routing,history_query}-20261003.log`。
