# Windows 工作台持续运行改进（2026-10-02）

本轮依据业务需求中的计划任务分母、跳过记录和按可靠身份执行要求，修复每日漏账与显示信息造成的过度暂停，并测量上一轮完整入站扫描的持续运行成本。全部实验使用合成数据库和录制发送替身，没有读取真实聊天、启用实际任务或调用真实 Hook。

## 每日计划逐次入账

旧实现跨过多个执行日后只记录第一个 `missed`，直接计算未来计划；即使当天尚在允许的 120 秒窗口内，也不会执行当天。现在按北京时间固定 UTC+8 算出最近应执行时刻，较早每个执行日分别写入 `missed`，当天仍在窗口内则正常领取并执行当天一次。

历史漏执行记录与本次领取在同一 SQLite 事务中写入。逐日写入使用生成器，不构造多年记录列表，也不循环调用发送。相同计划 ID 与日期仍唯一，重放不改写先前结果；没有为了限制条数而截断应有账本。任务卡片仍只显示最近 10 条，全部记录通过执行历史分页查看。

合成验证包含前三天错过、第四天迟到 30 秒；结果为三个 `missed` 加一次当天提交。边界为迟到 120 秒可执行、121 秒跳过。20 年间隔通过公开执行历史分页核对 7306 个计划日（7305 个跳过及一次提交）。在第二个漏执行日的入账处注入 SQLite 故障，验证整批事务回滚、发送次数为零、异常继续抛出。

手动暂停、断线或重启后恢复仍只安排未来计划，不为明确暂停期间补造应执行任务，也不补发过期计划。未知结果不自动重试的契约保持。

## 只按影响范围处理警告

旧实现把联系人名称、身份和删除标志的解码错误合并成同一种警告，并因任何警告暂停自动回复或定时发送。真实 Adapter 合成测试证实：一个与当前群无关的昵称包含无效 UTF-8，足以阻止批准规则启用。

现在先解析 `username` 和 `delete_flag`；这两项成功后，名称解码失败单列 `contact_label_decode_error`，用账号标识显示，仍向界面返回警告。自动回复和定时发送仅放行此精确类型。其他名称表结构错误、身份或删除状态错误、正文或 @ 元数据错误、撤回解析错误和未知警告继续阻断。

显示名不用于选择收件人：消息表按会话标识定位，发送者按 ID 判断，原生请求仅使用已验证的 `targetId`。测试覆盖群与发起人显示名回退、已删除联系人仍不可选、身份和删除标志损坏仍阻断，以及显示警告不能覆盖正文损坏。共享判断避免两个自动发送入口各自维护不同的警告规则。

## 入站扫描成本

诊断 workload 为单群 3000 / 10000 条历史非文本消息，加 201 条当前时间窗内文本；每种数据包含系统消息、图片消息对照。此前每个相同副本的重复入站扫描仍解码全部历史，完整自动回复 tick 还会独立读取最近 200 条作为发送证据。

分析显示历史消息解析是主要成本，逐页副本校验和 SQL 查询也占部分时间。最近 200 条读取仅作为成本对照，因其确实遗漏第 201 条消息，不能替代完整扫描。

现在在当前 Adapter 状态中按群复用完整、无新增预检警告的撤回集合。缓存最多保留 512 群、合计 8 MiB JSON 等价数据，超过容量按最近使用顺序淘汰；超大单项不缓存，仍按完整扫描处理。中途未完成或任意预检页有解码警告都不能发布缓存。显示名警告仍随每页从当前状态返回。

重新配置副本会建立全新状态，即使复用了 revision 标签也不复用旧缓存。命中仅省略已完成的历史撤回预扫，不跳过源文件校验、账号与会话校验或本轮消息时间窗；因此同一副本中时间戳稍靠后的消息仍能在之后进入有效窗口。

正式前后对照使用同一脚本，每种操作从新 Adapter 状态开始，连续测量 3 次；建库和配置不计时，未清空操作系统文件缓存，计时包含解码/SQL 的轻量计数。环境为 Windows 11、AMD64、32 逻辑处理器，Anaconda Python 3.13.9、SQLite 3.51.0。10000 条历史图片、201 条当前消息、有 `(create_time,local_id)` 索引的完整 tick 原样结果：

| 实现 | 第一次，新状态 | 第二次 | 第三次 | 重复轮询解码量 |
|---|---:|---:|---:|---:|
| 优化前 | 447.813 ms | 451.703 ms | 463.151 ms | 10401 条 |
| 优化后 | 474.041 ms | 38.771 ms | 34.781 ms | 401 条 |

这里改善的是同一副本的后续轮询；首次冷缓存扫描未证明更快。10000 条系统消息的对应 tick 为前 `[490.749,472.851,472.077]` ms、后 `[518.566,36.056,36.952]` ms。完整原始数据保留在本机忽略目录 `.runtime/diagnostics/inbound_perf_20261002/before.json` 与 `after.json`，包括源码摘要、SQL 计划和锁持有时间。

提交的纯合成复验脚本可从 `WeBridge` 执行：

```powershell
python web_mvp/diagnostics/check_inbound_performance.py --repeats 3 --output .runtime/diagnostics/inbound-performance.json
```

脚本覆盖 3000 / 10000 条系统及图片历史、索引与无索引对照；发送替身一旦收到调用就失败，不会连接真实客户端。

## 验证与边界

Windows / Anaconda 最终全量 `unittest discover`：350 项全部通过，无跳过，耗时 71.595 秒，开启 `ResourceWarning` 错误检查。日志为本机忽略目录 `.runtime/workbench-operations-20261002-tests.log`。本轮新增 17 项，覆盖逐日漏账、显示错误隔离及缓存行为；关键故障均先取得预期失败，再验证修复。

独立合成反例另确认：同 revision 标签但实际内容不同的新副本会重新检查撤回；暖缓存仍拒绝文件变化；分页中的意外解码异常不改变原游标；历史坏消息即使不在最近 200 条内仍阻断自动回复；补记历史漏执行时不会覆盖已有 `unknown`，当日已领取的 `unknown` 也不会再次发送。`git diff --check` 通过。

历史界面与执行查询的此前浏览器结果仍见 [历史改进](workbench-history-2026-10-02.md) 和 [审计改进](workbench-contracts-2026-10-02.md)。本轮不改变界面布局，因此没有重复浏览器验收。

测量是本机单群合成实验，不能推导为约 300 群的时延或吞吐承诺。副本更新、冷缓存、真实数据库分布、同时运行任务及真实群收发仍需单独验收。发布代码不会自动重启工作台；实际运行进程需重启后才使用更新。
