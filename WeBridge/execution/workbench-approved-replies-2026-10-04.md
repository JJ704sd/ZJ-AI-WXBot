# Windows 批准问法回复与转人工

本轮增加每群的“批准问答”模式：只有完整消息匹配已批准卡片的问法时，才向原群发送卡片中的完整答复。其余有效的新结构化 @ 进入本机人工待办，继续使用已有负责人分派和独立通知配置。

这是确定性问法规则，不是模型分类或知识检索。填写者负责核对资料和答复是否属于已批准的资料或流程场景；服务端没有识别报价、订单或交期承诺的语义能力，这些请求仍按首期业务范围交人工。系统不从群消息生成、扩写或更新批准答复，也不猜测移除显示的 `@昵称`。

## 配置与批准

群规则中选择“批准问答”后打开独立配置。每张卡片保存场景名称、1～5 个完整允许问法、资料标题、资料版本、完整批准资料和完整回复正文；每群最多 20 张。问法可从原消息复制，包括显示的 @ 文字。启用至少需要一张完整卡片。

“保存草稿 / 关闭问答”与“批准并启用”分开。当前群使用固定回复或纯转人工时，保存问答草稿不改变其模式、启用状态、冷却间隔或入站基线；批准启用才切换该群到新模式，并核对自动更新副本、读取范围及 Hook 绑定。已经处于批准问答模式时，保存关闭状态会停止该模式。

配置使用版本核对。其他窗口修改规则、暂停或重启后，旧编辑不能覆盖当前配置；冲突保留草稿，需明确重新加载。正常入站处理和最近发送时间变化不使编辑版本失效。启用建立完整消息基线，仍不回复启用前或同一秒的消息。

“试匹配完整消息”只检查文本与草稿卡片，不读取原生接口、不创建事件或发送。它不验证真实 @，不能代替原消息资格判断。修改卡片、试匹配文本或账号／群／来源后，旧预览不能继续使用。

## 入站与发送边界

沿用结构化 @ 本人、新旧时间、自身排除、撤回、解码和消息 ID 去重。未知身份、纯文字 @、@其他人、@所有人或无效解码不产生自动回复。匹配只统一 CRLF 换行并移除首尾空白，不忽略大小写、标点或内部空白，不使用子串匹配，也不截断消息后匹配。同一规范化问法重复配置会被拒绝。

有效 @ 中的未匹配消息、非文本消息、冷却期间的请求以及发送暂停后的请求进入待办，保存实际原因。追加一个未批准请求会使整条消息不匹配，避免只答一部分后把整条请求当成已处理。临时发送占用忙时不消费匹配事件，未知问法仍能进入待办。

Hook 异常或进程绑定变化暂停后续自动提交，批准问答仍继续接收入站并转人工；恢复发送需重新核对并批准。来源异常关闭处理，正常副本刷新期间让出。新的发送流程在 Hook 探测和提交期间不持有数据源、订阅或引擎锁；最后一次探测后短暂重新核对当前策略、群、来源、时效、撤回、基线和去重，并先持久化事件尝试，再调用原生发送。当前常驻轮询仍同步调用该流程，本轮验证的是其他线程可更新副本及处理入站，不是新增独立常驻接收线程。

结果未知不自动重试：保留原尝试和批准证据，并建立要求核对结果、避免盲目重发的待办。启动时将未完成的尝试标为未知；批准事件缺少核对待办时，按冻结原群名在同一事务补建，不探测或重发。已有任务的处理状态、通知和具体错误不被重写，旧固定回复未知事件不迁移。原生提交、服务器受理或本机存档仍不代表接收端已收到。人工待办和独立通知状态分别显示，不据此称“已转交”。

## 接口与兼容

| 接口 | 内容 |
| --- | --- |
| `GET /api/reply/policy?account=…&groupId=…` | 当前群问答草稿、版本、模式及发送暂停状态 |
| `POST /api/reply/policy` | 按版本保存草稿、关闭问答或明确批准启用 |
| `POST /api/reply/policy/preview` | 按版本试匹配完整文本，不写入或发送 |

策略输入 `{account,groupId,version,enabled,cooldown,cards}`。卡片字段为 `{id,name,questions,sourceTitle,sourceVersion,sourceText,replyText}`。预览输入 `{account,groupId,version,cards,text}`，返回决策、原因、匹配卡片、答复和策略版本。策略冲突返回 HTTP 409 与 `policy_conflict`。两个新 POST 最多接受 1 MiB JSON，模板／批量定时及其他接口维持各自原上限，沿用 Host、Origin 和 CSRF 检查。

策略保存在原 `windows-auto-reply.sqlite` 的规则 JSON 中；旧记录缺少策略版本时从 0 开始。固定回复和纯转人工语义保持原约定，卡片草稿在切换模式时保留。旧 `/api/reply` 可明确关闭批准问答，或明确切换到原有模式；省略新配置不能重新启用批准问答或清空卡片。能力声明为 `runtime.capabilities.approvedReplies`，旧服务和 Demo 隐藏新入口。

执行历史保存当次卡片及资料完整快照、策略版本与转人工原因，支持按卡片名、资料标题和资料版本查询。编辑当前卡片不改写过去的资料或答复；只读历史不探测 Hook，按当前账号及已勾选会话隔离。发现人工待办原消息撤回时，在同一事务清除待办和关联入站事件的触发正文，历史页和搜索也不能读回该正文；批准资料、答复及执行结果保留。

Windows / Anaconda 全量回归 543 项全部通过，无跳过，耗时 180.060 秒，并启用 `ResourceWarning` 错误检查。新增 27 项覆盖完整消息匹配、草稿与旧模式保留、版本冲突及重启失效、原生最后探测后的策略修改／撤回／副本忙、真实发送文件锁占用、冻结资料查询、混合群稳定 ID、Hook 离线转人工、入队事务故障回滚及未知尝试崩溃恢复。日志保存在本机 `.runtime/workbench-approved-replies-20261004-tests.log`。

14 组 Node DOM 回归通过，含新增批准问答 22 项检查。Chrome 批准问答 32 项、人工待办 19 项、负责人分派 31 项、负责人通知 48 项及历史查询 14 项，共 144 项通过。桌面和 390 像素视口核对全文显示、无横向溢出、按钮实际可达、编辑冲突保留草稿、账号迟到响应隔离及未知结果文案。截图保存在本机 `output/playwright/approved-reply-desktop.png`、`approved-reply-mobile.png`、`approved-reply-mobile-actions.png` 和 `approved-reply-audit-mobile.png`，已查看布局。Chrome 验收日志为 `.runtime/approved-reply-browser-20261004.log` 和 `.runtime/approved-replies-check_*.js.log`。

验证使用合成数据库副本、临时 SQLite、录制 Hook 替身和全部业务接口被模拟的 Chrome 页面。没有填写真实批准卡片、启用真实规则、重启实际工作台或发送真实微信消息。模拟浏览器和静态页面服务器已关闭。

本轮不替代语义场景识别、真实原生 @、负责人接收端确认或约 300 群持续运行验收。
