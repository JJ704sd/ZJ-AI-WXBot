# Windows 被 @ 自动回复

## 使用

1. 连接自动更新的数据库副本，并连接 Windows Hook。
2. 选择已勾选读取的群聊，打开右侧“自动回复”。
3. 填写固定文本、设置同群最小回复间隔，打开开关后保存。
4. 其他成员在该群新发明确 @ 本人的消息后，工作台通过 Hook 向同群发送普通文本。当前不会在回复中 @ 发送者。

界面显示启用/暂停状态和最近的处理结果。关闭开关并保存会停止后续自动回复。已经提交给微信的发送不会撤回。

## 触发范围

- 只依据数据库结构化 @ 元数据；文本中的 `@昵称` 不作为识别依据。
- 不回复本人、@所有人、撤回消息、未知身份或无法完整解析的消息。
- 启用时建立当前消息基线，只处理时间晚于启用时刻且不超过 120 秒的新消息。时间戳仅精确到秒，因此启用同一秒的消息不触发。
- 按账号、群和服务器消息编号持久化去重，跨分片重复也只处理一次。
- 间隔内的新 @ 记录为跳过，不排队补发；默认间隔 30 秒。
- 2026-10-02 起，每轮独立分页扫描 120 秒有效窗口，不再受页面最近 200 条限制；先完整检查当前副本中已支持的撤回记录，再按时间、分片和行坐标读取候选消息。每轮重叠扫描配合持久事件去重，接纳副本后来补入的有效消息；这仍不保证微信及时落库或大规模群聊处理时延。
- 数据源/Hook 异常、进程绑定变化、取消群读取、手动断开 Hook 或工作台重启会暂停/关闭规则，必须重新启用。副本正常更新期间等待更新完成。
- 原生发送前先持久化领取记录；超时或结果未知不自动重试。工作台无需浏览器保持打开，但服务、微信和 Hook 必须运行。

## 实现边界

`windows_auto_reply.py` 负责规则、消息资格判定、基线、间隔、持久化领取和暂停。新运行数据存放在 gitignored 运行目录的 `windows-auto-reply.sqlite`，不会改写旧通道的回复规则表。

2026-10-02 的入站扫描、完整启用基线和故障测试见 [工作台入站改进记录](workbench-inbound-2026-10-02.md)。下方原有验证记录保留为当时证据。

服务器复用 `/api/reply` 的 CSRF 保护，并由活动数据源生成账号和目标绑定。Windows 自动回复使用独立的服务端发送入口，复用 Hook 的版本、进程绑定校验及一次性提交，不伪造人工确认请求。原人工发送确认要求不变。
