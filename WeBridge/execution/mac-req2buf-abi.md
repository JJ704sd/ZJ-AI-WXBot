# Mac 新版 req2buf 与缓冲 ABI 静态复核

日期：2026-09-21。范围限定为已经校验的 ARM64 核心：旧版 `4.1.11.53 / 269109` 与本机 `4.1.13.10 / 269578`。本轮只读挂载官方旧 DMG、读取磁盘二进制、解析 Mach-O 并使用 LLDB 文件目标有限反汇编；没有运行或附加客户端、读账号数据、改应用、重签名或修改 SIP。版本和 SHA256 见 [基线报告](./mac-feasibility.md)。

**结论：三个 req2buf 缺口不能靠换地址补齐。新版仍有可分析的消息序列化入口，但对象、调用时机和寄存器布局发生变化；本轮没有产出可运行的新配置。发送任务入口和缓冲复制函数的局部 ABI 已确认相符，接收 taskId 的旧取法不能直接继承。**

## 已确认的局部 ABI

地址均为 ARM64 核心静态 RVA，不是运行时绝对地址。置信度仅指磁盘静态证据，不代表已成功登录、收发或处理外部群。

| 对象 | 新版静态位置 | 已证明什么 | 仍缺什么 |
| --- | --- | --- | --- |
| `MMStartTask` | 函数 `0x5570260`，旧 Hook 对应指令 `+0x10 = 0x5570270` | 新旧同样先分配 `0x140` 栈帧和保存寄存器，尚未覆盖 x0/x1；随后把 x1 保存到 x19、x0 保存到 x20，从原 x0 对象的 `+0x18` 取管理器，再把原 x1 传下去。局部参数捕获方式成立。 | 原 x1 所指 Task 的完整布局、生命周期及线程要求；不能据此确认旧伪造 Task 仍有效。 |
| 缓冲复制 | `0x42b9070` | x0 是缓冲对象，x1 是源数据，x2 是长度；先扩容，以内部长度 `+0x0c` 找末端，`memcpy` 后增加该长度，x0 返回传入长度。与旧 `0x3e7fa8c` 同构。 | 真实调用线程、所有权与输入长度限制的运行时验证；静态相同不等于可任意主动调用。 |
| 接收数据点 | `0x42b7c54`，所在函数 `0x42b78d0 + 900` | 此前把数据指针放到 x20，长度放入 x2，调用上述复制函数；在 Hook 点，x20 是缓冲数据，x0 是返回长度。 | 帧是否覆盖全部目标消息、具体 protobuf 类型、会话/成员 ID 和提及元数据；尤其 taskId 关联方式需重做。 |

证据：[当前发送/接收完整局部函数](./mac-current-abi-disassembly.txt)、[新缓冲复制函数](./mac-new-pattern-disassembly.txt)、[旧发送与缓冲窗口](./mac-old-pattern-disassembly.txt)。公开 Hook 对应 [script.js 575–706](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/script.js#L575-L706)。

## 接收 `sp + 0x140` 并不是本函数的 taskId 字段

新旧接收内层函数均分配 `0xf0` 栈帧；其直接包装调用者分别是旧 `0x3e7e190`、新 `0x42b7774`。包装函数均在自己的 `sp + 0x50` 执行 `stp x24, x23`。所以在内层 Hook 点读取 `sp + 0x140`，等于读取包装函数保存的**进入该包装函数以前的 x24**：`0xf0 + 0x50 = 0x140`。它不是内层函数明确接收或存储的独立 taskId 参数。

向外一层扫描直接 B/BL 引用还显示：旧包装函数有两条静态调用路径，其中 `0x3e5a910` 入口把 x1 保存到 x24，与旧脚本把该值当 taskId 的假设相符；新版只扫描到 `0x424fb88` 的直接调用，后者未在可见路径建立同样的 x24/taskId 关系。间接调用不在这次直接分支扫描的覆盖范围内。因此不能断言新版完全没有另一条路径，但**现有证据不支持保留旧 `sp + 0x140` 的 ACK 清理逻辑**。

这一点不仅影响显示：现有脚本会在 taskId 匹配时清零 `pendingInsertMsgAddr`。错误关联可能写坏内部对象，应先取消这种未经证明的关联写操作再设计新版探针。[原接收逻辑](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/onebot/script.js#L1132-L1159)

证据：[新包装函数](./mac-new-buf-callers.txt)、[旧包装函数](./mac-old-buf-callers.txt)、[新外层调用者](./mac-new-buf-outer-callers.txt)、[旧外层调用者](./mac-old-buf-outer-callers.txt)、[直接引用清单](./mac-buffer-wrapper-callers.json)。

## req2buf 三个缺口的具体结果

旧配置对应同一函数 `0x3e58e44`，下一函数边界 `0x3e5a3e4`。旧配置来源固定为 [4_1_11_53_mac.json](https://github.com/yincongcyincong/wechat_chatter/blob/04ae61400b9a5754431c10a1455e94c12c4b79e2/wechat_version/4_1_11_53_mac.json)。

| 旧 Hook 点 | 旧版真实指令/布局 | 新版结论 |
| --- | --- | --- |
| enter `0x3e58e8c` | `ldr x9, [x24, #0x60]!`；此前 x24 复制了对象 x19，taskId 保存在 x20，脚本却用 x1 判断。该指令开始按 taskId 查询对象内的树。 | 没有确认语义一致的新 enter 点。新版同名 RTTI 关联代码用对象字段 `+0x70`，但不能仅把 `+0x60` 改成 `+0x70`。 |
| `blrX8Addr = 0x3e58f0c` | 实际是 `add x4, sp, #0x138`，下一条 `0x3e58f10` 才是 `blr x8`；x1 是 AutoBuffer，x20 是 taskId。 | 找到同类缓冲序列化调用，但其 x20 已是消息对象；旧脚本 `x20.toUInt32()` 判断 taskId 会失去依据。 |
| exit `0x3e59de0` | 位于正常返回尾声，x25 已由上一条 `ldp x26, x25, [sp, #0x10]` 恢复。脚本读到的是调用者的 x25，并非该函数临时变量。 | 没有确认同样的调用者寄存器约定；不能把新函数末尾某条 `ldp` 当等价出口。 |

证据：[旧函数前 4092 bytes 反汇编，涵盖三个 Hook 点](./mac-old-req2buf-full.txt)。该文件名含 `full`，实际没有覆盖函数末尾异常清理区；本报告只引用文件确实覆盖的范围。

### 有价值的新入口，但不能当旧 req2buf 的一对一替身

旧函数的指针出现在虚表 `0x923b4c8` 的第 2 槽（从 0 计数）；其 RTTI 名称为 `_af1f970f`。新版仍存在这个混淆后的类型名，可沿类型信息找到虚表 `0x98e7bb0`。但新版第 2 槽 `0x4294718` 的可见成功分支会从树中删除任务、解锁并进入完成回调，没有旧 enter → 序列化 → exit 的同一流程；**同名 RTTI 和同一槽位不足以证明函数同义**。类型名只是可复核的定位线索，不把混淆名当正式类型定义。[指针及函数边界证据](./mac-rtti-vtable-evidence.json)

新版该虚表第 13 槽 `0x42931e8`（长 2848 bytes）有更有价值的消息序列化路径：

- 入口把 x1 保存为 x20，随后从 `[x20 + 0x0c]`、`[x20 + 0x18]` 等读取成员，证明这里的 x1 是对象指针。
- `0x42932b4` 调用 AutoBuffer 构造函数 `0x42b8eb4`，buffer 对象位于 `sp + 0xc8`。
- `0x42932c0`、`0x42932c4` 从该对象的虚表 `+0x10` 取函数；`0x42932dc` 执行 `blr x8`，此时 x0 = x20（消息对象），x1 = `sp + 0xc8`，x2/x3/x4 指向 `sp + 0xd4 / 0xc7 / 0xc0`。
- 后续读取缓冲数据/长度，并把结果复制进另一个结构；说明确有序列化链路。结合稍后的树插入和任务结构构造，它适合作为“更早的对象序列化入口”继续调查。尚未证明它覆盖所有主动发消息类型，也未证明 `[对象 + 0x0c]` 在该点就是脚本所需的最终网络 taskId。

这更支持“发送流程重组，需要更换适配策略”的判断，尚不足以证明旧 req2buf 被此函数完全取代。文件 [mac-current-req2buf-candidate.txt](./mac-current-req2buf-candidate.txt) 仅是候选路径反汇编，**不是可加载的地址配置**。[AutoBuffer 构造函数直接调用者清单](./mac-expected-buffer-ctor-callers.json)

## 有界下一步

1. **优先做接收探针设计：**把 `0x42b7c54` 的数据/长度作为候选，只拷贝有界原始帧；删除未经证明的 `sp + 0x140` taskId 判断及任何 ACK 清理写入。运行前仍需独立环境和版本/核心 SHA256 门槛。
2. **主动发送继续静态补一个小模块：**追踪 `0x42931e8` 的调用者及其 x1 对象构造，确认虚表 `+0x10` 对应接口、对象字段和生命周期；另审 `MMStartTask` 下游 Task 的新版布局。选定一条后再实现最小文本发送，不能复用旧假树节点/假虚表实现而只更换地址。
3. **旧版本作为对照组：**已下载的精确基线仍有价值，应该在真正隔离的 macOS 用户/系统中验证；不能启动同 Bundle ID 副本就假定与现用账号隔离。本轮没有启动它。

本轮新增证据不改变外部混合群的验收要求。当前仍无 Mac 运行态收发或真实 @ 的成功证据；未宣称新版适配完成。

收尾校验：旧 DMG 已由 `hdiutil detach` 返回 `"disk4" ejected.`；报告的 13 个本地证据链接均存在。
