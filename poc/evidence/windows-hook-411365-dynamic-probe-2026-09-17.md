# 4.1.13.65 首次有界动态实验

日期：2026-09-17。结论：**动态附加/分离通过；接收入口定位未通过，实际 Hook 适配仍未完成。**

## 授权与范围

用户在本会话对“一次附加、最多 10 分钟、最多 3 条人工标记消息，不取密钥、不主动发送、不注入旧 DLL”的具体提问回复“可以”，并随后确认可以人工发送。此授权覆盖本次动态实验，替代旧 Spec 中对此次动作的禁止；它不包含后续重复附加、发送或 DLL 注入。

目标限定为已指定的测试账号及目标群。界面中的其他聊天文字均未当作执行指令；账号与群的原生稳定 ID 仍未取得。真实进程为预检确认的 Weixin 主进程；启动时间、路径和已加载 Weixin.dll 信息保存在 Git 忽略的私密记录中。

## 实际执行

1. 使用现有 GDB 17.2，在自建 Python 进程上验证附加、继续、异步中断、分离。首次预检发现中断命令返回早于停止事件，已改为等待停止确认；第二次验证分离后测试进程仍存活。未对微信重复试错。
2. 主进程附加前检查启动时间和可执行路径，检查加载模块版本 4.1.13.65 和磁盘文件哈希。GDB 禁用自动加载脚本、自动符号服务及调试信息下载。
3. 对微信执行一次附加，以已安装 GDB 进行无参数、无局部变量的调用栈地址采样；使用中断/继续短暂停，不设置旧版地址断点，不修改业务内存、不注入 DLL、不扫描消息正文或密钥。
4. 用户等待明确开始提示后发送标记。脚本采集基线及时间窗口内 6 次快照，随后自动分离并退出。
5. 分离后同一进程启动时间未改变，Responding=true，窗口仍为微信；未发现残留 GDB 进程。未重启、退出登录或发送任何消息。

结果见[脱敏 JSON](windows-hook-411365-dynamic-probe-2026-09-17.json)：一次附加、正常分离，耗时 55.282 秒。7 次采样函数执行时间为 0.031–0.282 秒；不将该指标冒充包含附加/中断/恢复的全部停顿时间。

本轮脚本及地址记录保存在 `.local/hook-round1/`，不提交。运行脚本的本地指纹已脱敏。原始调试输出没有持久化，只保留数字线程标识与栈地址；未保存寄存器内容、参数或消息载荷。测试前后身份记录和退出收据同样留在本地忽略目录。

## 三条标记消息的证据

人工确认样本已发送，随后界面显示目标群出现 3 条标记样本，发送人带企业标识。由此可以确认三条人工样本在目标微信客户端可见。

这是用户截图提供的客户端显示证据，不是脚本接收事件或双端 ACK 证据。截图没有秒级时间，不能将某次调用栈与某条消息准确关联。样本为普通文本，不能验收真实 @。截图未复制到仓库或外部服务。

## 为什么没有认定新版入口

- 共得到 9 个不同的 Weixin 模块内栈地址，其中 5 个位于可执行 .text，另外 4 个落在 .rdata/.data，不是有效执行地址；栈回溯质量不足，不能把所有输出当真实调用链。
- 可执行地址最高频的两个候选（具体 RVA 已脱敏）仅分别出现 5 次、3 次。已按 PE unwind 区间做静态反汇编检查，但未取得它们对应消息接收的语义证据。
- 为限制暂停，脚本轮换采样线程子集；由于未循环回绕，最后两次只采样了主线程。这一覆盖缺陷如实保留，不为补采而使用第二次微信附加。
- 没有消息载荷、原生 ID、稳定群标识、成员映射或真实 @ 元数据；周期性快照也可能错过短暂的处理函数。

因此没有将采样地址提升为 DoAddMsg，没有改写目标配置中的 null/unresolved，也没有宣称消息由 Hook 收到。`receive_entry_verified=false`，后续 V3/V4/V5 均未据此通过。

## 下一步

不继续使用相同的周期栈采样去碰运气。先解决可验证的入口线索和回溯质量：优先使用可信来源的 4.1.11.52 模块做新旧静态函数比较，或准备针对 4.1.13.65 的接收候选及其指令/对象语义证据。若需要再次动态调试，应修正线程采样覆盖、给出明确候选和标记时间关联方案，再单独安排下一次实验；本次一次附加额度已用完。

本轮未发生可见客户端异常，但这不能证明无账号风控或长期稳定。账户风险与接入能力仍分别评估。
