# 实际线程寄存器核验与重复停止事件

本轮的新增证据是：在自建夹具中直接核验实际线程调试寄存器，而不再仅核对 GDB 断点列表。真实微信仅刷新进程/模块元数据，没有调试器附加、暂停、注入或消息读取。

## 机制核查

本机调试器输出版本为 GDB 17.2，MinGW-W64 Brecht Sanders r4 构建。同版本上游源码中，cygwin_set_dr / cygwin_set_dr7 更新寄存器镜像并标记线程待更新；resume / windows_continue 路径再对恢复的线程更新 Context。新线程登记时也标记待更新。这解释了为何 break-list 不能代替线程实际寄存器证据。上游标签核查不等于已证明供应商二进制与上游逐字一致。

- [GDB 17.2 上游 Windows 后端](https://gnu.googlesource.com/binutils-gdb/+/7adf9fa6b1ccb3c70f86cb630368b9d3dffcf3aa/gdb/windows-nat.c)
- [同版本 MI 手册源码](https://gnu.googlesource.com/binutils-gdb/+/7adf9fa6b1ccb3c70f86cb630368b9d3dffcf3aa/gdb/doc/gdb.texinfo)
- [Microsoft GetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext)：运行线程的上下文读取无效，需先暂停；不能以当前线程自读结果作为有效证据。

## 实现及范围

夹具可选启动一个自身采样线程，只接受程序内部保存的 main/old/new 三个线程身份，并再次校验归属本进程。它成功暂停某线程后读取 CONTEXT_DEBUG_REGISTERS，随后恢复一次；没有 SetThreadContext 或寄存器写入，也没有外部 PID/TID 输入。主 Agent 复审修正了暂停失败时仍调用恢复的实现问题，再开始实测。

寄存器快照在 continue 之后、首次 marker 之前取得；分离之后再取一次。采样线程自身不在覆盖对象内，覆盖结论仅限三个指定线程的两个快照时点。文件关闭后原子发布；原始地址仅留在忽略目录。公开结果保存一致性布尔值。

前置快照要求每个线程的有效执行断点槽与预期地址集合一致；后置快照要求没有启用槽，并不要求所有禁用槽的残留地址必须为零。

## 新发现与修正

第一次增强三点实验中实际 DR 配置匹配，分离后也清除，但出现同一线程同一断点的重复停止事件。旧夹具按原始 9 条事件结束，遗漏了一个应观察的线程/断点组合，因而失败。

现在夹具在有限事件上限内等待完整的线程/断点组合，并另外保留原始事件数与重复数；还验证夹具自身 stage 执行计数。这个判据只适用于已知调用次数的夹具，未对真实消息按线程/位置去重，真实运行器的命中上限也没有擅自提高。

## 实验记录

| 场景 | 观察 | 结论 |
|---|---|---|
| 初始增强三点，旧 9 条停止条件 | DR 前后通过；9 条原始事件，点计数 3/4/2 | 失败，促成夹具结束条件修正 |
| 修正后的早期增强三点 | 20 条事件、9 个唯一组合；分离后快照缺失 | 失败，原因未确认；该次未记录错误时目标退出码，现已补采集 |
| 单点+寄存器快照 | 3 个指定线程分别命中，前后 DR 通过，夹具退出 0 | 通过，仅本次夹具 |
| 三点不采寄存器的对照 | 9 条事件，9 个组合，stage 计数准确 | 通过，不能单凭此断言采样导致异常 |
| 补充错误退出码记录后的增强三点 | 10 条事件，9 个组合，stage 计数准确，前后 DR 通过 | 通过，未解释此前快照缺失 |
| 最终连续 5 次增强三点 | 原始事件数 9/11/9/13/9，每次均为9个组合，stage计数准确，前后DR通过，夹具退出0 | 5/5通过；2次存在重复停止事件，不代表长期稳定性已证明 |

所有运行中的空闲超时场景均完成清理。相关单元测试36项通过。早先两个失败产物保留在汇总 JSON 中，没有用后续通过覆盖。

## 本机身份刷新

普通沙箱查询未能读取完整模块资料，随后完成宿主只读元数据查询。发现6个微信进程，其中唯一一个同时具有可见主窗口和目标模块。其版本为4.1.13.65，模块磁盘哈希匹配；PID、创建时间、模块基址均与R4记录一致。这仅确认当前身份未漂移，未读取登录身份、群消息或内部运行状态。

## 对下一步的影响

可验证实际线程断点配置的方法已经在自建进程中成立；“GDB 接受类型即代表部署成功”的旧假设可以替换成明确的寄存器快照判据。重复停止事件也已被实际观察并独立计数验证。

但这是夹具自身采样能力，未作为代码注入微信，也没有将其覆盖结论转移给微信。R4零命中与重复停止事件不存在已证因果关系，早期快照缺失仍未解释。下一轮真机方案不能仅靠继续增加断点，仍需明确实际观测方式和范围；当前不安排用户再次发送标记。

复现命令（使用新的输出目录）：

```powershell
poc/.venv/Scripts/python.exe poc/scripts/verify_hook_attach_fixture.py --gcc <gcc-path>/gcc.exe --gdb <gdb-path>/gdb.exe --output-dir <新目录> --three-points --raw-address --capture-registers
```

兼容复验：修改后的夹具继续用于原v3回放，3次命中、地址回读、清理与分离后执行通过，退出码0。

只读复核补充：失败样本的日志已有断点表清空、正常detach回应和GDB退出记录，现有证据不足以认定detach失败。快照由夹具自身原生线程采集并发布文件，不经MI读取。由于当时缺少夹具/采样线程退出码及采集/发布错误细节，目前不能进一步区分失败环节；本轮不为这一局部失败再增加试验。
