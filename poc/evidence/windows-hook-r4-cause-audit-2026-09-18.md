# R4 零命中原因重新定位

本轮重新核对保存的运行器、目标快照、R4 结果和磁盘模块，未访问真实微信进程。机器可读结果见同名 JSON。

## 新核实的事实

1. 当前磁盘模块摘要与 R4 固定摘要一致。运行器三个地址均使用加载基址加 RVA，没有再加首选映像基址；三点均在快照报告的模块范围、可执行区及反汇编指令边界内。entry 和 callee 均是 PE 展开表记录的函数起点。此核对只排查计算和静态边界，不能证明 R4 运行时地址内容一致或该函数语义正确。
2. 标记窗口已正常完成，具体时间不在公开收据中；不能将整轮总耗时误作实际标记窗口。没有发现窗口根本未打开的证据。
3. 函数内分支可以绕过 join，但不能解释已在函数起点设置的 entry 也零命中。需要先查“该函数是否被执行/被观测”，不能继续仅调整函数内部条件分支。
4. 原运行器只检查 GDB 返回的 `type="hw breakpoint"`，未留存插入后地址、线程清单或各线程调试寄存器回读，也没有同一微信进程内的正向对照。因此此前的 `hardware_breakpoint_verified` 字段只能解释为“GDB 接受了硬件断点类型”，不能解释为“全部目标线程硬件断点已实际生效”。

## 假设更新

| 假设 | 当前判断 | 区分它所需的证据 |
| --- | --- | --- |
| 地址基址重复相加、越界或落在指令中间 | 保存资料不支持 | 三点静态审计已通过；运行时地址回读仍缺失 |
| 标记窗口未打开 | 保存资料不支持 | R4 窗口时间及用户入站确认已存在 |
| 原解析器普遍丢失断点事件 | 自建回放不支持 | 原运行器自建已知调用捕获 3 次 |
| 函数内部条件绕过了全部三个点 | 不能单独解释 entry 零命中 | 若 entry 生效，执行该函数就应首先触发入口 |
| 静态迁移的函数并非本次实时入站路径 | 仍然可能 | 独立调用关系/语义证据；不能靠相似字节直接确证 |
| 真实进程的断点部署或线程覆盖不足 | 仍然可能 | 运行时地址、线程覆盖证据及同进程正向对照 |

目前不能给后两种假设赋予可信的概率，也不能把自建进程通过视为对其中一种的排除。

## 下一轮的具体改进要求

先准备具有独立已知触发行为的同进程正向对照，再执行新一轮实验。对照必须在实际消息处理可能使用的线程上提供证据；只证明 UI 线程能命中不足以证明后台接收线程覆盖。

预检及记录需要增加：附加时重新确认模块基址与大小；核对 GDB 返回的断点地址与预期地址、启用状态、硬件类型；在继续运行及新线程出现后记录线程覆盖证据。公开产物只保留点名、数量和比较结果，不保存账号、消息内容或可复用地址。不能取得覆盖证据时明确标为 unknown，而不是 verified。

判定规则：正向对照失效时优先诊断观测部署，不能否定候选路径；对照通过但相关线程覆盖不明时仍不能否定路径；只有相关覆盖已证实且有效入站窗口候选零命中，才增强“该路径未处理本次消息”的证据。即使如此，也不能直接推出所有微信消息均不经过该函数。

当前尚未找到满足上述条件的独立正向对照，因此不安排用户重复发送标记，不消耗新一次真实进程附加额度。继续工作应先补独立候选语义/调用关系或正向对照设计；DLL 注入和消息对象解析仍未开启。
