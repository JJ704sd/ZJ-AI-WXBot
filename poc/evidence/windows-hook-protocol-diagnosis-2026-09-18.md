# 从协议层重新定位接收链路

## 当前结论

本机模块存在可用于独立定位的协议相关静态线索。之前迁移的旧 Hook 点尚未与网络回调、同步任务或消息分发建立调用关系，不能继续把它当作已经确认的协议接收入口。当前改从同步和分发边界寻找证据；零命中根因仍未确认。

另检出 longlink 109 次、shortlink 52 次、protobuf 235 次。计数是区分大小写的子串计数，不是接口或消息数量。LEA 扫描只识别两种 REX 前缀的 RIP 相对字节形式，尚未逐处反汇编验证；函数数只是展开表归属，不是已确认处理器数。零引用不证明不存在调用。new_sync 两次子串命中只有一条满足扫描条件的独立 ASCII 字符串，不能直接说发现两个协议接口。

## 协议分层和假设

腾讯公开 Mars 的接口区分长短连接、业务打包/响应解包及推送回调，并允许定制封包。它是分层分析的参考，不是本机微信私有协议规范。不能把默认示例包头、cmdid、序列号规则或公开版本功能直接套到 4.1.13.65。

排查模型为：传输收包 → 帧/任务分发 → 推送通知或响应解码 → 业务同步/消息分发 → 存储与界面。具体客户端可能重排、合并或绕过部分节点，图景尚未在本机动态证实。

- 假设 A：推送只通知有更新，客户端另起同步任务取得消息。若成立，单盯某个推送回调不一定能看到消息内容；应寻找通知与同步任务的调用和关联证据。当前不是已证实的本机行为。
- 假设 B：此前候选属于某类批处理、同步结果或条件化消息分支，没有处理 R4 样本。需要从 new_sync / AddMsg 独立线索向旧候选建立调用关系才能评价。
- 假设 C：混合群与普通群的差异发生在业务分发/身份映射层。现有证据无法证明它使用不同传输协议；不能因为群类型不同直接换网络解码器。
- 假设 D：业务路径正确但真实线程断点覆盖不足。协议分层不能排除这个观测问题，仍须保留同进程对照要求。

## 后续排查顺序及完成判据

1. 优先逐处反汇编核对 new_sync 的两个初步引用和 AddMsg 的四个引用：排除嵌入数据、日志引用和未执行字符串表，区分请求构建与响应处理。完成判据是有效指令、函数边界、调用角色证据齐全；仅名称相似不通过。
2. 再沿 OnPush / Buf2Resp 所在函数核查注册、调用及任务分发关系，与上述同步候选建立独立交叉证据。未建立关系前不生成可执行 Hook 配置。
3. 真机验证设计按层记录有界元数据：时间、点名、线程别名、事件数，以及已独立确认的关联关系。不能用“同一秒发生”代替因果关联；不假定网络序列号等于消息 ID，不记录凭据或会话载荷。
4. 仅在协议/业务路径和观测覆盖都已有依据时，开展少量入站验证；再比较普通群与目标混合群、他人入站与本账号同步。现阶段无需用户重复发送标记。

被动包长/时序即使可取得，也只能作为传输活动证据，无法单独证明具体消息已解析或经过候选函数。本轮未抓包、未解密会话、未重放登录/同步请求、未调用第三方协议服务。

## 三种“协议”必须分开

微信客户端与服务端的网络协议、Hook 后的本地 IPC 协议、861/GeWe 服务商的 HTTP API 是不同契约。能调用服务商的同步接口不能证明桌面客户端内部使用同一个接口；本地 HTTP 接收器正常也不能证明网络消息已被 Hook 捕获。IPC 实现应继续等待真实接收事件结构，而不是先猜 protobuf 字段或套用旧版消息结构。
