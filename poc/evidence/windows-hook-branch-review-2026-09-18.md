# 推送订阅分支 B/C 核查

本轮连续核查 B 的直接被调函数、两条下游信号输出、C 的调用适配器和可调用对象转发，并复用控制流工具检查可达关系。读取范围为固定磁盘模块及离线反汇编，没有运行时读取。

## 结果

- B 有多个整数分流条件；两个不同被调范围都具有信号节点遍历、间接调用及 signalslot.h 线索。离线图确认从入口到这两个直接调用点分别存在语法路径。图中仍有一个未解析分支，不能宣称穷尽全部路径。
- B 调用的某些函数地址靠近此前 new_sync 线索，但逐条检查发现有短对象初始化和成员释放代码。它们不是地址接近即可命名的同步触发器；这些探索文件的 B-sync-callee 名称只代表原假设，实际用途更接近对象清理，不能按文件名理解为确认同步。
- C 的调用适配器通过描述里的函数指针尾跳，已与参数传递形式对上。其处理函数随后从成员取可调用对象，再经虚表执行；该对象的具体目标仍未闭合。因此不能把 C 当成已解析到聊天处理的路径。
- 本轮检查的 B 及指定被调范围没有直接 call 到旧接收候选。尚未排除多层、信号或间接调用关系。

## 为什么现在不应继续靠名字扩大候选

目前已出现网络推送、业务信号、对象解析/清理和可调用对象封装等不同层级。它们都可能带有相近名称或地址，但不共享接收语义。只把每一层新地址加入断点会得到更多无法解释的命中，无法区分目标消息与背景网络业务。

下一阶段的有效检查应集中在两个方向：B 输出信号的具体连接描述，以及 C 可调用对象的赋值/实际目标。只有找到该层业务语义或得到相关运行时关联，才能判断是否需要沿消息同步任务继续追踪。还不能生成 HookChannel 或猜测 protobuf 字段。

若后续开展新一轮真机验证，可使用三个点名而不是盲目增加地址：业务推送入口、订阅者 B 入口、旧接收候选入口。目的只是区分候选是否执行，不能称为接收验收或正向对照已通过。

执行前须重新检查本机版本/模块和进程身份、断点回读及相关线程覆盖；采集限于点名、时序、线程别名、计数和停止原因，窗口与清理上限沿用已修正的运行器结果契约。只有经过独立验证的事件分类才能用于关联测试标记；仅同时间命中不够。没有该关联时，结果最多是“网络/订阅路径执行过”，仍不能否定旧候选或宣称抓到目标消息。
