# 推送订阅分支 B/C 核查

本轮连续核查 B 的直接被调函数、两条下游信号输出、C 的调用适配器和可调用对象转发，并复用控制流工具检查可达关系。读取范围为固定磁盘模块及离线反汇编，没有运行时读取。

## 结果

- B 有多个整数分流条件；两个不同被调范围都具有信号节点遍历、间接调用及 signalslot.h 线索。离线图确认从入口到这两个直接调用点分别存在语法路径。图中仍有一个未解析分支，不能宣称穷尽全部路径。
- B 调用的某些函数地址靠近此前 new_sync 线索，但逐条检查发现有短对象初始化和成员释放代码。它们不是地址接近即可命名的同步触发器；这些探索文件的 B-sync-callee 名称只代表原假设，实际用途更接近对象清理，不能按文件名理解为确认同步。
- C 的调用适配器通过描述里的函数指针尾跳，已与参数传递形式对上。其处理函数随后从成员取可调用对象，再经虚表执行；继续回溯本次注册的构造赋值后，已闭合到具体状态处理函数，详见下方补充；仍不能把 C 当成已解析到聊天处理的路径。
- 本轮检查的 B 及指定被调范围没有直接 call 到旧接收候选。尚未排除多层、信号或间接调用关系。

## 为什么现在不应继续靠名字扩大候选

目前已出现网络推送、业务信号、对象解析/清理和可调用对象封装等不同层级。它们都可能带有相近名称或地址，但不共享接收语义。只把每一层新地址加入断点会得到更多无法解释的命中，无法区分目标消息与背景网络业务。

下一阶段的有效检查应集中在两个方向：B 输出信号的具体连接描述，以及 C 状态处理之后提交的任务（其可调用对象目标已在本轮补齐）。只有找到该层业务语义或得到相关运行时关联，才能判断是否需要沿消息同步任务继续追踪。还不能生成 HookChannel 或猜测 protobuf 字段。

## 可审阅的运行时诊断方案草案

若后续开展新一轮真机验证，可使用三个点名而不是盲目增加地址：业务推送入口、订阅者 B 入口、旧接收候选入口。目的只是区分候选是否执行，不能称为接收验收或正向对照已通过。

执行前须重新检查本机版本/模块和进程身份、断点回读及相关线程覆盖；采集限于点名、时序、线程别名、计数和停止原因，窗口与清理上限沿用已修正的运行器结果契约。只有经过独立验证的事件分类才能用于关联测试标记；仅同时间命中不够。没有该关联时，结果最多是“网络/订阅路径执行过”，仍不能否定旧候选或宣称抓到目标消息。

该草案没有执行，没有预设用户已发送新的标记，也未消耗新的附加额度。旧 R4 证据和原始文件保留。

## 同轮补充：C 的具体调用目标已解析

对 C 注册点重新核对后，区分了可调用对象自身的虚表与负责引用计数的控制块虚表。注册构造把对象自身写入自身成员，再把该对象放入信号连接描述。沿处理适配器的成员读取、虚表槽、短尾跳函数，可以解析到一个 512 字节的具体函数。此结论仅适用于本次注册构造，未声称通用适配器的所有调用都指向同一个目标。

该具体函数检查所有者状态，状态已满足则返回，否则记录状态、更新字段并调用下一层。完整函数内未使用传入的整数参数地址或正文缓冲参数；因此当前证据不支持把它当成正文解析函数。后续层还会构造并提交任务，任务语义未解析，不能据此排除其间接触发消息同步的可能。

私有证据为 C-concrete-callable.txt（只解释入口至尾跳）、C-concrete-handler.txt（完整 PE 函数范围）和 C-state-continuation.txt。最初读取虚表时混用了文件偏移与 RVA，已修正为 RVA 转文件偏移后读取，并用可执行节反汇编交叉检查；无效输出已被正确证据覆盖。此修正属于离线研究脚本使用错误，不是 R4 故障根因。

## 续轮：B 启用条件与注册调用者

完整入口反汇编显示 B 在使用正文参数前检查启用位，未启用则返回。对注册函数的磁盘 E8/E9 候选引用扫描发现一处引用，并通过所在完整函数反汇编确认是有效直接调用；它在注册前将同一所有者的该字段置为启用。这里的“一处”仅指这种直接引用，不排除虚调用、函数指针或其他注册路径。

因此，B 有启用门槛已经有静态依据，但“注册时遗漏启用导致零命中”的解释不获这条路径支持。此处不是旧 R4 外层入口，且没有运行时状态，不能将该门槛解释成 R4 根因。私有证据：B-registration-callers.json、B-registration-caller-0.txt，以及已保存的 subscriber-B.txt。

本轮子 Agent 的 C 后续任务静态分析被平台安全检查拦截，没有产生可纳入证据的结果，也没有以改写请求方式重试。C 后续任务语义维持 unknown。
