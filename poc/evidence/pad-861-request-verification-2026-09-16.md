# Windows 861 请求检查验证

日期：2026-09-16。本轮只检查实现、脱敏历史收据、固定包契约并验证健康请求；没有重复生成、启动网关、扫码或发送消息。未修改运行代码。

## 已核验

| 请求 | 检查结果 |
|---|---|
| 本地 POST `/admin/GenAuthKey1?key=…` | 固定Swagger定义GenAuthKeyModel包含整数Count、Days及字符串Remark；现有Count=1、Days=1及备注符合字段类型。HTTP200不能代表业务成功；历史Code300、Data=null |
| 上游 POST `/api/v1/public/auth/generate` | 路径来自固定EXE；转发代码固定HTTPS主机，Content-Type为application/json，请求体字节不重新编码。合成边界检查确认方法、URL、正文不变；不能据合成验证宣称真实签名有效 |
| GET `/ping` | 本轮经相同转发函数访问真实厂商TLS地址，HTTP200，正文为pong，总耗时5.094秒；不携带管理凭据 |
| POST `/api/v1/auth/devices` | 固定EXE的查询路径；前次两次本地GetAllDevices没有触发此上游请求，不能把本地空列表当作上游不存在设备 |

合成检查在`upstream_request`外部网络边界替换opener，没有访问真实生成端点。验证厂商401状态及正文被保留，重定向不跟随。`tests/test_pad_auth_relay.py`三项实际运行通过，覆盖路径限制、超时后重复提交拦截、查询模式不能生成。合成正文不含真实凭据。

## 需要纠正的历史表述

1. **4秒是转发函数传给urllib的timeout参数，不是实测整个请求耗时。** 本轮健康调用设置相同参数却实际耗时5.094秒，不能把历史TimeoutError写成“整个请求4秒内未收到任何响应”。固定EXE初始化还包含5秒HTTP Client超时，形成内外两层超时；目前不能把失败直接归因于厂商服务。
2. **502和409均由本地转发层生成。** 首次超时映射502；程序再次提交被一次性限制映射409。没有厂商401/403拒绝授权的真实生成响应证据。
3. **旧事件不能区分连接/响应头/响应体超时。** 上游状态仅在读取完整响应体后才写入事件；因此“未记录上游状态”不等于“网络层没有收到任何HTTP响应头”。也没有阶段耗时可证明首次请求已到达厂商。
4. **不能声称整个HTTP请求透明传递。** 正文原样转发，但转发层重建Content-Type、Accept-Encoding及其它默认HTTP头，没有复制原始所有请求头。固定程序的已查调用使用Client.Post(application/json)，未发现该调用点额外自定义头；这仍不构成完整厂商签名契约证明。

## 当前判定与下一步

接口路径与本地字段未发现明显拼写或类型错误；健康路径可达。真实生成链路仍是结果未知，不能判定凭据有效或无效，也不能判定需要购买。

建议先修正观测：记录单调时钟阶段耗时、收到响应头的状态、读体是否完成，并分别记录本地映射码；不记录请求体、密钥或响应敏感值。以本地延迟响应测试验证两层超时与未知结果分类，再考虑得到上游核对条件后的真实生成验证。单纯增加timeout不能保证固定EXE的5秒客户端会等待，也不能解决首次提交未知的重复风险。本轮按检查请求范围未改运行行为或自动重试。
