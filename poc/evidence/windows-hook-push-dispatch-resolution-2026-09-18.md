# 推送业务对象与信号分发定位

## 本轮结果

连续核查完成了最后业务成员的赋值、业务对象构造和虚表槽，并沿推送处理函数进入下游分发函数。当前定位已从只有名称的网络桥接，推进到具有构造/注册依据的业务推送及信号分发代码。尚未定位信号的具体订阅者，也没有证明它处理了 R4 消息。

## 赋值来源为什么此前没有找到

拥有者存在多个接口指针。上层持有的接口指向拥有者内部的子对象，而不是拥有者起始地址。赋值方法相对于该接口写入一个成员，与推送方法相对于完整对象读取的成员实际是同一位置。因此仅搜索完整对象下固定偏移的写入会漏掉此赋值。

本轮沿拥有者构造函数的直接调用者核对：

1. 上层分配并构造拥有者，保存调整过基址的接口指针。
2. 上层另行构造业务对象并保存其指针。
3. 同一上层函数加载上述接口和业务对象，经接口表调用短赋值方法。
4. 对照构造时写入的接口表，确认短赋值方法的目标槽；把接口基址调整计入后，写入位置与推送转发读取位置相同。
5. 业务对象构造写入自身方法表，该表的目标槽指向本轮解析的推送处理函数。

以上为静态寄存器、成员与表指针的对应关系，未读取运行时对象，也没有仅凭结构偏移相同就认定任意对象是同一个类。

## 下游行为

已完整反汇编的推送处理函数为 309 字节：访问输入缓冲、构建本地副本并调用下游函数。下游范围为 1270 字节，包含链式节点遍历及间接处理器调用，同时引用 `signalslot.h` 与信号重入提示。

这些指令及字符串共同支持“此处是信号分发层”的静态判断，不支持“已找到聊天正文解析器”。不能把分发处理器数量解释为消息数，也不能把信号框架的间接调用自动解释为跨线程异步队列；是否跨线程尚未证实。

链路现在为：网络管理器 → 桥接 → 包装 → 拥有者转发 → 已追溯构造的业务推送函数 → 信号分发 → 待解析的订阅者。

## 对旧候选假设的再次校正

旧候选的 4 处直接引用实际上属于 3 个唯一函数范围，其中两处在同一函数，不能写成 4 个独立调用者。带 contact-message 字符串的两份范围文件对应同一个函数。

该函数靠近两处调用的条件分支，两条分支均存在到旧候选调用的语法路径。因此“看到 contact-message 配置，所以此分支把群消息全部绕过旧候选”的解释没有成立。尚未追到配置值与具体分支输入的关系，也未取得运行时值。

控制流核查复用了现有 `audit_hook_control_flow.py` 的解析、图和路径函数；结果见 `windows-hook-caller-branch-audit-2026-09-18.json`。这只是语法可达，不证明某条路径在 R4 实际执行。

## 本轮执行边界

本轮读取磁盘模块与已有反汇编，执行直接调用扫描、表槽读取、完整范围反汇编和离线控制流核验。一次全模块成员偏移启发式搜索在找到相关赋值后主动停止，不能将其计为完整扫描；它也产生了无关对象/栈字段匹配，没有采用为业务证据。原始相关证据保存在忽略目录：owner-constructor-caller-0.txt、business-object-constructor.txt、resolved-business-push.txt、business-push-dispatch.txt。

没有新增真机附加、抓包、对象载荷读取、DLL 注入或消息发送。

## 后续工作与停点

优先定位该信号的注册代码及处理器目标，再向同步任务和旧候选求交。网络推送不一定直接包含聊天消息，因此若订阅者只触发同步任务，需要继续追踪对应任务完成路径，而非立刻构造消息字段解析。

目前可作为后续有界诊断候选的是“业务推送入口”和“信号分发入口”，尚不是已验证正向对照。真机方案必须记录实际线程覆盖、区分背景网络事件与测试消息、保留断点清理和时限；不能把任何一次网络命中当作目标群接收成功。
