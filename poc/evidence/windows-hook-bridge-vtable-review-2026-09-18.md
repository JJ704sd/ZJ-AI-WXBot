# 网络回调桥接的表结构核验

本轮只读固定磁盘模块，未附加微信。结果见同名 JSON。

后续纠正：构造函数实际存在，但没有展开表记录，被前轮探索脚本过滤。现已沿直接调用确认写入同一桥接表，并补全静态注册链；下文“未找到”保留历史观察，不能再作为缺少注册代码的依据。见[注册链与漏查纠正](windows-hook-registration-chain-2026-09-18.md)。

## 新证据

OnPush 和 Buf2Resp 桥接函数的绝对地址在非代码区各找到一个指针引用，位于同一连续函数指针表，中间隔一个槽位。周围多个指针均指向 PE 展开表中的函数起点。表前记录具有 x64 RTTI Complete Object Locator 常见签名及正确的自引用 RVA；类型名位置不是可直接解码的 ASCII，因此不能宣称已通过 RTTI 确认类名，也不能据此认定加密或损坏。

此前反汇编显示两个桥接函数通过对象成员取得委托对象，再经其虚表间接调用。本轮找到的是包含桥接函数的表，**不是委托对象的业务实现表**。这个区别防止把查到的表误当作已解析的消息回调。

## 注册关系检查

限定扫描两种 RIP 相对 LEA 字节形式，没有找到直接引用该表起点的构造/注册位置；非代码区也未找到指向表起点的绝对指针。附近唯一 LEA 命中经完整范围反汇编确认是跳转表使用，不能计为对象注册。

这些是有限形式的阴性结果，不能证明桥接对象未实例化、代码无效或本机不使用这一路径。运行时实例化与委托目标仍为 unknown。

## 本轮决策

暂不将桥接函数升级为真机正向对照：它们的存在和表结构已有静态依据，但尚无证据证明当前客户端实际注册并使用这些实现。下一步需要扩展对构造、工厂和回调注册的引用形式核查，或从已确认调用者反向追踪；只有定位实际委托实现后，才能进一步判断其与同步及旧候选的关系。

原始指针表、引用范围和反汇编保存在忽略目录中的 bridge-vtable.private.json、bridge-registration.private.json 和 bridge-registration-0.txt。扫描没有导出账号、消息、密钥或运行时对象。
