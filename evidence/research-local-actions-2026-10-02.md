# 本地发送与动作执行链核查（2026-10-02）

时点说明：本记录保留旧基线 `626b123` 的审查及实验；后续 `edeb7a4` 已更新入站分页、查询与审计，当前结论以 [本地续审](research-current-state-audit.md) 为准。下文旧源码行号及测试结果不改写为新版本成绩。

范围：仅只读审查当前源码、合成测试定义及仓库执行记录；不读取私有运行目录或真实聊天，不启动服务、附加进程或发送消息，不修改产品代码。本轮未重跑测试。以下“已实现”是当前源码结论；历史实机记录单独标注，不能当作今日在线状态。

## 1. 应用于主报告的修正

1. **Windows 手工发送、固定回复和定时发送已经共用 Hook 提交口。** 服务器将三者指向同一个 `runtime/hook-send` 目录；自动分支调用 `send_automatic()`，最终与人工确认共同进入 `_submit()`。这里已有同目录跨进程文件锁、持久草稿、幂等键、账号/进程/模块/目标检查。无需另起一个完全平行的发送器。
2. **共享提交口还不是统一的业务动作仲裁。** 手工草稿、自动回复事件和计划运行分别保存在三个 SQLite 文件，尚无业务 `task_id`、需求版本、输入消费位置或人工接管版本；不同业务来源使用不同幂等键，同一意图可能顺序发送两次。锁只防止提交重叠，不判断业务冲突。
3. **已有 `backend.Store.outbox`，但 Windows 数据库模式不走它的旧发送循环。** 不能将旧表的存在描述为 Windows 已具备任务状态与动作意图的统一事务发件箱，也不能笼统说本项目完全没有 outbox。
4. **Windows 自动回复是被结构化 @ 触发的固定文本。** 它有严格资格筛选、基线、去重和冷却；没有业务语义判定、碎片聚合、无 @ 待回复匹配，也没有调用大模型。它能作为零 Token 规则基线，不能等同完整 Agent。
5. **Windows `once` 与 `daily` 已实现；真 @ 输出仍未实现。** 入站识别真实 @ 和出站产生真实 @ 是两项能力。Hook 请求明确拒绝 `mentionIds`，固定回复也是普通文本。

## 3. 最小迁移建议

保持原生 Hook、身份绑定、草稿哈希、提交前领取以及“未知不重试”边界，新增一个薄业务编排库和调度入口；不要将现有三份历史数据库直接拼接成“已统一”。

| 迁移步 | 最小设计 | 保留/调整边界 |
|---|---|---|
| A. 先落入站事件与消费位置 | 新编排库记录有来源命名空间的 event_id、每任务 inbox/消费位置、撤回/修改关联；消息快照游标与任务消费位置分别维护 | 现有自动回复 baseline 只是启用时排除历史，不是完整消费水位；不能用它承诺全量不丢 |
| B. 增加任务与动作意图事务 | 同一个 SQLite 事务写 task_state、requirement_revision、消费位置和 action_intent；action 含 task_id/revision、input watermark、目标、正文哈希、授权依据、owner/handoff epoch、稳定幂等键 | 当前 `hook_drafts` 留作传输层提交账本；迁移后不让消费者先改 task 再单独写另一个数据库当作已原子提交 |
| C. 一个业务仲裁入口 | 手工、固定回复、定时、Agent 统一提交意图；执行前重新验证任务版本、接管状态、权限、最新输入是否尚待归并及当前账号/目标绑定 | 业务锁以短事务保护决策；外部调用沿用 Hook guard。版本检查只保证检查时刻，若要挡住提交前的新修改，需明确最终仲裁点与临界区 |
| D. 受控转换历史来源 | 先影子生成 action，不发送；再将一个来源切到 dispatcher，并关闭该来源原直发；确认去重后再切其他来源 | 不能让旧 tick 与新 dispatcher 同时拥有同一个来源的执行权；无需回放旧 attempted/unknown |
| E. 更新历史投影 | 历史增加 task_id、revision、intent_id、origin 和判定理由；Hook 原始结果保留为传输证据 | 查询多个库仍可保留，但清楚标明投影是展示，不是原子性保证 |

事务意图进入 Hook 后仍有跨数据库/网络间隙。建议在调用前将 intent 与稳定 draftId/幂等键绑定；崩溃后先读取原账本分类，绝不因“上层还没写成功”生成新 key 重发。原生结果 unknown 的任务停在核对状态。这样的目标是可审计、可恢复且不盲目重复，不是端到端 exactly-once。

任务补充/修改的输入水位应与 requirement_revision 分开：不改变业务参数的补充仍可能必须被消费；仅检查 revision 不能证明 Agent 看过所有相关输入。人工接管也应有独立状态或 epoch，防止旧 run 在接管后发送。

## 4. 可据实引用的验收证据

- **当前静态定义**：`test_windows_hook_sender.py:49–62,138–166,220–241` 覆盖重启幂等、超时未知、错误 ACK、锁；`test_windows_auto_reply.py:62–135` 覆盖结构化 @、旧消息/重复/冷却、重启和变化暂停；`test_windows_scheduler.py:26–128` 覆盖 once/daily、并发领取、错过时刻、未知不重试等。本轮只查定义，不把这些测试描述为本轮全部通过。
- **2026-09-28 历史合成/界面记录**：`WeBridge/execution/windows-scheduled-send-2026-09-28.md:26–31` 记录 18 项新增合成测试、当轮 257 项通过及隔离合成界面验收，同时明确没有真实定时投递。历史测试数字不能充作当前全量结果。
- **历史自动回复观察**：同一记录 `:32` 写到两次新增本人同文本数据库记录，证据级别是 `local_record_observed`，没有服务器或收件端回执。它是 `windows-auto-reply-2026-09-28.md:35`“当时还没有新真实 @”之后的后续补充，报告应保留时间先后，不能只引用早期未触发结论。
- **历史手工 Hook 观察**：`WeBridge/execution/windows-hook-enable-2026-09-28.md:5–11` 是当日个微 4.1.15.13 发送启用及本地记录观察；其中 `:15,:23–31` 的“定时/自动回复尚未接入”是早期阶段描述，现已被当前源码及后续执行记录超过。不能拿这段作为今日能力清单，更不能外推企微版本。

迁移验收应新增以下故障序列，而不是重复证明普通文本能发送：同任务旧 revision 结果到达、人工接管后旧 run 返回、已落 intent 未调用时崩溃、原生已调用但上层结果未写时崩溃、回复与计划同一意图竞争、新输入已入 inbox 尚未消费时出站、重启后 attempted/unknown 不重放。验收先用独立临时库和录制 transport；真实平台测试仍需特定版本/会话/内容的独立证据。
