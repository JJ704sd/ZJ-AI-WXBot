# 个微／企微混合群 Agent 技术可行性报告

**v1.12｜更新日期：2026-09-21｜收费细节调研补充｜本地代码基线：ff7dcd5**

本版承接用户提供的 v1.11 精简汇报版、两项 9 月 21 日研究任务及本地最新证据；版本号承接附件，不表示仓库曾逐版发布 v1.7—v1.11。首次编写 v1.12 前工作区无未提交改动；本次复核保留并修正上一轮尚未提交的文档。本轮只更新文档，未运行微信、使用试用密钥、联系供应商、购买或发送消息，未重跑项目测试。

## 1. 当前结论

**局部受控收发已取得证据；约 300 群的定时真实 @ 索价、被 @ 后按范围自动回复及人工接管，仍未形成可交付的完整系统。** 两个新增付费候选具备继续核对接口和安排试点的依据，不能直接判为可投入生产。

- 业务边界已调整：首选接管个微，可以更换业务账号，优先保留现有群。改用企微或迁群属于替代方案，单列功能差异、客户配合和迁移成本。
- 业务包含两条流程：每日按群真实 @ 索价；收到对接管账号的真实 @ 后，批准场景内自动回复，其余交原群业务员。人工逐条审批仍是初期测试方式，不是最终所有回复都必须人工审批的产品要求。
- 已有桌面普通文本局部闭环。必须分别记录独立 Qt/UIA 验证、OCR 单次发送和有中断的草稿验证，不与私有付费 API、稳定身份、原生 @ 或持续运行混算。
- wechat2ipad 已有可核对的 Swagger；WeChatDataAnalysis 已有 GUI／纯接口交付声明，但尚缺付费 API 契约。两者均无本项目目标混合群的付费接口与 300 群验收。

旧报告的“尚无完整收发验收”不能被理解为从未单次发送成功；“当前只推进 pyweixin”“必须当前账号”也不再代表本版需求范围。9 月 18 日 pyweixin 详情探针的身份失败仍成立；不能用其他回合成功覆盖原记录。[历史 v1.6](agent-feasibility-v1.6-historical-2026-09-18.md)完整保留旧阶段及来源。

## 2. 业务目标与验收层次

需求依据为任务《拆解微企混合群代理需求》的最新完整分析及用户关于保留现有群、调整业务账号的表述。详细功能基线见[业务需求与采购验收](mixed-group-business-requirements-2026-09-21.md)。

| 范围 | 当前确定内容 |
|---|---|
| 账号与群 | 个微为首选，约 300 个现有混合业务群；允许调整个微账号，新号入群条件待核 |
| 主动索价 | 每群每日一次作为首期配置基线；按执行日和窗口分批，群内联系人可一人或多人，要求真实 @ |
| 被动处理 | 识别对接管账号的真实 @，结合必要同群上下文，简单明确且批准的场景自动回复 |
| 人工接管 | 每群负责人在原群处理；无负责人进统一待办；明确暂停、完成和恢复 |
| 不纳入本期 | 催收与收齐判断、价格表解析入库、自动比价、自动报价、订单确认和时效承诺 |
| 采购形态 | 成品系统及接口服务都比较；连接、业务编排、工作台和维护分开核算 |

保留附件 T1—T10 编号，但修正它们的适用层次：

| 编号 | 验收对象 | 当前项目判断 |
|---|---|---|
| T1 | 账号、群及必要成员绑定；改名、切号、重启后失效检测 | 局部标题／人工确认，不是所有路线的稳定程序绑定 |
| T2 | 真实群文字采集 | 数据库、独立 Qt/UIA、OCR 各有局部证据，不能拼成持续完整输入 |
| T3 | 发起人、方向、新旧、重复与同文不同事件 | 尚未在选定生产通道完整验收 |
| T4 | 有依据的同群分析与草稿 | 真实短 ACK／草稿已有；通用业务质量与转人工判断未验收 |
| T5 | 原群发送 | 局部人工受控文本发送成立；最终产品还需实现批准策略范围内自动执行 |
| T6 | 同一回复的企微／个微两类接收端确认 | Qt/UIA 有本机回显及企微端截图／用户确认；OCR 另有客户端类型未明的人工收件。不能合并宣称同条回复完成两类接收端验收 |
| T7 | 两类成员真实 @ 的接收识别与受控应答 | 未完整通过；是最终被动业务必需项，不是普通文本测试前置 |
| T8 | 定时真实 @ 索价 | 最终要求每日按群任务，旧“一次性主动任务”只作首轮验证；300 群尚未验收 |
| T9 | 权限、策略／人工审批、防重、unknown 对账及人机交接 | 有离线和单 run 保护，跨运行和完整真实链路待验 |
| T10 | 有界持续运行、掉线恢复、补收与停止 | 未通过；短时成功不等于长期稳定 |

自动发送采用预先批准的群、对象、模板／资料及场景策略；符合策略的正常变量替换不要求每条重新审批。超出策略或身份不确定时停止或转人工。逐条人工审批模式则绑定该次目标与完整正文，任一变化都使该次审批失效。两种模式均需任务防重、发送状态及接管控制；本版只定义需求，未开放自动发送。

公开说明、供应商聊天承诺、接口定义、离线测试、局部实机、业务及规模验收分别记录。未实测不等于技术不可行；不按通过符号或测试数计算业务完成率。

## 5. 两个新增付费方案的功能对照

下表依据已读取任务《评估微信协议付费方案功能》及两份本地专项报告；“有”指相应证据存在，不表示实测通过。

| 功能 | A19 wechat2ipad | A20 WeChatDataAnalysis |
|---|---|---|
| 接入与交付 | 飞书登录教程＋Swagger；登录、状态和初始化入口 | 供应商确认 GUI 和纯接口；私有 API 文档／包未取得 |
| 群与成员 | /qy/ 企业群同步、详情和成员入口；普通 GroupList 仅描述保存的群 | 企业微信能力声明；最新明确区分企微用户未测试，稳定 ID 契约未知 |
| 发出真正 @ | MessageItem.AtWxIDList 字符串数组 | 供应商及高级版功能声明；私有入参未见 |
| 识别被 @ | MessageCallbackPayload 未显式给出被 @ 列表，message_data 未展开 | 公开固定代码有 atuserlist → atUsernames，付费实时接口是否保留未验 |
| 收消息与上下文 | WS、HTTP 轮询、回调入口；历史接口与删除历史逻辑记录需澄清 | 实时更新／解密声明；刷新不自动等于可靠新事件流 |
| 发送结果 | SendTextMessage 响应未定义 schema，不能推定成功即送达 | 无付费响应契约；尤其要区分真实发送与本地补录／修改记录 |
| 定时索价 | 有发送／群发原语，逐群 @、窗口和任务账本未见完整交付 | 有定时群发功能声明，不能一律写成必须自建；具体粒度及 API 控制待核 |
| AI 与人工交接 | 关键词回复不等于场景判断、负责人待办或接管工作台 | 供应商明确仅基础核心能力，Agent 业务流程由我方建设或另购 |
| 人机共存 | 教程记录 Mac 直登挤掉 PC；iPad 共存须另测 | 当前报价称 Windows 本地；精确机制、客户端和共存待核 |
| 300 群及恢复 | 无本项目实测；账号数、群完整率、并行收信和限流待验 | 不绑账号／设备为许可声明，不是容量、性能或稳定性证明 |

9 月 21 日离线复核 A19 快照：223 个路径、22 个 /qy/ 路径，AtWxIDList 为字符串数组；公开版不记录快照 SHA-256，原值仅留本地受限研究材料。专项记录计 223 个操作、仅 2 个 200 响应包含 schema；文档标题不是实际服务版本。未调用登录、收发或任何带 key 的接口。

**成员是否有“企微用户”标签，不单独决定成败。** 必须验证稳定群／成员身份、@ 正确对象、准确识别对接管账号的 @，并分别覆盖两类成员。标签缺失未必阻断业务，但供应商“尚未测试”也不能被此前笼统承诺覆盖。

公开代码没有私有执行器，不等于付费功能不存在；宣传、演示或我们自己的 Qt/UIA 成功也不证明付费接口可用。专项来源：A19 评估和 A20 评估（父工作区研究记录，未随仓库发布）。

## 8. 建议验收顺序与选型结论

1. 先验交付契约：版本、个微承载方式、现有群覆盖、接口／工作台边界、PC 共存、价格权益。
2. 单个混合测试群验身份和双向真实 @，加入纯文本 @、@他人、本人回显、重复事件及 @所有人策略反例。
3. 逐条批准固定文本／索价模板，分别核验两类接收端及正确提醒。普通文字和原生 @ 分开验，不以本地气泡或补录通过。
4. 验业务：一次按时索价、批准场景自动回复、超范围转人工、负责人接管与恢复。未核验附件内容只能确认文件消息存在。
5. 验掉线、重启、发送超时及紧急停止，确认不重发不确定任务、不补发过期任务、不重复人工作答。
6. 核心通过后分阶段扩大授权群和时长。300 群每天各一条是约 300 条主动任务／日；60 分钟窗口平均 5 条／分钟，仅是负载换算，不能当安全发送频率。

旧计划中的 20 条独立文字、3 条批准 ACK、30 分钟观察可作早期局部验收参考，不是 300 群最终容量承诺。规模验收至少记录计划数、提交／受理／接收依据、失败、跳过、unknown、重复、漏读和处理时延；基准阈值在试点前明确。错群、@错人、跨群泄露、越权业务承诺为阻断项。

**当前建议是进入接口与试点条件核对，而非采购已验收的完整系统。** A19 接口形状较明确；A20 应先取得纯接口契约，已有定时能力逐项核实后再决定补建范围。二者没有足够证据作稳定性或总成本排名。本次文档更新不启动上述试验，不发供应商问卷，也不自动切换现有后端。
