## 一、研究结论

**本项目具有继续进行受控技术验证的基础，但尚不具备宣布“Agent 已接管个人微信并能在原混合群稳定工作”的证据。** 已有成果包括有限场景下的真实消息读取、部分真实 @ 识别、独立模型调用、人工审批与发送状态管理、API Agent 离线闭环及观察器基础设施。决定能否实际交付的核心缺口，是一个在指定账号、指定混合群中验证过的可靠收发通道，以及该通道上的身份映射、真实 @、送达和恢复能力。

截至研究截止时间，可以作出六项判断：

1. **消息理解与受控任务编排具备实现基础。** 本地已有可复用代码及离线测试；模型接口也有独立真实调用记录。无需为更换微信接入方式重新设计整套 Agent。
2. **读取能力曾在限定场景中部分成立。** 9 月 15 日数据库路线取得真实混合群消息和结构化 @ 证据，但未完成完整编号消息、当前 WAL 世代和全部反例验收，不能升级为持续完整读取。
3. **原群发送闭环仍未成立。** 桌面发送因无法核验当前群而停在发送前；API 路线尚无原群双端收件证据。模型调用成功和本地接口返回成功均不能填补这一缺口。
4. **当前非 MAX Windows 861 路线属于“有条件可验证”，不是“已可部署”。** 最近有界试验拿到了上游数据库连接超时的明确业务错误，未取得有效设备 key。缺少上游恢复证据时，重复本地网络调参不能解除该阻塞。
5. **付费与自部署可以改变服务取得方式，但不能直接消除供应商依赖。** Cloud 提供托管能力；MAX 文档提供自部署路径，但仍要求平台 TokenKey。具体套餐价格、到期执行规则、永久运行权及完整核心源码交付均未确认；更没有证据表明购买 Cloud／MAX 权益能修复旧版 861 的签发故障。[E14][S5]
6. **StarBot Pro 可列为有条件 PoC 候选，尚不足以替代现有后端。** 其文档提供结构化 @ 和个人微信侧企微群接口，具备明确的适配入口；但准确版本兼容性、底层机制、目标群实测、回调可靠性及 Pro 权益尚未闭合。对外提供 HTTP API 不能证明底层不依赖 UI RPA。[E15][E16][S10]

当前已从固定 861 单线探索扩展为分路线研究：861 缺设备 key；Cloud 有取码失败反馈；UIA 已恢复有界研究但聊天控件仍缺；Hook 已开展动态观测但入站语义未验证。保留现有 Agent，各路线按自己的证据关卡推进，不自动切换后端补发。新的研究与用户尝试不证明已经采购或获得永久授权；没有匹配 key／恢复依据时仍不重复 861 签发。统一首个业务里程碑仍是“一次真实 @ → 人工固定回复 → 个微与企微双端确认”。[E17]

## 二、研究范围与证据口径

### 2.1 “接管”在本报告中的含义

目标是由一个个人微信账号进入含企业微信成员与个人微信成员的外部群，接收目标群新消息，识别发送者和真实 @，理解任务，并通过同一账号向原群回复。进一步能力包括定时提醒指定成员、收集回复和关闭任务。

应分开评价三个层次：

| 层次 | 交付内容 | 当前判断 |
|---|---|---|
| 辅助工作 | 已授权消息输入、分析、草稿与人工审核 | 软件基础已具备，实时输入仍受通道约束 |
| 受控代理 | 程序接收、人工批准、原群发送、送达留证 | 离线框架具备；真实收发闭环未完成 |
| 无人值守代理 | 自动触发、自动回复、定时任务、异常恢复 | 仅有部分离线机制，不能作为生产能力交付 |

本轮研究以文本为主，不把图片、语音、文件解析、内部订单查询、报价承诺或业务系统写入列为已实现能力。群聊文字是任务数据，不是扩展系统权限的指令。

## 四、能力成熟度与关键证据

### 4.1 真实消息读取：局部成立，完整性未闭合

9 月 15 日记录显示，目标 `message_0.db` 完整性检查通过，群会话可唯一绑定，成员结构中出现企微 `@openim` 键及个微本人键。初次有界续读取得水位后的 3 条记录，后续扩展到 8 条。这证明该限定环境存在可用的结构化读取路径。[E3]

但这些记录位于主库已提交页，当前 WAL 世代有效已提交帧为 0；旧世代盐值不一致的帧被跳过。因此尚未证明未 checkpoint 的新消息可以稳定读取。20 个测试编号被集中发在 2 条原生消息中，也不满足“企微 10 条＋个微 10 条独立消息”的验收要求。

多分库发现、迟到消息、同秒消息、重启水位及当前 WAL 覆盖必须分别验证。缩短轮询间隔不能修复消息排序或分库发现错误。Chat-Lab 第二轮已用合成实验发现相关边界，不能因界面和业务分析功能更新就认为这些问题自动解决。[E2]

### 4.2 真实 @：部分正反例成立，不能只匹配正文

关键进展是确认真实 @ 可出现在压缩 `source` 的顶层 `<atuserlist>` 中；仅查看 `packed_info_data` 可能误判为空。后续记录包含原生单独 @本人、纯文字伪 @、本人发送的结构化 @ 样本。原生 @他人、引用旧 @、@所有人等反例尚未全部闭合。[E3]

这里还必须区分“收到别人 @本人”和“向企微成员发出原生 @”。前者局部成功并不证明后者可用。昵称、企业标签和成员稳定键未完全映射时，不应执行指定成员提醒。

### 4.3 模型与业务执行：模型可调用，业务正确性另验

T3 三条真实请求耗时分别为 1.344、3.359、5.297 秒；模型正确回答时间换算，并对无法访问的内部订单信息明确表示无权限，但对蓝天成因的表述有过度简化。上述耗时是模型请求和解析时间，不是群消息端到端延迟。[E4]

当前适合继续验证一般问答、固定字段收集和待审核草稿。报价、订单状态或客户承诺需要额外接入可追溯业务数据，不能由模型凭群聊推断后直接对外确认。现有离线任务状态机可作为收集“是否收到／是否愿意”等字段的基础，尚无真实业务效果指标。

### 4.4 原群发送：决定性缺口

T4 记录为发送尝试 0、本地提交 0、接收确认 0。原因是微信只暴露外壳节点，无法证明当前选中的就是绑定群；实现因此停在 `not_sent`。这是发送保护生效的证据，不是发消息失败或发出后丢失。[E5]

API A1 的 `accepted` 来自 fake channel，`verified=0`。当前代码仍保留 `A1 refuses live start`。后续不能通过删除阻断、把 HTTP 200 当成功或把本地气泡当双端送达来升级验收状态。[E6]

### 4.5 稳定性与账号风险：没有足够实测

仓库已有重复事件、冲突暂停、崩溃后不盲目重发、额度、过期任务取消等离线覆盖，但尚无真实混合群连续运行、断线恢复和跨日观察结果。不能据此估算账号受限概率、可用率、漏读率或长期维护成本。此处的风险判断来自非官方接入依赖及证据缺口，不构成“已发生封号”的结论。

## 五、技术路线比较

| 路线 | 已有价值与证据 | 当前主要限制 | 本项目建议 |
|---|---|---|---|
| 官方企微机器人／接口 | 官方已有双向智能机器人 SDK；传统 Webhook 有明确产品能力 | 未核验出适用于本目标的“个人号接管＋混合群普通消息＋原群发送”完整官方通道 | 持续核查能力边界，不作为已解决方案 |
| 本地数据库读取＋独立发送 | 混合群历史局部读取和真实 @ 已有证据 | 需要密钥访问；分库／WAL／新旧消息仍有缺口；发送需另解 | 保留研究成果；按最新计划不继续实施该支线 |
| 桌面 UIA | 已恢复研究；隔离 wxauto4、独立 UIA8、v2/v3 正对照与看门狗已有证据 | 所测聊天窗口仍仅外壳；原生对照成功不等于微信成功 | 需要新语义控件或机制证据，不重复已失败入口 |
| 纯 OCR／坐标发送 | 理论上能利用视觉界面 | 群身份、真实 @、消息去重及焦点可靠性缺证；本轮未验证 | 不作为当前原群自动化的可靠替代 |
| Windows Hook 研究 | 已做 4.1.13.65 静态候选迁移及三轮有界动态观测；未注入 DLL | 入站命中、对象布局、群／成员、真实 @ 未验证；R2/R3 样本方向不成立 | 先纠正样本方向与时间关联；不直接沿用旧布局，不开启收发 |
| GeWe 等服务 API | 已有观察器及本地 HTTPS 集成基础 | 缺有效服务接入、真实回调契约、混合群样本与来源证明；费用未确认 | 保留适配资产，不能写成免费可用后端 |
| WeChatPadPro Cloud 托管 | 平台文档及用户取码尝试反馈 | GetQRMac POST 502＋缺少 CORS 头；完整 Network、具体上游根因和登录成功缺证 | 先核对已失败请求链路；独立于 861，不能只补 CORS 就算打通 |
| WeChatPadPro MAX 自部署 | 已有文档研究和独立离线观察器；文档要求平台 TokenKey | 自部署仍依赖授权；与 legacy 契约不同；@、历史、身份等仍有缺口 | 可研究短期验证条件；不自动切换、不按永久授权采购 |
| WeChatPadPro 非 MAX Windows 861 | 固定包、授权诊断及离线接收适配器已有交付 | 最近授权服务业务失败；无有效设备 key；未扫码和原群收发 | 维持 G1；有匹配 key 优先核验，无新证据不重复签发 |
| StarBot Pro 本地 Windows 接入 | 文档提供 HTTP 分派、群消息结构化 @、个微侧企微群与成员查询 | 4.1.13.65 支持未明确；RPA／DLL／协议的实际调用路径未确认；回调、历史、送达及 Pro 报价有缺口 | 有条件 PoC 候选；先确认机制与版本，不替换后端或恢复已暂停操作 |

官方边界本次复核：腾讯云传统群机器人说明仍明确外部群不支持配置；企业微信团队 SDK 已提供消息收发接口，所以不能概括成“企微官方只能单向推送”；腾讯 `openclaw-weixin` 当前源码声明 `chatTypes: ["direct"]`，不能据此宣称原混合群已经获得官方支持。[S1][S2][S3]

会话存档可作为另一类分析来源，但“有读取来源”与“能以个人号向原群发消息”是两个独立问题。本报告沿用既有官方边界研究，不将存档开通条件或当前权限矩阵视为本次重新验收的事实。[E1]

## 六、候选通道的阻塞、商业条件与自建边界

### 6.1 已经收敛的根因

有界授权试验中，上游生成请求在 11.281 秒后返回 HTTP 200，但业务 `code=1`，明确报告自动注册管理员密钥时查询系统用户失败，其数据库连接超时；没有设备 key。固定网关约 5 秒的等待导致它先超时，遮蔽了更具体的上游原因。[E9]

据此可以解释该次失败，却不能断言所有更早的未知请求都由同一原因造成。健康检查成功只说明相关入口可达，不能证明数据库恢复；调整本地 MySQL、Redis 或增加等待也不能直接修复上游数据库。当前报告未重新探测该服务，其是否恢复仍未知。

### 6.2 自建不等于完全自主

该构建可在本地运行，但授权依赖已经表现为外部故障点。公开资料与新附件不足以构建协议核心；新 `WeChatPadPro-2.01.zip` 包含文档、脚本、配置与预编译发布包，不能当成完整网关源码。其内嵌 Windows 构建早于当前 20250822 基线，Swagger 路由数量更多也不能证明更适合当前目标。[E11][E12]

因此，无法仅凭当前材料承诺本地修复供应方授权实现、消除其外部依赖或实现完全离线运行。消息正文具体经过哪些服务、会话恢复和设备并存行为，也仍需验证。

### 6.3 MAX 与 legacy 必须分开

两者的路径、请求模型、鉴权及回调签名不能混用。MAX 文档签名公式只覆盖部分元数据，既有离线研究已指出它不能单独证明消息正文完整性；新附件 Webhook 示例则使用时间戳与原始请求体签名，但示例并不是固定 861 构建已观测到的契约。[E8][E11][E12]

接收方必须对固定构建的真实样本验证字段和认证。HTTP 客户端没有重试，也不能证明黑盒网关内部没有重发；需要结合消息 ID、提交结果及接收端记录判断。

### 6.4 Cloud 付费服务与实际权益

v1.3 新增运行反馈：分享记录显示 `api.wechatpadpro.com/v1/Login/GetQRMac` 的 POST 请求出现 502，且响应缺少 `Access-Control-Allow-Origin`。这是登录取码阶段的失败证据，不是已登录或已付费证明。502 与 CORS 分属上游响应和浏览器读取许可两层；“不带跨域头的网关错误响应”为合理解释，具体故障组件仍待 Network／平台日志核实，Aid 错误和账号限制均未证实。不能据此重装本机微信、恢复旧 UIA 实验或将 Cloud 与 861 上游数据库超时合并归因。详见 [E17] 第 2 节。

指定调研任务读取到的平台公开能力如下。它们属于产品说明，不能当成每个付费档位均包含的权益，也不是本项目实测结果。[E14]

| 服务层 | 页面说明 | 尚需确认 |
|---|---|---|
| Cloud 托管 | 微信节点连接、在线状态、运行维护及消息／联系人／群组 API | 套餐是否包含托管费、允许的账号数和运行实例数 |
| 事件通道 | Webhook、WSS 消息及状态事件 | 认证、重放、历史、额度、可用性及原群样本 |
| 凭证管理 | 工作区 API Key 与节点 Access Token 分离 | 具体权限、轮换、到期和限流行为 |
| 企业方案 | 多实例、权限审计、系统集成、技术支持及单独报价的私有化 | 普通套餐是否包含、服务承诺及独立部署范围 |

调研记录中的体验页面显示 **3 天、1 个访问凭证、1 个运行客户端、1 个账号名额**，同时注明可由管理员调整、以后台配置为准。这不是当前账号已获得的试用权益。公开价格说明要求登录后按账号身份展示套餐，故月费、年费、调用量、额外托管费及实际可购方案仍未知，不据此计算预算。[E14]

Cloud Swagger 的页面观察记录区分 `X-Admin-cloudToken`（工作区）与 `X-Cloud-Access-Token`（节点），并说明节点 Token 只访问对应节点。完整目录需验证 Key，本轮没有取得完整 Cloud schema，也未调用 API。MAX 的 TokenKey、设备 Token 和旧 861 管理／设备 key 必须分别建模；名称相似不代表可以互换。[E14]

### 6.5 到期不续费：可确定边界与待验证行为

指定调研任务记录的服务条款将功能访问权限限定于订阅或授权有效期，且不转让软件知识产权。作为研究结论，不能据此假设“到期只失去升级和客服，消息收发永久保留”；具体合同权益仍以实际套餐、订单及许可为准。本次未独立取得条款正文，亦未进行到期试验。[E14]

| 对象 | 报告采用的判断 | 不能擅自写成的事实 |
|---|---|---|
| Cloud API、节点、Webhook／WSS | 按可能中断设计；续用权未确认 | 到期立即全部停止，或永远继续 |
| 已登录微信会话 | 下线时间、下一次鉴权和重登限制未知 | 一到期必踢下线，或只要不重登就永久可用 |
| MAX 自部署进程 | 文档要求平台 TokenKey；到期拦截位置与持续校验频率未知 | 本地运行必定不受订阅影响 |
| 平台日志、配置和会话数据 | 保留、导出窗口、删除及续费恢复政策未知 | 到期数据必删，或永久保留 |
| 自有 Agent、业务代码与本地数据库 | 自有部分可以保留；接入通道可能失效 | 业务程序还能启动就代表微信链路可用 |

工程上应识别凭证过期／授权失败并暂停新动作，保留必要任务状态和待核对的发送记录；恢复后先核验会话与水位，不补发过期任务。以上是新增设计要求，尚未作为供应商到期行为或本地已实现功能验收。

### 6.6 自建服务的三个层次

| 自建范围 | 可行性与资产 | 仍依赖的条件 |
|---|---|---|
| 自建 Agent，调用 Cloud | 现有编排、审批、存储可复用；需独立 Cloud adapter | 平台托管、授权、接口契约与协议维护 |
| 自部署 MAX 协议程序 | 文档提供 Linux 二进制、Redis、平台 TokenKey 配置及设备 Token 流程 | 匹配版本程序、平台授权；并非已验证脱离供应商运行 |
| 从源码独立构建整个协议服务 | 本项目材料不足以确认可执行 | 完整核心源码、许可证、构建链、版本适配和独立运行许可 |

本次重新读取的 MAX 快速入门要求配置 `token_key_for_validate`，从平台取得 TokenKey 后再生成设备 Token。它直接支持“自部署仍有平台授权前置条件”的判断，但不证明校验频率、离线宽限或到期断开时机。[S5]

可以自行编写业务服务和合法取得接口权限后的适配器；仅搭建一个同名授权端点、使用自生成 Token 或拥有发行包，并不能建立对平台和微信协议的有效访问。普通套餐是否交付核心源码、永久运行权及商业使用许可，均未确认。[E14]

### 6.7 StarBot Pro：文档更贴近混合群，实机条件仍缺

StarBot 的价值在于提供了可以验证的具体字段与操作，而不是已经证明可靠接管。专项方案记录其本地入口为 `POST http://localhost:10001/api/processor`，通过 `type` 与 `params` 分派；主动调用的 `Authorization` 直接携带配置 token，空 token 会关闭该鉴权。实际接入时应使用非空 token，不能自行假设需要 `Bearer` 前缀，也不能将这套主动调用鉴权视为回调已认证。[E16]

| 能力 | 文档线索 | 仍须取得的证据 |
|---|---|---|
| 群消息接收 | `event="10003"`；样例有 `messageId`、`atWxIdList` 和身份字段 | 目标混合群真样本、消息 ID 唯一范围、历史与重连语义 |
| 群与成员查询 | `getWorkGroupList`、`getWorkGroupMemberInfoList` 位于个人微信侧 | 真实集合、分页、缓存和企微成员键；现有响应示例不足 |
| 发送文字 | `sendTextMessage` | 成功状态语义、原生消息 ID、双端送达与超时对账 |
| 指定成员 @ | 正文内使用厂商标记 | 企微和个微成员分别收到原生提醒；标记转义规则 |
| 在线与本人 | `getLoginStatus`、`robotInfo` | 完整状态枚举、缓存语义；不能将手机待确认状态当在线 |

目录的“企业微信开发中”与“个人微信账号在企微混合群工作”是两条不同路径，不能相互替代或直接否定。Pro 版本表对个微侧企微群查询标为支持，是选型线索；接口存在仍不证明本目标群可收可发。[E16]

厂商首页自述 RPA／无障碍点击框架，目录同时有 DLL、CDN 和协议分类。合理结论是逐项核查接收、文字发送、指定成员 @、企微群查询所走的实际机制，而不是判定所有接口均为 RPA，或反过来宣称已经摆脱 UI 依赖。若实施仍要求排除底层 UI RPA，当前材料尚不满足选型条件；需先确认准确交付版本与路径。最小化、锁屏、远程桌面断开后的行为也应纳入实测。[S10][E16]

未发现专项调研所读页面明确支持 Weixin 4.1.13.65。历史更新条目、接口目录版本号与页面修改时间不一致，不能据此确认最新稳定程序或维护响应。现有 UIA 探针失败既不能证明 StarBot 必然失败，也不能被 StarBot 的宣传抵消。

### 6.8 StarBot 的契约与商业缺口

StarBot 文档中的 `fromWxId`、`finalFromWxId` 应由已知群与发送者样本确认方向，不能按名字直接赋为群键和成员键；`atWxIdList` 缺失不等于空列表；文档缺少明确历史标志时保留 `history_status=unknown`。消息 ID 保持字符串，拒绝浮点精度损失；`messageSource` 或到达时间不能擅自当成新消息证明。[E16]

发送响应示例没有原生消息 ID，HTTP 200／业务成功只作为受理线索。回调签名、重投、队列持久化、断点续收、发送幂等和查询机制均未明确。适配层能阻断不确定发送，却不能补偿上游从未交付的消息；不得承诺端到端恰好一次。

指定成员 @ 的厂商语法由适配器根据已绑定成员键生成，不交给模型直接拼接。若正文包含原始操作标记，在未确认转义规则前应拒绝提交；JSON 转义不能解决正文被二次解释的问题。此项是专项方案提出的实现要求，本次没有新增代码或安全验证结果。[E16]

标准版、标准买断版和 Pro 的权益分开。专项方案读到的标准买断版历史“500”不是 Pro 报价，不能用于估算 Pro 年费或总成本。Pro 试用、账号／实例／设备绑定、调用上限、升级维护、联网授权及到期规则仍待确认；不能把 WeChatPadPro 的体验配额或条款移植给 StarBot。SaaS／私有化描述也不证明交付核心源码、永久授权或完全断网运行。[E16]

## 七、可复用架构与实施重点

建议沿用现有 API Channel 与 runtime，将接入后端限制在边界内：

```text
固定构建与设备会话
  → 单一路径有界接收
  → 来源校验、账号／群／成员映射
  → 标准事件、历史水位、持久化去重
  → 触发策略与必要上下文
  → 模型草稿／业务字段提取
  → 人工批准或已核准的自动规则
  → outbox 串行提交
  → 原群双端核验、异常暂停与人工接手
```

`api_channel.py`、`api_runtime.py`、`api_store.py` 和 `agent_policy.py` 已构成可复用的编排基础；GeWe 与 Pad 观察器保持取样和协议验证用途。861 已有 transport、channel、decoder、receive 离线适配器。当前构建交接记录专项 19 passed、较早全量 244 passed；本次未复跑。去重水位明确为 `id_set`，排序与可重放游标仍 unknown，合成夹具为 `not_observed`，不能称为已完成真实同步接入。[E13]

若以后选择 Cloud 或 MAX，应另行锁定其 provider、构建、凭证与真实事件 schema，再映射到同一 Channel；保留业务编排，不把三种产品的 Header、路由或回调字段拼接使用。更换供应商后的群与成员标识也应重新核验。

StarBot 同样复用现有 Channel 与 outbox，拟新增独立 `StarBotChannel`、只读观察器、配置和契约测试；这些在专项方案中均为待实现。首轮建议 StarBot、观察器及 Agent 同处一个隔离 Windows 节点，不直接暴露 10001 控制端口。回调来源验证与主动 API token 分开，事务持久化成功后再确认回调，模型异步处理；桥接 token 不自动升级为厂商来源证明。没有可接受的来源验证前，仅开展隔离观察，不启用无人值守发送。[E16]

实施中最重要的约束是：目标账号与群由程序绑定，不能由模型任意选择；真实 @ 必须来自结构化字段；未知身份或历史状态不触发；稳定消息 ID 用于去重；提交超时进入 `unknown` 并暂停，不能直接重发；确认送达需要接收端证据。

由于业务动作与输入正文有不同信任等级，群成员发来的“改目标群、关闭校验、导出历史”等文字不能改变运行权限。后续接入业务系统时，应单独定义允许查询及允许写入的动作，而不是把完整桌面或任意工具权限交给群聊触发。

## 八、后续验收关卡与完成标准

以下为建议验收标准，不是本次已执行结果。G0—G6 对齐现有非 MAX 计划；若另选 Cloud／MAX，先确认产品、套餐和独立契约，替换相应构建与授权关卡，不能沿用 861 的 G0／G1 作为证明。涉及账号和发送操作时仍核对当时有效授权。

| 关卡 | 必须完成的验证 | 通过标准 | 不通过时 |
|---|---|---|---|
| G0 构建锁定 | 固定 ZIP／EXE／Swagger 哈希，区分管理与设备 key | 唯一 20250822 非 MAX 构建，契约无 MAX 混用 | 保持离线核查 |
| G1 授权可用 | 有新恢复依据后进行有界复验 | 非空有效设备 key，并通过无副作用状态核验 | 保留收据；未知先对账；同类失败不连发 |
| G2 身份绑定 | 在线本人、原群稳定键及目标成员映射 | 唯一账号与原群；企微成员键可明确对应 | 不接入发送 |
| G3 接收及 @ | 至少 20 条独立消息，含两类成员及真实／伪 @、历史、重复、自身、引用对照 | 每条有人工标签、稳定 ID 与时间；分类一致；未知样本不触发 | 仅观察；不升级自动回复 |
| G4 固定回复 | 人工触发 1 条 ACK，确认后再完成后续 ACK | 3 条分别有提交与个微／企微双端证据；错群、重复发送均为 0 | unknown 停止；不得把提交当送达 |
| G5 AI／主动任务 | 先审核草稿，再按批准范围验证回复与指定成员 @ | 无伪 @／历史／本人循环触发；原生 @ 与多目标隔离分别通过 | 回退人工审批 |
| G6 连续运行 | 至少 30 分钟，覆盖断线、重连、进程重启和过期任务 | 样本无已知漏读、无重复／错群；恢复不回放已处理任务 | 分项列出缺口，不能标稳定 |
| G7 商业连续性（选用订阅服务时） | 明确套餐期限、到期／授权服务不可用时的 API、回调、会话、重登及数据规则；在获准测试环境验证 | 书面权益明确；试验与规则相符；中断后暂停、恢复不误补发 | 不认定具备持续运营条件，不按永久独立运行采购 |

其中 G3 的 20 条应是独立原生消息；一条消息内包含多个编号只计一条。若仍研究数据库支线，另须验证当前 WAL 世代、分库发现及同秒迟到消息，API 关卡不能代替这些测试。

通过 G6 只证明指定环境的短时 PoC。正式使用前，建议另做至少 7 天的有界试运行，记录在线率、采样漏读、重复、人工介入次数、P50／P95 端到端延迟和模型成本；该周期为报告建议，不是已授权定时任务，也不是账号安全保证。指标目标需结合业务响应时限设定，本报告不虚构已达到的 SLA。

### StarBot 独立验收计划

StarBot 专项方案提出更完整的 P0—P4，适用于该候选后端，不改写上表 861 最小关卡，也不把历史数据库 @ 样本计入 StarBot 成绩。所有数量均为拟议验收标准，不是实测结果。[E16]

| 阶段 | 通过条件 | 未通过时 |
|---|---|---|
| P0 版本与机制 | 准确客户端版本矩阵、可信安装包与摘要、Pro 权益、实际机制及关键 JSON 明确；与当前实施约束相容 | 停在候选研究，不安装或替换通道 |
| P1 离线适配 | 大 ID 无损、未知身份／历史阻断、去重、标记不能越权、发送 unknown 不重试 | 修复对应契约；不拿 fake 当真实回调 |
| P2 只读采样 | 单账号单原群 100 条受控输入可逐条核对，覆盖两类成员、真实／伪 @、重连历史 | 仅观察，来源或历史未知不自动回复 |
| P3 人工发送 | 普通文字、@ 个微、@ 企微各 10 条，共 30 条双端核对，原生提醒有效，无错群／错人／重复 | 停发并对账，不切换其它后端补发 |
| P4 有界试运行 | 单群 48 小时，记录掉线、恢复、延迟与缺失；无误发且异常可停发告警 | 报告缺口，不升级生产可用 |

专项方案的回调 ACK P95 ≤ 500 ms、账号每分钟最多 6 次发送及同群至少间隔 10 秒，均为拟议实验参数，不是厂商性能、平台限制或防封保证。48 小时试运行也不能替代长期稳定性和订阅到期验收。

## 九、成本、工期与决策建议

既有零采购预算仍是实施基线，本次权益调研不等于批准付费。Cloud／MAX 的账号实际价格和权益尚未取得，GeWe 资格与费用也未确认；不能提供可靠总价。后续预算应分别核算订阅／授权、节点或账号额度、服务器、模型、运维及停服迁移成本。自部署减少部分托管依赖，却可能增加服务器维护，且不自动免除授权费用。[E14]

若用户后续选择商业验证，优先核查是否具备页面所述体验资格，或取得最短周期的明确报价，先验目标混合群，再决定云托管或自部署。不建议因“付费一次即可永久自建”的预期购买长期套餐。采购前应取得：Cloud 与 MAX 各自价格及账号／实例／Key／调用上限；到期与宽限、重登和 Token 生成规则；授权服务失联行为；数据保留与导出；核心源码和运行许可范围；混合群收发与原生 @ 的适用性。该清单用于决策，本次未代发供应商或采购。

可将后续两天分为“第一天锁定构建与授权，条件满足后登录、绑定和收样；第二天完成固定回复与恢复检查，余量验证 AI”。这是外部条件满足后的安排，不是无条件工期。若 G1 持续受阻，交付内容应改为契约、transport／离线测试及阻塞证据，不能用聊天演示替代原群验收。

当前建议作出以下项目决策：

- **StarBot 先进入 P0 评估。** 优先补准确版本、各接口实际机制、混合群 JSON、回调与送达语义及 Pro 权益。研究价值成立，实机可用性未成立；不默认它优于 Cloud／MAX，也不修改当前后端配置。

- **非 MAX 861 保持有条件恢复。** 已有离线适配器不重复开发；有匹配 key 优先核验，无新恢复证据维持 G1。购买其它产品权益不能当作旧签发服务已恢复。
- **Cloud／MAX 增列为待决策商业候选。** 先核对权益、试用资格及目标群验证条件；尚未选定、未购买、未迁移。当前研究不能判定付费必然打通，也不能判定付费必然无效。
- **保留数据库路线的历史成果。** 它证明局部读取可能，但按最新计划不恢复取钥或另开实施支线。
- **UIA 已恢复研究，但停止无新依据的重复试验。** v2/v3 提升的是诊断可信度，聊天语义树仍未出现；下一步由新的控件或机制证据驱动。
- **Hook 下一关是有效入站关联。** R2/R3 清理通过、零命中属实，但发出方向样本不能证伪入站路径。先修正样本，再按当时具体范围安排实验，不自动追加附加、对象读取或注入。
- **暂不批准生产无人值守接管。** 当前缺原群双端送达、连续运行及账号与业务风险的实测基础。

对外可准确表述为：**“项目已完成多路线技术研究、部分真实读取验证及受控 Agent 框架建设；当前正在收敛个人微信接入通道，原混合群自动回复尚未通过验收。”**

StarBot 专项方案估计复用现有 Agent 后需 **4.5–8 人日**，另含 48 小时观察时间；不包含厂商等待、修复、客户端迁移和生产 SLA 建设，不能理解成确定的日历交付期。预算另计 Pro 授权、Windows 节点、可选私有化／维护及模型调用。先明确 P0 条件再安排工程投入，不能沿用 861 “两天首关”的期望作为 StarBot 完整交付承诺。[E16]
