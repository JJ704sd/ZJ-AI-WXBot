# Agent 接管个人微信参与企微／个微混合群工作的技术可行性研究报告

**版本：1.0｜研究截止：2026 年 9 月 16 日｜对象：技术负责人、项目负责人及实施人员**

## 一、研究结论

**本项目具有继续进行受控技术验证的基础，但尚不具备宣布“Agent 已接管个人微信并能在原混合群稳定工作”的证据。** 已有成果包括有限场景下的真实消息读取、部分真实 @ 识别、独立模型调用、人工审批与发送状态管理、API Agent 离线闭环及观察器基础设施。决定能否实际交付的核心缺口，是一个在指定账号、指定混合群中验证过的可靠收发通道，以及该通道上的身份映射、真实 @、送达和恢复能力。

截至研究截止时间，可以作出四项判断：

1. **消息理解与受控任务编排具备实现基础。** 本地已有可复用代码及离线测试；模型接口也有独立真实调用记录。无需为更换微信接入方式重新设计整套 Agent。
2. **读取能力曾在限定场景中部分成立。** 9 月 15 日数据库路线取得真实混合群消息和结构化 @ 证据，但未完成完整编号消息、当前 WAL 世代和全部反例验收，不能升级为持续完整读取。
3. **原群发送闭环仍未成立。** 桌面发送因无法核验当前群而停在发送前；API 路线尚无原群双端收件证据。模型调用成功和本地接口返回成功均不能填补这一缺口。
4. **当前非 MAX Windows 861 路线属于“有条件可验证”，不是“已可部署”。** 最近有界试验拿到了上游数据库连接超时的明确业务错误，未取得有效设备 key。缺少上游恢复证据时，重复本地网络调参不能解除该阻塞。

建议保留现有 Agent 与证据资产，按最新本地计划集中验证固定 861 构建；先取得“一次真实 @ → 人工固定回复 → 个微与企微双端确认”的最小结果，再扩展 AI 回复、定时 @ 和业务对话。若外部授权条件持续不满足，应交付明确的阻塞结论与离线成果，不承诺两天内完成真实机器人。

## 二、研究范围与证据口径

### 2.1 “接管”在本报告中的含义

目标是由一个个人微信账号进入含企业微信成员与个人微信成员的外部群，接收目标群新消息，识别发送者和真实 @，理解任务，并通过同一账号向原群回复。进一步能力包括定时提醒指定成员、收集回复和关闭任务。

应分开评价三个层次：

| 层次 | 交付内容 | 当前判断 |
|---|---|---|
| 辅助工作 | 已授权消息输入、分析、草稿与人工审核 | 软件基础已具备，实时输入仍受通道约束 |
| 受控代理 | 程序接收、人工批准、原群发送、送达留证 | 离线框架具备；真实收发闭环未完成 |
| 无人值守代理 | 自动触发、自动回复、定时任务、异常恢复 | 仅有部分离线机制，不能作为生产能力交付 |

本轮研究以文本为主，不把图片、语音、文件解析、内部订单查询、报价承诺或业务系统写入列为已实现能力。群聊文字是任务数据，不是扩展系统权限的指令。

### 2.2 本次核查方法

本报告核查了本地 Git 历史、现有研究和规格、脱敏阶段证据，以及关键运行时和适配器代码；并重新访问部分腾讯官方文档及维护者页面。未重新运行微信、取钥、读聊天库、启动网关、扫码、发送消息或调用付费模型。

本地基线为 `main`，HEAD `523a1b7d583f4dc2940d29990553f788c55d46b3`。工作区存在后续 UIA 探针、交接、附件审计、861 计划及 transport 等未提交改动，本报告将其作为工作区资料单独评价，不视为该提交已经交付的能力。收尾时还观察到其它工作新增 legacy channel、decoder、receive、配置及测试文件，并修改 API 契约；这些并行开发内容未完成本报告审查，不能据文件存在升级可行性结论，后续应以独立测试及实机证据增补报告。客户端版本沿用 9 月 16 日实测记录：Weixin `4.1.13.65`、WXWork `5.0.11.6018`；本次未重测客户端。

## 四、能力成熟度与关键证据

### 4.1 真实消息读取：局部成立，完整性未闭合

9 月 15 日记录显示，目标 `message_0.db` 完整性检查通过，群会话可唯一绑定，成员结构中出现企微 `@openim` 键及个微本人键。初次有界续读取得水位后的 3 条记录，后续扩展到 8 条。这证明该限定环境存在可用的结构化读取路径。[E3]

但这些记录位于主库已提交页，当前 WAL 世代有效已提交帧为 0；旧世代盐值不一致的帧被跳过。因此尚未证明未 checkpoint 的新消息可以稳定读取。20 个测试编号被集中发在 2 条原生消息中，也不满足“企微 10 条＋个微 10 条独立消息”的验收要求。

多分库发现、迟到消息、同秒消息、重启水位及当前 WAL 覆盖必须分别验证。缩短轮询间隔不能修复消息排序或分库发现错误。Chat-Lab 第二轮已用合成实验发现相关边界，不能因界面和业务分析功能更新就认为这些问题自动解决。[E2]

### 4.2 真实 @：部分正反例成立，不能只匹配正文

关键进展是确认真实 @ 可出现在压缩 `source` 的顶层 `<atuserlist>` 中；仅查看 `packed_info_data` 可能误判为空。后续记录包含原生单独 @本人、纯文字伪 @、本人发送的结构化 @ 样本。原生 @他人、引用旧 @、@所有人等反例尚未全部闭合。[E3]

这里还必须区分“收到别人 @本人”和“向企微成员发出原生 @”。前者局部成功并不证明后者可用。昵称、企业标签和成员稳定键未完全映射时，不应执行指定成员提醒。

### 4.3 模型与业务执行：模型可调用，业务正确性另验

T3 三条真实请求耗时分别为 1.344、3.359、5.297 秒；模型正确回答时间换算，并对无法访问的内部订单信息明确表示无权限，但对蓝天成因的表述有过度简化。上述耗时是模型请求和解析时间，不是群消息端到端延迟。[E4]

当前适合继续验证一般问答、固定字段收集和待审核草稿。报价、订单状态或客户承诺需要额外接入可追溯业务数据，不能由模型凭群聊推断后直接对外确认。现有离线任务状态机可作为收集“是否收到／是否愿意”等字段的基础，尚无真实业务效果指标。

### 4.4 原群发送：决定性缺口

T4 记录为发送尝试 0、本地提交 0、接收确认 0。原因是微信只暴露外壳节点，无法证明当前选中的就是绑定群；实现因此停在 `not_sent`。这是发送保护生效的证据，不是发消息失败或发出后丢失。[E5]

API A1 的 `accepted` 来自 fake channel，`verified=0`。当前代码仍保留 `A1 refuses live start`。后续不能通过删除阻断、把 HTTP 200 当成功或把本地气泡当双端送达来升级验收状态。[E6]

### 4.5 稳定性与账号风险：没有足够实测

仓库已有重复事件、冲突暂停、崩溃后不盲目重发、额度、过期任务取消等离线覆盖，但尚无真实混合群连续运行、断线恢复和跨日观察结果。不能据此估算账号受限概率、可用率、漏读率或长期维护成本。此处的风险判断来自非官方接入依赖及证据缺口，不构成“已发生封号”的结论。

| WeChatPadPro 非 MAX Windows 861 | 固定包、路由审计、授权诊断和后续关卡较明确 | 最近授权服务业务失败；无有效设备 key；未扫码和原群收发 | 当前有条件验证主线，外部阻塞未解除前不承诺完成 |

官方边界本次复核：腾讯云传统群机器人说明仍明确外部群不支持配置；企业微信团队 SDK 已提供消息收发接口，所以不能概括成“企微官方只能单向推送”；腾讯 `openclaw-weixin` 当前源码声明 `chatTypes: ["direct"]`，不能据此宣称原混合群已经获得官方支持。[S1][S2][S3]

会话存档可作为另一类分析来源，但“有读取来源”与“能以个人号向原群发消息”是两个独立问题。本报告沿用既有官方边界研究，不将存档开通条件或当前权限矩阵视为本次重新验收的事实。[E1]

## 六、861 路线为什么仍被阻塞

### 6.1 已经收敛的根因

有界授权试验中，上游生成请求在 11.281 秒后返回 HTTP 200，但业务 `code=1`，明确报告自动注册管理员密钥时查询系统用户失败，其数据库连接超时；没有设备 key。固定网关约 5 秒的等待导致它先超时，遮蔽了更具体的上游原因。[E9]

据此可以解释该次失败，却不能断言所有更早的未知请求都由同一原因造成。健康检查成功只说明相关入口可达，不能证明数据库恢复；调整本地 MySQL、Redis 或增加等待也不能直接修复上游数据库。当前报告未重新探测该服务，其是否恢复仍未知。

### 6.2 自建不等于完全自主

该构建可在本地运行，但授权依赖已经表现为外部故障点。公开资料与新附件不足以构建协议核心；新 `WeChatPadPro-2.01.zip` 包含文档、脚本、配置与预编译发布包，不能当成完整网关源码。其内嵌 Windows 构建早于当前 20250822 基线，Swagger 路由数量更多也不能证明更适合当前目标。[E11][E12]

因此，无法仅凭当前材料承诺本地修复供应方授权实现、消除其外部依赖或实现完全离线运行。消息正文具体经过哪些服务、会话恢复和设备并存行为，也仍需验证。

### 6.3 MAX 与 legacy 必须分开

两者的路径、请求模型、鉴权及回调签名不能混用。MAX 文档签名公式只覆盖部分元数据，既有离线研究已指出它不能单独证明消息正文完整性；新附件 Webhook 示例则使用时间戳与原始请求体签名，但示例并不是固定 861 构建已观测到的契约。[E8][E11][E12]

接收方必须对固定构建的真实样本验证字段和认证。HTTP 客户端没有重试，也不能证明黑盒网关内部没有重发；需要结合消息 ID、提交结果及接收端记录判断。

## 七、可复用架构与实施重点

建议沿用现有 API Channel 与 runtime，将接入后端限制在边界内：

```text
固定构建与设备会话
  → 单一路径有界接收
  → 来源校验、账号／群／成员映射
  → 标准事件、历史水位、持久化去重
  → 触发策略与必要上下文
  → 模型草稿／业务字段提取
  → 人工批准或已核准的自动规则
  → outbox 串行提交
  → 原群双端核验、异常暂停与人工接手
```

`api_channel.py`、`api_runtime.py`、`api_store.py` 和 `agent_policy.py` 已构成可复用的编排基础；GeWe 与 Pad 观察器保持取样和协议验证用途。工作区新增 `pad_legacy_transport.py` 只说明 transport 工作已开始，本次没有其完整测试和 live 集成证据，不能将其描述为完整 legacy 通道。

实施中最重要的约束是：目标账号与群由程序绑定，不能由模型任意选择；真实 @ 必须来自结构化字段；未知身份或历史状态不触发；稳定消息 ID 用于去重；提交超时进入 `unknown` 并暂停，不能直接重发；确认送达需要接收端证据。

由于业务动作与输入正文有不同信任等级，群成员发来的“改目标群、关闭校验、导出历史”等文字不能改变运行权限。后续接入业务系统时，应单独定义允许查询及允许写入的动作，而不是把完整桌面或任意工具权限交给群聊触发。

## 八、后续验收关卡与完成标准

以下为建议验收标准，不是本次已执行结果。优先对齐现有非 MAX 计划；涉及账号和发送操作时仍核对当时有效授权。

| 关卡 | 必须完成的验证 | 通过标准 | 不通过时 |
|---|---|---|---|
| G0 构建锁定 | 固定 ZIP／EXE／Swagger 哈希，区分管理与设备 key | 唯一 20250822 非 MAX 构建，契约无 MAX 混用 | 保持离线核查 |
| G1 授权可用 | 有新恢复依据后进行有界复验 | 非空有效设备 key，并通过无副作用状态核验 | 保留收据；未知先对账；同类失败不连发 |
| G2 身份绑定 | 在线本人、原群稳定键及目标成员映射 | 唯一账号与原群；企微成员键可明确对应 | 不接入发送 |
| G3 接收及 @ | 至少 20 条独立消息，含两类成员及真实／伪 @、历史、重复、自身、引用对照 | 每条有人工标签、稳定 ID 与时间；分类一致；未知样本不触发 | 仅观察；不升级自动回复 |
| G4 固定回复 | 人工触发 1 条 ACK，确认后再完成后续 ACK | 3 条分别有提交与个微／企微双端证据；错群、重复发送均为 0 | unknown 停止；不得把提交当送达 |
| G5 AI／主动任务 | 先审核草稿，再按批准范围验证回复与指定成员 @ | 无伪 @／历史／本人循环触发；原生 @ 与多目标隔离分别通过 | 回退人工审批 |
| G6 连续运行 | 至少 30 分钟，覆盖断线、重连、进程重启和过期任务 | 样本无已知漏读、无重复／错群；恢复不回放已处理任务 | 分项列出缺口，不能标稳定 |

其中 G3 的 20 条应是独立原生消息；一条消息内包含多个编号只计一条。若仍研究数据库支线，另须验证当前 WAL 世代、分库发现及同秒迟到消息，API 关卡不能代替这些测试。

通过 G6 只证明指定环境的短时 PoC。正式使用前，建议另做至少 7 天的有界试运行，记录在线率、采样漏读、重复、人工介入次数、P50／P95 端到端延迟和模型成本；该周期为报告建议，不是已授权定时任务，也不是账号安全保证。指标目标需结合业务响应时限设定，本报告不虚构已达到的 SLA。

## 九、成本、工期与决策建议

当前零采购预算可以继续支持本地代码、协议审计、合成测试和报告整理，但不等于第三方授权、模型、托管及维护总成本为零。GeWe 资格与费用未确认；861 缺有效设备 key；已有模型三次调用也不构成长期免费承诺。

可将后续两天分为“第一天锁定构建与授权，条件满足后登录、绑定和收样；第二天完成固定回复与恢复检查，余量验证 AI”。这是外部条件满足后的安排，不是无条件工期。若 G1 持续受阻，交付内容应改为契约、transport／离线测试及阻塞证据，不能用聊天演示替代原群验收。

当前建议作出以下项目决策：

- **继续有限投入非 MAX 861 验证。** 首要里程碑是 G1 和 G4，不继续扩展复杂 Agent 功能来掩盖通道缺口。
- **保留数据库路线的历史成果。** 它证明局部读取可能，但按最新计划不恢复取钥或另开实施支线。
- **结束当前 UIA 重复试验。** 若未来出现准确版本的新机制或明确环境变化，再重新评估；现有失败不应被改名为成功。
- **暂不批准生产无人值守接管。** 当前缺原群双端送达、连续运行及账号与业务风险的实测基础。

对外可准确表述为：**“项目已完成多路线技术研究、部分真实读取验证及受控 Agent 框架建设；当前正在收敛个人微信接入通道，原混合群自动回复尚未通过验收。”**
