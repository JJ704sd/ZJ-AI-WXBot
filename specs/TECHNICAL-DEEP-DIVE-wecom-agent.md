## 一、为什么必须切成三层

【报告】的核心论点是"在 Hook 接入与业务 Agent 之间加一层编排"。但真正的原因不是"结构更清晰"，而是
**三层的服务等级目标方向相反，耦合会让最慢的拖垮最严的**。

| 层 | 目标 | 优化方向 | 最坏情况 |
| --- | --- | --- | --- |
| 接入（Collector） | 不丢、不乱序 | 吞吐优先，尽量快 | 慢 10ms 无所谓，但漏一条就是错 |
| 编排（Coordinator） | 不错判、能等待 | 正确性优先，可以慢 | 慢几秒可以等，判错要人背 |
| 仲裁（Dispatcher） | 不越权 | 严格优先，宁可拒 | 拒一次只是少回一条，越权一次是事故 |

三者串在一个 `poll_loop` 里会出现这个具体故障：

```
poll_loop 顺序执行：副本检查 → 自动回复 → 计划 → (新)模型推理
                      ↑ 模型推理耗时 3-8 秒
                      ↑ 这 3-8 秒内 poll_loop 不再轮询副本
                      ↑ 期间到达的消息堆积，冷却窗口/有效窗口可能滑过
                      ↑ 结果：为了"少回几条"付出"漏掉几条"
```

这就是报告 §4.1 说"不能把推理放进 poll_loop"的真实代价——不是风格问题，是**用采集完整性换回复质量**。
反过来也一样：如果把采集塞进仲裁的锁里，一个慢的提交会卡住整条采集链。

【报告】给的解法是"把推理移出临界区，保留提交前的身份校验"。注意这个措辞——**移出的是推理，不是校验**。
校验必须留在锁内，否则"检查通过后被接管、旧发送仍无条件通过"（报告 §5.4 原话）。

## 二、延迟链路：为什么不能相加

【报告】§5.2 给了数据库路线的延迟构成，并明确拒绝把它们加起来当上界。这是反直觉但正确的：

```
T_端到端 = T_客户端落库
         + T_源变化检测        (约 5s 轮询)
         + T_副本构建          (不可变副本拷贝/校验)
         + T_主循环等待         (约 2s)
         + T_编排判定
         + T_模型推理
         + T_仲裁校验
         + T_原生提交
         + T_对端可见
```

**为什么不能相加**：源变化检测和主循环是两个独立循环，它们**并行**；副本构建在源检测触发后才开始，与主循环不重叠；
而客户端落库时间与系统时钟无关（对方什么时候按的发送键）。

所以 `2s + 5s + 副本构建` **不是** 7s+ 的下界，而是"两个周期互相错相时的常见观测值"。

【报告】给的正确做法：**分别记录五个时点**——事件发生、被观察、信息齐备、合法启动、提交。每个时点单独统计，
才能回答"慢在哪一跳"。这也解释了为什么报告坚持要区分 `occurred_at` 和 `observed_at` 两个字段：
只有一个时间戳的话，你无法区分"客户端晚落库"和"我们晚发现"，优化方向完全不同。

**这里有个坑值得单独说**：消息时间是**整数秒**。报告 §2 已经点了 `activated < timestamp` 导致启用同秒被排除。
同理，同秒多条消息在"按时间排序"下是并列的，排序不稳定——必须用数值复合键（时间 + 分片 + 稳定 ID），
而旧视图曾用**字符串**排序 ID，大整数会被排错位置（`"10" < "9"`）。

## 三、事件契约：每个字段在防哪个 bug

报告 §2.3/§5.1 给了 `MessageEvent` 的字段清单。逐个看它们防的是什么：

| 字段 | 不加它会出的 bug |
| --- | --- |
| `schema_version` | 字段增删后，旧消费者读到缺字段的记录，行为静默改变 |
| `source_kind` | 数据库副本和 Hook 两路混在一起，无法判断一条事件从哪来、能不能互相信 |
| `collector_epoch` | 账号**重登后**新旧事件混算；旧会话的排队任务被当成本会话 |
| `event_id` | 本系统事件 ID，用于本路去重 |
| `server_id`（**字符串**） | 平台消息 ID，用于跨源核对。⚠️ 必须是字符串：平台 ID 常超 2^53，过 JS `Number` 会精度丢失 |
| `occurred_at` / `observed_at` | 只有后者就算不出延迟；只有前者算不出我们的处理时延 |
| `kind` | 撤回/更正必须能表达成**带目标引用的新事件**。若只是"改当前窗口里那条的显示文本"，所有依赖它的摘要、向量索引、未发草稿都不会失效——这是最隐蔽的一类 bug |
| `mention_ids` | 只有 `mentionSelf` 布尔值时，无法区分"只@我" vs "@我和张三" vs "@所有人" |
| `quote_id` | 引用链是最强的任务关联证据，丢了就只能靠时间和正文猜 |
| `history_status` | 分不清"刚到的消息"和"重启后重放的历史"，会拿旧消息触发新动作 |
| `decode_status` | 解码失败若静默丢弃，你永远不知道少了消息；若不置 unknown，模型会拿空正文补猜 |
| `evidence_ref` | 摘要/结论无法回到原文核对。省 token 不能牺牲可追溯性 |

**一句话总结**：这份契约不是为了"记录更多信息"，而是为了让**每一种丢失或错乱都有名字**。
没有名字的故障叫"偶发"，有名字的故障叫可修 bug。

## 四、一致性引擎：四个版本号为什么必须分开

报告反复强调 `requirement_revision` 和 `state_version` 要分别保存、分别检查。这是最容易做错的地方，
因为合并成一个计数器"看起来能跑"。

【推论】为什么分开是必须的 —— 用一个具体场景论证：

> 客户甲 @ 询问 A 型资料 → 生成草稿 A1 → **业务员人工接管** → 草稿 A1 仍在生成中。

- 接管是**技术状态变更**，不是需求变更。`state_version` 递增，`requirement_revision` **不动**。
- 提交屏障发现 `state_version` 变了 → 拒绝发送 A1。**正确**。
- 如果只有一个版本号：判据变成"版本变了所以需求变了" → 逻辑上会去重算需求，
  而需求其实没变，白白重跑一次生成；更糟的是**丢失了"是接管导致作废"这个可解释原因**，
  审计时无法区分"业务员接手"和"客户改需求"。

四个计数器各自的触发条件与语义：

| 计数器 | 递增时机 | 回答的问题 | 消费位置 |
| --- | --- | --- | --- |
| `input_watermark` | 每条输入被消费 | 我看到的输入是最新的吗 | 提交屏障 |
| `requirement_revision` | 目标/条件/动作前提变化 | 这件事还是不是同一件事 | 就绪检查 + 提交屏障 |
| `state_version` | 接管、暂停等状态操作 | 现在还允许自动动作吗 | 提交屏障 |
| `scope_epoch` | 来源切换、取消群、本人身份变化 | 这批数据还在授权范围内吗 | 编排层 + 附件 + 旧草稿 |

### 最难的那一类：入箱未消费窗口

【报告】§5.4 点出一个专门的窗口：**"更正已入箱、尚未更新需求版本"**。

```
t0  客户:"不是 A 型，是 B 型"  → 进任务收件箱（持久化成功）
t1  worker 尚未运行，requirement_revision 仍是 7
t2  仲裁校验：requirement_revision == 7 == 草稿记录的 7 → 通过
t3  草稿 A1 被发送 —— 但它基于已被更正的 A 型
```

只比 revision 会漏掉这个窗口。正确做法是**同时检查水位**：

> 提交前检查该任务及"可能影响它的未决关联输入"是否已被消费。
> 有更新输入尚未处理 → 先处理，或保守阻断旧动作。

【推论】这解释了为什么报告坚持 `input_watermark` 必须**每 run 独立保存**，而不是全局一个值：
它记录的是"这个 run 出发时看到的输入边界"。全局水位回答不了"这条 run 有没有跑在旧信息上"。

### 已确认消费位置 ≠ 发送资格的迁移

这是 M1 的本质。当前 `inbound_messages` 扫 **120 秒窗口**判断"这条消息是否触发发送"。

【报告】的原话很准：**这是发送触发，不是任务收件箱**。

- 发送资格：时间有界（120s），目的是"新鲜消息才值得回"
- 任务消费：逻辑无界，必须能跨天等待客户补资料

把两者混为一谈，就会出现"客户第二天补一句型号，Agent 已经完全不知道有个事项在等"。

## 五、双源核对：为什么正文匹配绝对不能用于去重

数据库副本和 Hook 两路拿不到共同的稳定 ID。直觉做法是按"正文 + 时间"匹配。

**这个做法有直接的灾难性反例**：

```
10:15:03  客户甲:"报价发一下"
10:15:03  客户乙:"报价发一下"
```

两路各到一条。按正文+时间去重 → 判定为同一条 → **丢一个客户的请求**，而且系统记录显示"已处理"。

【报告】§3/§4.2 的规则因此是：

- 正文/时间匹配 **只能作为"关联候选"**，作为同一条消息合并前必须有更强的证据（稳定 ID）
- 没有共同 ID 时**不做跨源去重**，两路各自成立
- 关联不确定 → **抑制发送 + 人工核对**（fail-closed）

【推论】这条规则的代价是"同一个业务事实在两路里各存一份"，收益是"绝不会静默丢客户请求"。
在混合群业务里这个交易明显划算——丢一条客户请求的业务损失远大于一次人工核对。

## 六、幂等：两层，两个不同的失败模式

报告 §9.3 指出了容易混淆的两层幂等，必须分开处理。

### 第一层：传输层幂等（已实现）

`idempotencyKey → draftId`。同 key 不同内容会被拒绝。这层防的是**同一个 key 被重放**。

⚠️ 但 `attempted` 状态写在原生 POST **之前**：

```
t0  写 attempted（本地事务提交）
t1  准备发原生 POST
t2  ← 进程崩溃
```

此时 `attempted` 存在，但 POST 从未发生。**`attempted` 不证明请求发生过。**
所以崩溃恢复必须**读回草稿状态和传输证据去核对**，不能按 `attempted` 直接重试。

### 第二层：业务层幂等（我上一版夸大了缺口，第四轮更正）

**先说自动回复 —— 这块没有缺口。** `windows_auto_reply.py:148-151` 的事件身份是**派生**的：

```python
def _event_id(account, group, message):
    server = message['serverId']
    identity = server if int(server) > 0 else message['id']
    return hashlib.sha256((account+'|'+group+'|'+identity).encode()).hexdigest()
```

配合 `:303` 的 `'idempotencyKey': 'reply_'+event`，得到：**同一条消息 ⇒ 同一 event ⇒ 同一 key ⇒ 同一 draft ⇒ 幂等**；
不同消息 ⇒ 不同 key ⇒ 各发一条（这本就正确，两条消息该有两份回复）。
所以自动回复**不存在**我上一版说的"业务层看不出冲突"问题。

**批量定时确实有三层防重**（`schedule_batches.py`）：

| 层 | 实现 | 防住什么 |
| --- | --- | --- |
| 批次请求 | `:31` `UNIQUE(account, request_id)`；`:163` `_receipt()` 复用 | 同一个 `requestId` 重复提交 |
| 计划规格 | `:91` `job['state'] in ('active','paused') and job['spec']==spec` | 同目标＋同全文＋同日历的启用/暂停计划 |
| 任务 ID | `:170` `_digest({'batchId':..., 'groupId':...})` | 批内任务 ID 确定性，避免碰撞 |

⚠️ **残留缺口比我上一版写的窄**：规格比对包含**完整日历**（`clock` / `at`），所以
**同一业务意图换个执行时刻表达，就绕过了去重** —— 同一个群同一天可以发两遍不同文本，
这正是报告 §2.5 说的"正文不同的两个批次仍可为同群同日分别发送"。

【推论】这条缺口的本质：**现有三层都是"规格去重"，没有一层是"业务意图去重"**。
要真正堵上需要一个稳定 `business_intent_key`（如"今天索价"），与 `clock`/`at` 解耦。
这与我在 §6 的原结论方向一致，但**缺口的实际范围只有"换时刻表达"这一种**，不是我说的"两条路径 intent 不同"。

## 七、模型该放在哪：Jev 的正确定位

报告把 Jev 放在"有界语义判断"层。这个位置是对的，但理由需要说清楚——**不是因为它便宜，而是因为它没有权限**。

### 7.1 三层权限分离

```
Jev/小模型  →  输出「建议动作 + 概率」      ← 无权限
代码仲裁    →  校验权限/版本/水位/暂停      ← 真正的门
原生发送器  →  唯一发送出口                 ← 唯一副作用点
```

【报告】原话："最终门禁属于代码和发送服务，模型无权更改目标或自行重试。"

这带来一个反直觉但正确的推论：**即使把 Jev 换成 GPT-5 级模型，也不会让系统更危险**——
因为危险从来不在模型那一层，而在"有没有一层不看模型输出就能拒绝的代码"。

### 7.2 为什么 confidence 不能直接当发送门槛

【核验】三个独立理由，任何一个都足以否定"高置信度就自动发"：

**(a) confidence 测的是分布集中度，不是正确率。**
官方定义：confidence 是"a statistic computed from the probability distribution"。
第三方从交互 demo 反推的公式是 `c = (K·p_max − 1)/(K − 1)`，K 是候选数。
**这意味着 confidence 和 p_max 是两个刻度**：K=2 时 confidence 0.9 对应 p_max≈0.95，K=10 时对应 p_max≈0.91。
**同一个阈值在不同候选数下含义完全不同**——所以报告说"不同原语或候选数变化后需要重新校准"是对的。

**(b) 校准是分组性质，不保证单条。**
官方限定语："These rates describe groups of predictions, **not a guarantee about any single answer**."

**(c) 校准不穿过组合。**（本次核验新增，报告未展开）
单个判断各自校准，经过阈值、加权、分支之后，整体流程**并不校准**。相关错误在组合中存活。
本项目链路是"轻判定 → 就绪检查 → 仲裁"三层，正是最容易被这条击中的结构。

### 7.3 所以报告的兜底策略是对的

对价格、库存、订单、交期这类**越界动作**：即使 Jev confidence 0.99 也不放行。
这不是浪费模型能力，是承认**"语义判断对"和"有权限做"是两个正交的问题**。

## 八、成本：Jev 到底省不省钱

报告 §7 的预算表是"假设值，不是实测"。既然如此，我们可以把它的数字代进去算一遍，看杠杆在哪。

### 8.1 重新分账

B 方案（轻判定 + 单业务 Agent）每天的 token 分布：

| 层 | 输入 | 输出 |
| --- | ---: | ---: |
| 轻判定 | 3,600,000 | 240,000 |
| 业务生成 | 1,080,000 | 108,000 |
| 摘要更新 | 480,000 | 48,000 |
| 合计 | 5,160,000 | 396,000 |

【推论】注意这个反直觉的事实：**轻判定的输入量是业务生成的 3.3 倍**。
因为判定层要过 12,000 条，生成层只过 600 条。判定层才是按"消息条数"计费的大头。

### 8.2 假设单价后，杠杆在哪

设输入 $x/M、输出 $4x/M（典型比例）。用 $1/M 输入算：

| 层 | 输入成本 | 输出成本 | 小计 |
| --- | ---: | ---: | ---: |
| 轻判定（LLM） | $3.60 | $0.96 | **$4.56** |
| 业务生成 | $1.08 | $0.43 | $1.51 |
| 摘要更新 | $0.48 | $0.19 | $0.67 |
| **B 合计** | | | **$6.74/日** |

把轻判定换成 Jev（$0.042/M 输入，输出免费）：

```
判定层：3.6 × 0.042 = $0.1512/日
节省： 4.56 − 0.1512 = $4.41/日
占 B 总成本：约 65%
```

【推论】**所以报告的杠杆判断是对的，而且比它自己说的更强**：
省钱的大头不是"少让模型说话"，而是"让过 12,000 条消息的那一层换成极便宜的决策模型"。
分层架构省的钱，几乎全部来自这一跳。

### 8.3 但这个 65% 有一个大前提

【推论】Jev 的成本优势会被**弃权率**吃掉。

如果 Jev 有比例 ρ 的判断置信度不达标、需要升级到 LLM：

```
实际节省 ≈ 65% × (1 − ρ)
```

参考外部独立测评的量级：某生产队列上约 **30%** 的判断置信度不达标需升级（同一来源记录名义优势被摊薄）。
代入 ρ=0.3 → 实际节省约 **45%**，而不是 65%。

**结论**：Jev 的经济价值**高度依赖一个本项目还没测过的量**——中文业务集上的弃权率。
这正好对应报告 §8 的待补证项"Jev／小模型效果与报价"。【推论】**建议把弃权率列为 M4 的首要指标**，
因为它是决定"要不要上 Jev"的唯一关键数，其他指标（准确率、延迟）都排在它后面。

⚠️ 以上全是**假设单价下的推算**，不是实测。真实单价、真实弃权率、真实中文准确率都未验证。
唯一可引用的是报告里那句："这里验证的是预算公式，不是模型效果或真实成本。"

## 九、评测：为什么分母比指标重要

报告 §8 是两份文档里方法论最扎实的一节。它的价值不在数字，在**几条反直觉的纪律**。

### 9.1 分母必须先冻结，且各方案一致

【报告】的核心要求："各组不能自选分母，只报总体 accuracy 也会被大量闲聊掩盖。"

为什么这条能防作弊：
```
方案甲：分母 = 过了确定性预筛的 12,000 条  → 精确率 0.98
方案乙：分母 = 全部 60,000 条              → 精确率 0.98（但分母里 48,000 条本来就不该回复）
```
两者数字一样，业务意义完全不同——甲是在**受控样本**上测，乙是在**生产分布**上测。
报告要求分母是"共同确定性预处理后**冻结**的事项加决策时点"，且**包含被各组 gate 拒绝的机会**。
后者是关键：如果分母只含"通过的"，那"全拒掉"就是个满分方案。

### 9.2 零错误不等于零风险（统计功效）

【报告】§8 这段值得单独拎出来，它在工程文档里很少见：

```
200 个负例、0 次误介入  →  真实误介入率的 95% 单侧上界 ≈ 1.49%
要把上界压到 0.1% 以下  →  需要约 2,995 个独立负例且零错误
```

【核验】用 Clopper–Pearson 精确区间重算，两数都对（上界 1.487%，n=2,995）。

【推论】这条的实际含义是：**任何"我们测了 200 条没有误回复所以很安全"的说法都是无效的**——
按那个样本量，你其实仍然可以有 1.5% 的误介入率在跑。
更麻烦的是报告指出的第二层：真实群消息**有相关性**（同一客户、同一话题），
所以 200 条并不是 200 个独立样本，还要按群/时间分块。**有效样本量比名义值更小。**

### 9.3 可证伪实验的设计

报告 §8 的"同一回放集、每次只看到当前时点之前的事件与知识版本"是正确的实验设计要点。补三条工程上常用的：

- **开发/评测隔离**：调阈值用的数据和最终评测必须按**群 + 时间 + 完整事项**三重隔离。
  把同一事项的前半段和后半段拆进两组，等于用未来信息调参。
- **顺序置换测试**：把候选任务的呈现顺序打乱，看分类结果是否稳定。
  【核验】官方文档明确 Jev 的 Choice **可能偏向列表首项**——如果不测顺序置换，
  你会把"检索排序偏好"误读成"模型判断正确"。
- **判据要能被证伪**：报告 §8 要求轻判定对同一候选集做顺序置换并记录答案稳定性，
  这条比"多测几个 case"强得多——**测的是方法论的脆弱性，不是结果的好看程度**。

### 🆕 S2 细节：幂等键是**派生**的，不是随机的

```python
# windows_auto_reply.py:148-151
def _event_id(account, group, message):
    server = message['serverId']
    identity = server if int(server) > 0 else message['id']
    return hashlib.sha256((account+'|'+group+'|'+identity).encode()).hexdigest()

# windows_auto_reply.py:303
'idempotencyKey': 'reply_' + event
```

同消息 ⇒ 同 event ⇒ 同 key ⇒ 同 draft_id ⇒ 幂等。不同消息各发各的（正确）。
所以**自动回复不存在业务幂等缺口** —— 我上一版说的"两条路径 intent 不同"是错的。

批量定时则有三层（`schedule_batches.py`）：`:31` `UNIQUE(account,request_id)`、
`:91` 规格比对、`:170` 确定性 job id。**报告 §2.5"三种约束不同层"的说法被代码证实。**
残留缺口只剩一种：规格比对含完整日历（`clock`/`at`），换时刻即可绕过。

### 🆕 S3 细节：三套发送状态机互相独立

`backend.py:379-382` 中 `automatic.tick()`、`scheduler.tick()`、`windows_auto_reply.py:270`
的 `approved.tick()` 是三套独立状态机；`/api/jobs/pause-all` 与规则 `enabled` 互不影响。
**所以 M2 的影子分支如果只关自己的开关，旧直发不会停** —— 报告 §9.1 的警告在结构上成立。

### ⚠️ `read_only` 这个名字是反的

代码实证（全部在 database 模式下生效）：

```
server.py:398   if engine.read_only and path=='/api/reply'      → 才能配自动回复
server.py:413   if engine.read_only and scheduler ...           → 才能建定时任务
server.py:177   if not engine.read_only ... raise               → 人工待办**要求** read_only
server.py:78    if not engine.read_only ... raise               → 批准问答**要求** read_only

```

**`read_only=True` 不是"什么都做不了"，它是"数据源只读"模式 —— 而所有 Windows 原生能力只在这个模式下存在。**
`read_only=False` 走的是 legacy Live/Demo，反而**没有**自动回复、定时、待办、批准问答。

这解释了报告"不能把 `read_only=False` 当作启用 Agent 的开关"为什么是对的，但名字极具误导性：
**按字面理解会得出完全相反的结论。** 这比报告的措辞更值得记下来。

【推论】建议后续重命名为 `read_only_source` 或 `database_mode`。

## 十一、落地顺序与其真实门槛（本节经五轮源码核对后重排）

报告 §9.1 的 M0–M5 依赖排序**依然成立** —— 它在补的是当前代码**确实不存在**的能力（任务层、逻辑收件箱、原生 @、模型）。
但我第一版写这张表时，隐含前提是"路径上有很多潜在 bug 要先绕开"。**五轮核对后这个前提不成立。**

### 先说三条不该埋在 M0–M5 里的事

**① 唯一活跃的 bug 可以立刻修，与 M0–M5 无关。**

`windows_auto_reply.py:213` 的 `activated < stamp`（严格小于）会漏掉启用同秒的消息。
这是**当前生产路径上的活跃缺陷**，不是任务层的前置条件。
报告 §2 建议"以观察序号／事件水位定义启用边界"是正解，但短期内改比较符或改用事件序号即可止血。
把它放进"M0 冻结基线"里会白白拖一个季度。

**② 原生 @ 是真实业务缺口，而且它卡的是首期业务本身。**

`windows_hook_sender.py:355-356` 明确拒绝 `mentionIds`。而报告 §9.1 说
"Windows 原生 @ 是现有索价业务的缺口" —— 也就是说**每日索价这个核心场景现在做不了真 @**。
⚠️ 这一点应从"并行补证项"提到与 M1 同级，因为它决定首期业务能否成立，
而不只是技术完整性。

**③ 我第一版 §11 末尾那句"业务层看不出冲突"是错的。**

那是我在 §6 已纠正的夸大：**当前自动回复用 `'reply_'+event_id` 派生键，本来就没有业务幂等缺口**。
但这个结论**不能移植到 M5**：迁移期若新旧两条路径同时对同一事件发送，
新路径若用自己的 intent 派生键，就**确实**会产生两个不同键。
→ 正确的约束是：**新路径必须复用同一套 event 派生键**，否则幂等网会在迁移瞬间破一个口子。

### 三个仍被低估的门槛

【推论】**M1 的难点不是分页，是"哪个游标"。**
`inbound_messages` 返回的 checkpoint 绑在**不可变副本**上（`revision` 参与比对，`:121` 不符即重置）。
任务消费位置必须绑**逻辑流**。两者若共用一个字段，副本换代时消费位置会静默错位。
报告 §4.2"事件保存与推进游标应在同一事务"讲的就是这个。

【推论】**M2 的验收必须包含"证明旧直发仍在跑"这一负向断言。**
因为影子分支只声明自己不发送，证明不了别的路径停了。
报告 §9.1 说"验收记录既有规则和计划"就是这个意思 —— **它是必要的验收项，不是走过场**。

【推论】**M5 的切换是"改键"而不是"改代码"。**
既然幂等键派生自事件身份，新路径只要沿用同一个派生函数，幂等网天然延续；
一旦换成自己的 intent 键，迁移瞬间就会出现双发窗口。
→ **这条约束应在 M1 设计事件身份时就定下来**，不要留到 M5。
