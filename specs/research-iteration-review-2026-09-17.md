## 2. Cloud：首次纳入具体取码失败证据

分享对话先讨论“云 Mac＋Aid 服务＋自动验证”配置下不能生成二维码，随后用户提供控制台文本：来源为 `https://cloud.wechatpadpro.com`，请求为 `POST https://api.wechatpadpro.com/v1/Login/GetQRMac`，浏览器记录 `net::ERR_FAILED 502 (Bad Gateway)`，并报告缺少 `Access-Control-Allow-Origin`。

**证据等级：分享记录中的用户错误文本。** 本次未取得原始 Network 导出、完整响应头、响应正文、请求 ID 或服务端日志，也没有重新复现；对话界面时间不是完整的请求时间和时区证明。不推断账号已购买套餐、Aid 无效、Token 失效、微信被限制或平台全面停服。

502 表明请求链路中的网关／代理未从上游取得有效响应；缺少 CORS 头意味着浏览器不能让网页脚本读取跨域响应。“上游失败产生不带 CORS 头的 502”是与日志相容的解释，尚非已定位根因。补 CORS 头不等于修复取码服务，关闭浏览器安全检查也不能修复上游。[MDN 502](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/502)、[MDN CORS 缺失头](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS/Errors/CORSMissingAllowOrigin)。

| 路线 | 出错阶段 | 已有结果 | 不能混淆的边界 |
|---|---|---|---|
| 旧非 MAX 861 | 管理密钥注册／设备 key 签发 | 一次 HTTP200、业务 code=1，上游数据库连接超时，无设备 key | 本地详细收据；不是 Cloud GetQRMac 的后台日志 |
| Cloud 云 Mac | 登录二维码取得 | 分享记录 POST 502＋缺 CORS 头 | 具体网关、上游、预检与 Aid 依赖仍缺证 |

两者共同说明存在外部接入依赖，**不能证明共用同一个故障组件，也不能证明买新套餐可修复旧故障**。Cloud 应从“仅商业文档候选”更新为“已有取码失败反馈、尚未证明登录成功的候选”。

下一步证据包应优先使用已失败请求：核对 OPTIONS 与 POST 是否分别出现及其状态、发生时间／时区、实际域名路径、响应头和可见错误正文。控制台文本指向 POST，但尚不能重建完整预检链。若预检失败且 POST 未发出，先查预检链路；若预检通过且 POST 502，查实际取码上游。Aid 状态仅作为关联证据，不先改 Aid、设备类型和代理等多个变量。保留脱敏错误和请求 ID，不公开 token、Cookie、二维码或完整 Aid。本文不执行重放或外联。

research-v2 E0 修正“旧 COM 对象还能返回值就表示窗口有效”的错误假设，改用 HWND 与进程世代核验。E1 在前后身份稳定、3 节点未截断的情况下，两处 HWND 的 server-side 查询为 false，来源为 Win32/MSAA 代理；Text/Text2/Value/ItemContainer 属性结果为 `not_supported`，不是泛化成普通 false。结论限于该次窗口和状态，不能断言整个进程永远没有 provider。[v2 执行记录](../poc/evidence/uia-research-v2-execution-2026-09-17.md)

v3 的自建 Win32／WPF 对照实际观察到 server-side=false／true，WPF 只读 ValuePattern 取得且合成值匹配，关窗失效判据通过。它证明采集路径可识别正例，未产生微信新消息证据，也没有重跑微信 E1/E2。[v3 原生对照](../poc/evidence/uia-v3-review-and-native-control-2026-09-17.md)

看门狗续验覆盖自建进程树挂起、退出 0 无报告、报告成功但进程非零退出三类真实故障样本，另有正常路径及 9 项离线反例。所测超时清理通过，不代表制造过微信 COM 死锁或覆盖任意进程逃逸。[看门狗记录](../poc/evidence/uia-v3-watchdog-followup-2026-09-17.md)

**剩余首关仍为聊天语义控件。** 控件出现后还须真实后端、账号／群绑定、UI 消息身份、虚拟化和连续性、真实 @、发送与双端核验。不得以探针测试通过替代这些关卡。

## 4. Hook：从旧版候选推进到有界动态研究

首次动态实验执行一次附加和调用栈地址采样，55.282 秒后分离；存在无效栈地址、线程覆盖和消息时间关联限制，接收入口未确定。用户截图显示标记可见不能充当 Hook 接收结果。[首次动态记录](../poc/evidence/windows-hook-411365-dynamic-probe-2026-09-17.md)

后续取得旧 4.1.11.52 签名模块，只做静态比较，未安装降级。新版 4.1.13.65 候选具有常量、引用和函数结构依据，但字段及容器步长变化阻止直接沿用旧布局。静态相似性不等于接收入口已验证。[静态迁移](../poc/evidence/windows-hook-411365-reference-port-2026-09-17.md)、[夹具与步长](../poc/evidence/windows-hook-411365-attach-readiness-2026-09-17.md)

自建进程夹具验证了硬件断点命中、新线程覆盖、删除和分离；真实 R2 一次附加约 44 秒零命中，R3 一次三点实验约 43 秒全部零命中，均有清理、分离及退出后进程响应记录。硬件断点涉及调试寄存器和线程暂停，不应描述为毫无侵入。记录总耗时也不是客户端全部暂停时长。[R2](../poc/evidence/windows-hook-candidate-hit-r2-2026-09-17.md)、[R3](../poc/evidence/windows-hook-three-point-r3-2026-09-17.md)

**重要纠正：** 后续截图显示 R2 是三个右侧绿色发出气泡；R3 是一个右侧绿色气泡内含三个标记。两轮都未确立其他群成员入站条件，也没有秒级关联。零命中事实保留，但不能据此否定外部成员接收路径；候选组恢复为“静态候选、入站命中未验证”。旧中间位置存在可选分支的静态发现仍成立，与本次缺少有效入站样本是两个独立问题。

下一次若安排验证，先固定另一成员账号、三条独立消息、方向及时间证据，再区分采样覆盖与真实路径语义。不能因零命中盲目换地址、自动追加附加或读取对象。命中之后仍需对象布局、稳定群／本人身份、消息 ID 和真实 @，之后才可能进入接收适配；当前接收／发送 profile 继续禁用。
