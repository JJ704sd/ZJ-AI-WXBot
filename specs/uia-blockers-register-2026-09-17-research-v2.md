# UIA 卡点总表与交接说明

日期：2026-09-17。范围：Windows 个微 UIA、指定测试账号、原个微/企微混合群。本文汇总已保存证据和当前实现；本次只整理文档，没有重新操作微信或运行测试。

## 1. 核心结论

**当前首要卡点：正常聊天窗口没有通过已测试的 Windows 可访问性入口暴露聊天语义控件。** 能找到进程、窗口及渲染面板，也能看到用户提供的聊天截图，但不能据此读取消息。

这是已观察到的直接阻塞，不是已经证明的内部根因。账号策略、客户端内部可访问性开关、启动时状态等仍是待验证假设；不能直接断言“腾讯针对这个账号封了UIA”。

业务目标的依赖顺序：

```text
进程/窗口识别 → 聊天语义树 → 账号/群独立绑定 → 可见消息身份与正文
→ 新消息连续读取 → 原生@本人 → 单次受控发送与送达核验
→ M3自动回复 → 主动定时询问
```

目前到达“能找到窗口”，曾观察到登录页语义树；没有跨过“聊天语义树”这一关。后续步骤主要是未验证或尚未实现，不能全部写成已实测失败。

## 3. 已证实的直接卡点

| 编号 | 卡点 | 实际证据 | 影响 | 解除条件 |
|---|---|---|---|---|
| U01 | 聊天语义树缺失 | 根常为Qt51514QWindowIcon，下面只有空MMUIRenderSubWindowHW；最小化时还可能有标题栏 | 无法定位会话、消息气泡及输入框 | 真实聊天状态下出现可遍历语义控件，而非仅增加普通Win32节点 |
| U02 | wxauto构造未成功 | 异常位置wx.py:340→main.py:211；后续异常原因定位为找不到已登录客户端主窗口 | 未进入ChatInfo；不能运行上游接收流程 | 构造所需结构实际存在，并完成有界ChatInfo验证 |
| U03 | 直接文本接口也未提供 | 最小化状态主窗口/面板Text、Text2、Value、ItemContainer均false，Legacy为true | 不能绕过子树直接读取文本 | 非伪造的文本或条目接口实际可用；仍需验证对象归属 |
| U04 | 替代遍历入口没有找到聊天对象 | FindAll、RawViewWalker、命中测试返回外壳/渲染面板；MSAA选中/焦点入口为空 | 换一个遍历函数没有修复provider缺失 | 出现新的机制依据或不同可复现状态，而非反复查询 |
| U05 | 登录页可见与聊天页不可见并存 | 曾观察mmui::LoginWindow及21个节点；随后聊天窗口恢复外壳 | 不能把“登录页UIA可见”当作全客户端成功 | 同一实验明确记录登录前后结构及窗口世代；不能推断当时变化由何触发 |
| U06 | 运行时窗口和进程状态变化 | 曾1进程2窗口，随后1窗口；也出现过Weixin未运行 | 旧句柄、进程数量和原先归属不能沿用 | 每轮重新核验唯一目标；歧义时不自动挑第一个 |

注：Qt51514QWindowIcon作为Win32窗口类本身并非错误。问题是UIA视图没有提供所需mmui语义结构；把期望类名改成Qt只能绕过检查，不能生成消息控件。

## 4. 已尝试方法及结果

| 方法 | 执行状态/结果 | 能说明什么，不能说明什么 |
|---|---|---|
| wxauto4受控构造 | 已执行，构造失败，ChatInfo未成功调用 | 不能记为ChatInfo返回空群或群不存在 |
| 临时还原最小化窗口 | 历史对照已执行，还原后仍为空面板，结束恢复最小化 | 不能只归因于最小化；不是所有界面状态都测试过 |
| RawViewWalker | 已核对依赖源码实际在用；结构扫描无聊天节点 | 不是误用了Control View过滤造成漏读 |
| FindAll + TrueCondition | 非最小化窗口仅1个后代渲染面板 | 排除了该次仅walker遍历遗漏的解释 |
| ControlFromPoint | 起初遮挡而跳过；用户截图后归属检查通过并执行，仍命中Qt根+1子节点 | 最新状态已不是“尚待无遮挡验证”；只覆盖所测点，不是全屏扫描 |
| MSAA OBJID_CLIENT | 主窗口可获取对象、1子节点，面板0子节点 | API存在不等于聊天对象存在 |
| Legacy GetCurrentSelection | 调用完成、0对象 | 当前选择入口无旁路，不等于所有潜在选中状态都不可用 |
| MSAA accFocus | 主窗口/面板均none | 未主动改焦点，不能外推任何前台状态均无对象 |
| Pattern可用性 | Text/Text2/Value/ItemContainer=false；Legacy=true | 限所测窗口与最小化状态；Legacy可用不等于可读消息 |
| WM_GETOBJECT/UIA_ROOT | 主窗口、面板；最小化/还原两种状态均完成请求，返回零，树未改善 | 标准请求未恢复本次控件；不证明微信内部开关的具体实现 |
| CUIAutomation8 | 独立comtypes，不导入wxauto4；最小化状态2后代、仍为外壳 | 降低“仅wxauto包装层导致失败”的可能；不是与旧客户端同时同状态的严密对照 |
| 权限、位数、会话、运行库 | 同会话、同高完整性级别、均64位；Oleacc/UIAutomationCore已加载 | 不支持反复提权或重装组件；运行库加载不证明provider启用 |
| 讲述人/读屏标志等早期实验 | 构建文记录为既往未解决路径 | 本次未重新取得原始输出，不把它提升为完整可复现证据 |

这些入口大多共享微信自身的无障碍provider，不是多种独立协议。多次失败不能直接计算“成功概率为零”。

## 5. 尚未证明的内部原因

| 假设 | 支持线索 | 目前缺少的证据 |
|---|---|---|
| 客户端内部可访问性状态未启用 | 标准入口仅外壳；第三方同版源码声称热修改后出现控件 | 本机状态与控件变化的受控因果对照；没有执行内存写入 |
| 账号相关策略/历史无障碍状态 | 第三方维护说明提出账号差异 | 本测试号的官方说明或可授权的隔离对照；不应擅自换到排除账号 |
| 启动前后状态影响 | 登录页与聊天页暴露不同，通用Qt存在可访问性逻辑 | 在不改变授权边界下的明确实验设计；通用Qt源码不等于Weixin定制构建 |
| UIA身份/版本选择器变化 | 第三方同版源码提及AutomationId点分路径 | 本机真实控件的AutomationId样本；在控件缺失时改匹配无助 |
| wxauto二进制特定缺陷 | 构造异常、版本自述不匹配 | 与41.1.7一致的源码或可定位二进制行为；独立接口同样外壳，故不能仅归咎于wxauto |

## 6. 控件出现后仍需解决的业务卡点

以下为后续准入缺口，**不是已执行失败的项目**。

| 编号 | 待解决项 | 最小验收要求 |
|---|---|---|
| B01 | 真实UiaSessionReader后端未实现 | 同一COM/UIA线程提供observe/read_visible；数据来自实际UI，不从配置复制 |
| B02 | 本人账号独立识别 | 证明当前客户端是指定测试号；昵称或标题不能单独代替账号标识 |
| B03 | 原群独立绑定 | 原群与同名会话区分；旧DB内部键不能自动变成UIA观察证据；成员数量会变化 |
| B04 | 消息与发送者对应 | 文本、系统消息、本人/他人、企微成员可区分；无可靠字段保持unknown |
| B05 | UI消息身份稳定性 | 同人同文连续两条不合并；RuntimeId或控件ID复用、重绘、滚动须实测 |
| B06 | 首次基线与新消息边界 | 首次不派发历史；之后有明确新增证据，不能只依赖未读徽标 |
| B07 | 滚动/虚拟化与遗漏 | 快照无交集停止；不能宣称可见区域等于全历史或全量新消息；需测高频/跨屏到达 |
| B08 | 真实@本人语义 | 区分文本“@昵称”、引用中的@、@所有人和真正@本人；显示名称不等于原生mention |
| B09 | 锁屏、切群、重登、窗口重建 | 读取前后绑定一致；世代变化重建基线；禁止复用旧审批/身份 |
| B10 | 长时间运行 | seen集合增长、控件回收、超时/线程退出、异常停止均需定义与验证；当前仅有界基础 |
| B11 | 发送与送达 | 独立授权后固定文本一次；本地调用返回不等于个微/企微两端收到；不自动重试未知结果 |
| B12 | M3与主动任务接入 | 接收/身份/@/发送先通过；已有M3单独通畅不能证明UIA链路可用 |

当前Reader为后端无关的离线基础：线程亲和、前后绑定检查、首次基线、缺ID/重复ID拒绝、快照连续性检查、异常暂停，输出mention_status固定unknown。它不是已完成的微信真实读取器，也不含发送操作。

## 7. 工程及证据质量卡点

- **匹配源码不完整：** .pyd不可由.pyi替代审计；公开分支需明确版本与来源。
- **构造器副作用：** 默认resize、日志、可能窗口激活；只检查安装不能直接调用构造。当前禁用相关默认项、子进程限时，但不等于二进制内部完全审计。
- **深度/数量上限：** 主结构扫描128节点/6层；登录页曾因深度限制不完整。达到预算必须报告未知，不当成“无控件”。
- **结果口径：** 脚本退出0表示报告生成；报告status=observed仅表示查到结构，不表示chat/read/binding通过。
- **运行上下文：** 报告目前未统一具备run_id、时间、进程启动世代、目标模块哈希及前后台状态，跨轮比较有局限；未来新实验应补这些脱敏元数据。
- **隐私与诊断冲突：** 异常可能含账号、标题、正文。现有脱敏正则不是普适匿名化；泛化异常又会丢根因。只保存必要结构及错误类别，不大范围dump。
- **脚本覆盖范围：** 新增探针部分仅语法检查+实机调用，缺少全面超时/状态切换反例；不能把既有27项算到全部新脚本。
- **测试环境干扰：** 曾遇pytest缓存权限、临时目录清理失败；另有全量回归临时根含.local导致路径用例失败。后续单项复验与原运行分开报告。
- **文档状态分散：** 早期“未安装”“未执行位置命中”“构造原因未知”在各阶段当时成立，最新汇总应结合续验；不删除历史，也不只读最早摘要。
- **工作区交叉变更：** 用户已有暂存/未提交工作与其他路线并存；不reset、覆盖、提交或打包私密目录。

## 8. 当前不能自动采用的“修复”

| 做法 | 原因 |
|---|---|
| 只改窗口类名/放宽失败条件 | 会绕过准入，无法产生真实消息，可能误绑窗口 |
| 直接运行同版第三方聚合入口 | 可能自动登录、写进程、数据库读取、OCR回退及发送；超出现行范围 |
| 热写可访问性状态 | 未执行；上游实现有候选试写、失败恢复未核验等问题，恢复字节不保证内部状态或风控影响消失 |
| 使用旧版本Hook或降级 | 版本与偏移不匹配或用户已排除；不能作为UIA只读修复 |
| 用截图、旧DB键、配置填充观察 | 不能证明当前UIA账号、群、消息或真实@ |
| 安装官方单聊插件宣称群接入完成 | 业务能力不同；见接入机制矩阵 |

## 9. 可执行的继续条件

1. **有明确新证据再开实验：** 新版官方可访问性说明、精确匹配的源码、新出现的聊天控件，或操作人明确改变测试范围。
2. **先记录最小结构证据：** 唯一目标、版本、窗口世代/状态、完整性预算、根和必要控件；禁止从预期配置推导观察。
3. **有控件后先只读绑定：** 账号、原群、消息身份、首次基线；随后做同文重复、切群、锁屏、重建反例。
4. **有新消息后验真实@：** 原生字段不可得就保持unknown，不能用正文包含昵称代替。
5. **最后另行进入发送验收：** 不把广义“继续排查”当作真实发送、内存写入或换账号授权。

若没有新证据，不再重复构造、讲述人、WM_GETOBJECT、窗口还原、遍历API轮换。此停点是证据与机制约束，不是缺少一次泛化授权。

## 11. 续研记录：本轮实际完成的工作与结论

续研日期：2026-09-17。版本：研究续补 v2。第1—10节原样保留；第11—17节为新增分析，不回写或覆盖历史观测。

### 11.1 本轮执行边界

本轮已完成：阅读上传的卡点总表；只读核对仓库中标准对象请求、运行环境排除、内存热激活源码审查等记录；查阅 Microsoft UIA 官方文档；静态核对 Qt 官方版本源码和同版本第三方驱动源码；形成下一轮实验设计与未执行证据模板。

本轮未完成、也未声称完成：连接用户 Windows 桌面、访问本机 D: 工作区、重新扫描微信、恢复聊天树、读取真实消息、变更客户端状态、写进程内存、扫码/重新登录、切换账号、发送、提交或推送 Git。本轮新增实验均为 `not_run`，不能计入原27项测试。

本文依据上传文件续写。远端同名 `specs/uia-blockers-register-2026-09-17.md` 的读取返回404；这不否定用户本地文件的存在，也不能据此用远端较早记录替换上传文件。

### 11.2 更新后的技术判断

**目前仍没有证据表明：在指定测试账号、微信4.1.13.65、原混合群以及不写进程内存的边界内，聊天语义控件已经可读。**

但“当前不可读”不等于“这个版本在所有账号和状态下都不可能支持UIA”。合理的下一步不是继续换遍历器，而是补齐两个诊断证据：

- 当前探针能否可靠识别自己创建的合成控件，是否正确区分不支持、错误、超时与真实否定结果；
- 微信窗口返回的UIA对象究竟有哪些provider/代理来源线索，是否存在局部语义控件的迹象。

本轮新增的价值是**改进诊断的可证伪性并收窄后续实验**，不是发现了已经验证有效的新激活办法。Provider来源探测仍使用Windows无障碍机制，不是独立协议，也不保证恢复控件。

### 11.3 哪些是新补充，哪些只是复核

| 项目 | 本轮性质 | 对结论的影响 |
|---|---|---|
| Qt处理WM_GETOBJECT时尝试激活无障碍层 | 对既有实验依据的版本固定与复核 | 原标准请求记录已经采用这一依据，不能重新包装成新修复 |
| `QAccessible::isActive()`与接口查询不是完全等价的概念 | 官方源码层面的进一步区分 | 不能将所有“空树”简化为一个通用active字节未置位 |
| Provider来源、默认值/不支持区分 | 新增诊断设计 | 补充U01/U03/U04证据粒度，不直接解除卡点 |
| 自建合成控件正对照 | 新增测试设计 | 检验探针，不检验微信账号策略 |
| 同一窗口世代的局部焦点对照 | 有条件实验设计 | 只有新语义迹象或明确的新状态依据时执行 |
| 同版本第三方驱动固定提交 | 来源锁定与静态复核 | 可提高复查一致性，不等于安全或兼容性认证 |

## 12. 官方机制与第三方实现复核

### 12.1 Qt的激活、接口工厂和事件发送是不同环节

**官方源码事实。** Qt `v5.15.14-lts-lgpl` 的 `qwindowsuiaaccessibility.cpp` 中，`handleWmGetObject` 会先尝试启用平台可访问性状态，再检查生命周期状态、查找对应窗口、取得其accessible root，并尝试返回provider。[S1]

**官方源码事实。** 同版本 `qaccessible.cpp` 说明，即使 `isActive()` 为false，仍可调用 `queryAccessibleInterface()`；未激活时的平台通知行为与接口查询能力应分开考虑。查询实现还涉及接口工厂、插件、类继承链及缓存，而不是只读取一个布尔开关。[S2]

**项目证据。** `poc/evidence/uia-activation-attempt-2026-09-17.md` 已基于Qt激活逻辑设计并完成标准对象请求对照；因此不再建议重复该实验。[P1]

**本轮推断。** 本机所见外壳可能涉及定制构建的请求路径、可访问根/接口实现、实例状态或其他尚未识别的条件。现有证据尚不能把原因缩成“通用Qt冷启动没有开启”，更不能确认为账号被封。

**限制。** 窗口类名 `Qt51514QWindowIcon` 不是本机Weixin.dll与Qt官方源码逐字相同的证明。上述源码只能界定通用机制，不能证明微信调用了相同函数或执行了相同分支。

### 12.2 Provider来源值得查，但不能成为新的单项放行条件

Microsoft提供 `UiaHasServerSideProvider(HWND)` 来查询某窗口是否具有UIA provider实现；`ProviderDescription`（30107）用于返回对象provider的来源和代理信息，`FrameworkId`（30024）提供框架线索。[S3][S4]

下一轮应把以下事实分开保存：

| 维度 | 可以支持的判断 | 不能支持的判断 |
|---|---|---|
| 某HWND的server-side provider查询结果 | 该API对该窗口的检测结果 | 整个进程所有窗口的UIA能力 |
| `ProviderDescription`、`FrameworkId` | 当前对象的provider/代理与框架线索 | 仅凭字符串认定腾讯内部机制或账号身份 |
| 实际可遍历控件及其关系 | 在本次状态、范围、预算内观察到的结构 | 只凭节点数证明聊天读取成功 |
| 所需业务字段的独立观察 | 对应B01—B12中的具体能力 | 把登录页、搜索框或其他局部可见性等同于完整群接入 |

特别注意：`UiaHasServerSideProvider=false` **不能自动否定MSAA桥接或客户端代理可能暴露的有效语义**。反过来，`true` 也不能证明聊天消息存在。该值仅是诊断的一条证据，不是业务能力总开关。

### 12.3 “false”“不支持”“读取失败”必须分开

官方 `GetCurrentPropertyValueEx(propertyId, true)` 允许查询时忽略框架默认值，避免把provider没有实现的属性直接当成默认值。属性读取还可能返回HRESULT错误。[S5]

建议新报告将单项结果建模为：

```text
state = observed | not_supported | error | timeout | not_run
value = 真实返回值或null
```

只有 `state=observed` 时，`value=false` 才能被解释为成功取得的否定值。异常、COM失败、对象已失效或预算耗尽不能改写成false。

这是一项对后续探针的设计要求，**并非已经发现原脚本将这些状态混淆的确定bug**。原始U03记录继续保留；没有完整原始输出与实现对照前，不撤销历史结果。

### 12.4 固定同版本第三方来源，但不执行其聚合入口

本轮读取的 `fanyuantaier/wechatauto-replica` 驱动来源固定为：

```text
commit: 20a6ed69fdf889b2ecd80cae06ff800536630e87
file:   wechatauto/uia_driver.py
```

该文件明确把自身定位为混合驱动，并包含进程内存热激活路径及失败后OCR降级的设计。此前“同版本存在成功声明”应继续解释为维护者报告，不升级为本机复现，也不能将其整体功能等同于纯UIA读取。[S8][P2]

进一步需要区分：

- **选择器兼容**解决已有对象的匹配，不能创建缺失的对象。
- **进程内存修改后再使用UIA**属于“修改客户端运行状态＋UIA消费”，不属于原生只读UIA的成功。
- **只改一个字节**不意味着与正常API激活完全等价。官方实现涉及调用路径、观察者通知与缓存；没有因果与恢复验证，不能认为恢复字节就恢复全部客户端状态。[S1][S2]

另外，固定提交中的 `is_running()` 即使增加了多判据，仍返回布尔值；其源码明确存在“无法确定但返回False”的分支。若将来借鉴这一函数，必须改为三态结果，且不能用窗口标题命中替代指定进程、账号或窗口绑定。这是对该上游源码的静态审查发现，**不是当前项目已安装wxauto4的已证实缺陷**。[S8]

### 12.5 事件订阅不等于打开了另一条消息通道

Qt源码的事件通知路径仍检查可访问性激活、有效接口以及是否有客户端监听。Microsoft也明确提醒：不能假设provider会发出所有可能的事件。[S1][S7]

因此，事件订阅只有在已经发现可访问对象或有明确时序证据时才有诊断价值。没有语义树时盲目增加全局监听，不应作为优先修复；没有事件不能证明没有新消息，有事件也不能证明得到完整消息。

## 13. 下一轮最小实验：E0 → E1 → 有条件E2

所有预算均为本轮提出的实验上限，不是测得的性能指标。实验仅生成结构诊断，不接入M3，不发送，也不以配置内容补齐观察结果。

### E0：自建合成控件正对照

**问题：** 同一套探针能否确实识别已知存在的语义控件，并正确处理失效对象与不支持属性？

**方法：** 用独立测试进程创建只含合成内容的普通Windows控件窗口，至少包含一个输入框、列表、按钮。使用与后续E1相同的UIA客户端和结果序列化路径，按该测试进程的PID/HWND探测。探针不得从fixture配置复制期望控件作为“观察值”。

**范围：** 不访问微信、不使用其他个人应用作对照、不读取密码框或真实文档。对照程序是新的测试产物，实施前需审查；本文没有创建或运行该程序。

**验收：** 实际找到目标控件及合理的父子关系；可区分支持、不支持、COM错误；测试窗口关闭后正确报告目标失效，而不是“空树成功”。UIA查询放在独立、不拥有窗口的MTA工作线程；对照窗口自身的GUI线程可按其框架要求使用STA，两者不能混为同一线程。[S6]

**判读：** 正对照失败则先修探针，不继续解释微信现象。普通Win32/WinForms对照通过，只排除探针明显失灵，不能证明Qt桥接无问题。已有可审查Qt fixture时可再加Qt对照，但不得为此更换微信DLL或安装来路不明的插件。

**状态：** `not_run`。

### E1：微信provider来源与最小结构指纹

**问题：** 当前观察到的外壳有哪些provider来源线索？是否存在值得后续跟进的局部语义对象？

**前置：** E0通过；客户端仍为指定测试号；无需重新登录、切群或重启；操作人确认当前仍在原测试范围。操作者确认只用于诊断授权，不能当成B02/B03的机器独立绑定证明。

**目标绑定：** 显式确认PID、进程启动时间、会话、主窗口句柄及其归属、客户端版本、允许记录的模块哈希。多个候选不自动挑第一个。读取前后复核；PID或窗口世代变化时本轮失效。模块哈希只是分发物/实例对照，不是账号或群身份。

**最小采集：** 对已确认主窗口及其已确认渲染子窗口，记录 `UiaHasServerSideProvider` 的API结果与provider/框架线索。结构扫描沿用原有128节点、6层预算，而非另起无上限桌面遍历；达到预算则明确 `truncated`。仅依据真实观察列出控件类型、必要类名、父子关系与Pattern可用性。

**隐私：** 默认不读取或保存Name、Value正文、Text正文、群名、昵称、聊天消息或账号标识。ProviderDescription可能含路径等信息，只落盘必要的来源标签；未知格式不原样转存。AutomationId若可能携带业务标识，先不落原文；确需关联时仅在单次诊断内做受控匿名关联，不将哈希冒充账号/群身份。

**调用约束：** 不构造wxauto WeChat对象；不调用Invoke、SetValue、SetFocus、Scroll或SendKeys；不写剪贴板、注册表或客户端内存。不手工重复WM_GETOBJECT激活对照；正常UIA/provider查询可能触发应用自身的无障碍初始化，故“只读诊断”不等于“绝无内部状态变化”。

**预算：** 一个子进程执行一次有界采集，外层看门狗总预算15秒。超时只终止本次探针，绝不终止Weixin。这个15秒是实验预算；不保证每个COM调用能在15秒内自行返回。

**结果判读：**

| 观测组合 | 本轮能作出的结论 | 下一步 |
|---|---|---|
| 该HWND未检测到server-side provider；来源只有外壳/代理线索；范围内仍无聊天结构 | 本次样本支持“当前仅得到外壳” | 维持U01；不把false外推到整个进程或所有MSAA对象 |
| 检测到provider，但结构仍为空面板 | provider被检测到与聊天语义可用不是一回事 | 维持U01；调查根/子树/状态，而非改选择器 |
| 出现输入框或其他局部语义对象 | 局部语义候选出现 | 记录精确状态，再决定E2；不直接宣布聊天读取成功 |
| 出现与聊天页面相符的结构关系 | 值得进入后续只读验收的结构候选 | 另行验证B01—B07，不跳到发送 |
| 只有登录页或无关区域的语义对象 | 非目标页面局部可见 | 保留U05，不解除U01 |
| 查询错误、超时、预算截断、绑定变化 | 结论不完整或样本失效 | 标记inconclusive/invalidated，不记为provider=false |

表中组合是待验证分支，不是本轮实测结果。`server-side provider` 检测结果必须按窗口保存，不能把多个窗口合并成一个真假值。

**状态：** `not_run`。它是新增诊断证据，不是已验证的激活方法，也不保证获得新结构。

### E2：有条件的同世代局部焦点对照

**启动条件：** E1发现局部语义候选，或出现与当前构建直接相关的新证据，足以说明某个尚未测过的焦点状态值得验证。E1仍是相同空壳且无新依据时，不启动E2。

**问题：** 原记录中的accFocus为空发生在没有主动改变焦点的状态；在明确、同一世代的焦点条件下，是否存在仅局部可访问的聊天输入控件？这不是重做最小化/还原或全屏位置扫描。

**方法：** 操作人仅在原群当前页面内手动点击输入区域，不输入、不按回车、不切群。探针不自动点击，只读取 `GetFocusedElement()` 及限定范围的结构差异。[S9]

**归属与隐私：** 先核对前台窗口/PID；焦点对象的ProcessId不是目标进程就停止，不继续读取该对象名称或内容。UIA焦点查询本身可能遇到对象已失效，按错误记录，不做无界重试。[S9]

**判读：** 只出现输入框而没有消息列表时，记录 `input_semantic_candidate=true`、`message_reading=unverified`；不能把潜在发送控件可见等同于接收可行。只有列表和消息结构也出现时，才考虑B01—B07。

**预算与退出：** 单次人工状态切换，最多三次有界快照，总观察窗口30秒；目标/账号/群状态变化立即停止。操作者不能确认测试范围或本轮尚未允许该状态变化时保持 `not_run`。

**状态：** `not_run`。

### 暂缓：启动顺序、事件监听和内存热激活

冷启动/重登涉及客户端生命周期变化；全局事件监听还增加隐私与线程生命周期成本。在已有标准激活对照未成功、又无本机匹配新证据时，不把这些作为默认下一步。

如未来进入限定事件实验，只订阅已确认目标子树与必要事件，不保存Name/Text变化负载；工作线程统一注册、注销，处理注销后迟到回调；回调只作为“需要重新观察”的信号，不充当持久消息队列。[S6][S7]

内存热激活、换账号、降级、Hook、数据库及OCR维持第8节原边界。本次继续研究不改变这些授权条件。

## 14. 新增证据格式与判定规则

随文提供 `uia-probe-evidence-template-2026-09-17.json`。它是**未执行模板**，不是测试输出；所有未知观测保留null。

最小记录应包含：实验ID、run_id、时间、执行状态、来源类别、探针版本、目标实例绑定、前后台状态、每个HWND的provider查询与来源线索、结构预算、错误类别、失效原因、分别列出的能力状态。

建议将以下三个字段彻底分开：

```text
execution_status: not_run | completed | timed_out | invalidated | error
observation_status: not_observed | observed | incomplete
capability_status: unverified | blocked | candidate | verified
```

规则：

1. `completed`只说明探针完成；不代表UIA读取或绑定成功。
2. 未采集的字段为null；不能将模板里的expected_version、目标群配置、fixture期望值复制到observed字段。
3. `UiaHasServerSideProvider`只保存对应API的结果；它不提供“不支持属性”那种语义，API失败/超时与bool结果分开记录。
4. `not_supported`主要用于UIA属性/Pattern等明确不支持的接口；不能用来掩盖COM或序列化异常。
5. 空集合只有在目标有效、查询成功、预算完整、观察范围明确时，才支持“本次范围内未发现”。
6. 登录页可见、输入框候选、消息候选、账号绑定、群绑定、新消息边界、原生@与发送是不同字段，不能用一个 `uia_ok` 取代。
7. 不为本轮研究补造PID、模块哈希、节点数、焦点对象或测试通过数。

## 15. 语义树恢复后仍可能存在的可行性边界

### 15.1 消息控件ID不等于持久消息ID

Microsoft明确指出，AutomationId不保证跨版本稳定，也不要求在整个桌面全局唯一；RuntimeId是运行期对象标识，可能随时间复用。[S4]

因此B05不能只验证“有ID”。应在授权的合成消息条件下测试同人同文连发、控件重绘/回收、滚动、切群返回和窗口重建。不能用正文哈希代替独立消息身份，也不能将两个相同文本天然去重为一条。

### 15.2 可见区域读取不天然具有无遗漏保证

如果两个真实消息过程在所有已采集的UI快照中都产生相同结果，那么只依赖这些快照的算法无法区分二者。这是可观测性上的限制，不是选择更复杂哈希函数就能解决的问题。

故无法证明快照连续性时必须停止派发、报告缺口。UIA链路能承诺的读取范围、采样边界和异常行为，要由实测确定，不能以“能读到几条”替代长时间增量完整性。[P0第6节]

### 15.3 原生@与账号/群身份必须独立证明

正文包含“@昵称”、窗口标题、输入框名称和群成员数量均可能不足以满足原B02/B03/B08要求。若恢复的UIA对象仍无足够区分信息，能力应继续标为unknown/blocked；不能由UIA控件出现反推身份或原生mention已经可得。[P0第6节]

### 15.4 发送能力不得提前由接收诊断推导

E0—E2不调用任何发送相关操作。即使可定位输入框与发送按钮，仍需独立授权、固定文本单次验收以及两端送达核验。未知结果不自动重试；M3草稿生成正常也不能替代这一验收。[P0第6、9节]
