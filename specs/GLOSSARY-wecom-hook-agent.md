## 一、平台与通道

| 术语 | 解释 |
| --- | --- |
| **企微 / WeCom** | 腾讯的企业微信，企业内部使用的 IM 平台。本项目当前业务群是"个微／企微混合群"。 |
| **个微** | 个人微信。混合群里有的人用企业微信账号、有的人用个人微信，这是本项目最大的复杂度来源。 |
| **混合群** | 同一群里同时存在个微成员和企微成员。已确认：两类账号**身份命名空间不同，不能靠昵称互认**，跨来源需显式身份映射（报告 §5）。**待验证**：两类成员的 Hook 能力与可见范围是否真的不同——报告明确把这列为未补证项（"两类成员非 @ 消息"仍在 P1 验收清单里），不要当成已知事实。 |
| **AI Bot** | 企微管理后台里创建的机器人应用，有独立的 bot ID／secret。它是**机器人身份**，不是员工账号。 |
| **自建应用** | 企微的企业内部应用，走 Callback（Webhook 收消息）模式。 |
| **会话内容存档** | 企微官方的合规读侧能力，企业配置并取得相关同意后可读会话记录。**只读，且需授权**，与发送能力是两回事。 |
| **UIA / OCR** | UI Automation（读界面控件树）/ OCR（读屏幕像素）。兜底手段，能看见界面上显示的东西，但拿不到离屏消息、重名难区分、正文可能截断。 |
| **iLink** | 腾讯 iLink Bot API，Hermes 走这个接**个人微信**（与企微 WeCom 是两套）。扫码登录后拿到的身份形如 `xxxx@im.bot`，是 **bot 身份，不是那个个人账号**。用长轮询（long-polling），无需公网端点。⚠️ 官方文档列出三条硬限制（详见下方专条）。 |
| **Bot 模式 / Webhook 模式** | Hermes 两种企微接入口。Bot 模式走 WebSocket 长连接（不需要公网地址），Webhook 模式走 HTTP 回调（需要公网 URL + IP 白名单）。 |
| **group_policy / dm_policy** | 通道访问策略。控制"哪些群允许 bot 说话""谁能私聊 bot"，取值常见 `open`（全开，默认）/ `allowlist`（白名单）/ `disabled` / `pairing`（配对）。⚠️ `open` 是默认值＝默认对所有人开放，投产通常要收紧。 |
| **Ambient room events** | OpenClaw 的"环境事件"机制：把**非 @ 的群消息**也交给 Agent 静默处理。所以"机器人没发言"≠"没产生模型调用"。 |

### 关键区分（报告反复强调）

**投递范围 vs 处理范围**：框架层的 mention 配置只影响"已收到的事件怎么处理"，**不能改变企微服务端决定投不投递**。装个插件不会让平台凭空投递它本来不投递的私聊群消息。

## 二、Hook 与进程插桩

| 术语 | 解释 |
| --- | --- |
| **Hook（挂钩）** | 在程序运行时"截获"某个函数的调用，插入自己的代码，从而观测或改写行为。用来在客户端里拿到消息，**不需要官方 API**。 |
| **进程内探针** | Hook 注入到客户端进程内部的那部分代码。只能做轻活：边界检查、拷贝必要字段、附加序号、进队列。 |
| **进程外 Collector** | Hook 进程之外的宿主服务，负责版本校验、持久化、去重、补收、健康状态。⚠️ 报告强调：**模型、HTTP、OCR、数据库写入一律不能进回调线程**。 |
| **插桩（instrumentation）** | 在运行时给程序挂钩子并采集数据的行为。 |
| **Frida** | 动态插桩工具。用脚本语言写探针，迭代快，适合 PoC 和字段验证。`Interceptor` 是它的挂钩 API。 |
| **Detours** | 微软的 Windows 调用插桩库，偏底层、要编译 C/C++，性能可控。 |
| **MinHook** | 提供 x86／x64 API Hook 的基础库（Windows 平台）。 |
| **DLL 注入 / Loader** | 把自己的 DLL 塞进目标进程的手段。Loader 负责把 DLL 装进去。 |
| **ABI** | 二进制接口约定。程序内部函数的调用方式、参数布局。**版本一升，偏移就可能失效**。 |
| **模块摘要** | 对目标 DLL 文件算出的哈希值，用来确认"我挂钩的确实是这个版本"。 |
| **偏移（offset）** | 目标函数在模块里的字节位置。找偏移是 Hook 的核心工作，也是版本升级后最容易失效的地方。⚠️ 报告明确：运行期 AI 不应自行寻找偏移。 |
| **有界队列** | 有固定容量的缓冲区。满了只能丢或拒。⚠️ 队列满时必须**记录丢失区间并告警**，不能静默丢弃后继续宣称"完整监听"。 |
| **指针跨回调失效** | 在回调里拿到的内存指针，回调返回后就指向无效内存。**必须当场拷贝字节**，不能存指针等以后用。 |
| **能力清单** | 把版本、架构、模块摘要、进程启动时间、账号、字段契约打包成一个绑定体。未知版本 → 暂停原生路径。 |

### 路线对比

- **Frida 探针 + 外部宿主**：迭代快，适合 PoC；长期稳定性需实测。
- **自有 DLL + Detours/MinHook + 外部服务**：可控性好，字段契约稳定后再评估。
- **现成 SDK／商业 Hook**：能省适配时间，但"只有 DLL"≠"可自维护"，还要看维护期和授权。
- **框架事件扩展点**：⚠️ 这是**框架插件**，不是 Windows 进程注入，两者不能混为一谈。

## 三、事件流与数据一致性

这组词是两份报告里密度最高、也是最容易读不懂的部分。

| 术语 | 解释 |
| --- | --- |
| **事件账本** | 落盘的消息事件总账，所有消费者从这读。区别于"最近 200 条消息"这种窗口视图。 |
| **游标（cursor）** | "我已经读到哪儿了"的位置标记。类比数据库的翻页位置。 |
| **检查点（checkpoint）** | 任务消费进度标记。⚠️ 报告强调：窗口游标 ≠ 任务检查点，不能混用。 |
| **水位（watermark）** | `input_watermark`＝这个 run 已经消化到第几条输入。提交前检查"有没有更新的消息还没处理"，防止用过时上下文发消息。 |
| **去重（dedup）** | 同一条消息只处理一次。⚠️ 按"来源＋账号＋群＋稳定消息 ID"去重，**不能按正文去重**——两个客户发同样的话是两条消息。 |
| **幂等（idempotent）** | 同一个操作做多次和做一次效果相同。`idempotency key`＝幂等键；`draft_id = hash(key)[:32]`，同 key 不同内容会被拒（`idempotency_conflict`）。⚠️ **本项目的幂等键是"派生"的**：自动回复用 `'reply_'+event_id`，而 `event_id = sha256(account\|group\|serverId)` —— 键来自消息身份而非随机数，所以同消息天然幂等。批量定时另有三层：`UNIQUE(account,request_id)`、规格比对、确定性 job id | |
| **持久领取（claim）** | "我把这个动作独占了"的原子操作，防止两个 worker 重复提交。 |
| **分片（shard）** | 数据被拆成多块存放。消息落在哪个分片要参与排序，不能只按时间排。 |
| **分页（pagination）** | 分批取数据。⚠️ 本项目踩过坑：默认只取最近 200 条，突发 1205 条就漏读。 |
| **快照（snapshot）／WAL** | 客户端数据库的时点副本。WAL＝预写日志，源变化时的增量。 |
| **副本（copy）／代际（generation）** | 为了安全读源库而复制一份。⚠️ 只保留当前和前一代，所以后台读取跨代切换时需要**代际租约／引用计数**，否则清理线程会删掉还在读的文件。 |
| **scope epoch** | "读取范围"的版本号。切换来源、取消群勾选、本人身份变化 → epoch 递增 → 排队中的 worker、附件引用、旧草稿全部作废。 |
| **unknown 状态** | 发送结果未知（提交了但不知道成没成）。⚠️ **unknown 不自动重发**，必须先核对。 |
| **补收 / 重放（replay）** | 漏掉的消息事后补回来。接收侧可以幂等重放；发送侧不能盲目重试。 |
| **双源核对** | 数据库和 Hook 两路数据对账。没有共同稳定 ID 时，正文／时间匹配**只能算关联候选，不能直接去重**。 |
| **sourceId** | 来源命名空间，由源路径＋selfId 派生。⚠️ 不是独立验证过的登录凭证。 |
| **identityVerified** | 是否验证过客户端真实登录身份。本项目当前仍是 `False`。 |
| **occurred_at / observed_at** | 事件真实发生时间 / 被我们观察到的时间。两者差值就是延迟，报告要求分别记账。 |
| **schema_version** | 事件契约版本号。字段变化时要能识别。 |
| **静默 Agent** | 没有可见发言但实际调用了模型的 Agent（见 Ambient room events）。⚠️ 成本上必须计入。 |

### ⚠️ 报告里最关键的一条区分

**「已创建本机待办」≠「已转交负责人」≠「负责人已收到」≠「业务已完成」**

这四层报告反复要求分开记账。同样：
- 提交 ≠ 服务器受理 ≠ 对端可见 ≠ 已读
- 消息发出 ≠ 对方读完 ≠ 对方理解

## 四、Agent 与编排

| 术语 | 解释 |
| --- | --- |
| **Agent（智能体）** | 模型驱动的业务执行单元。注意报告的划分：Collector、规则引擎、发送账本**不需要**各自变成 Agent。 |
| **会话解缠（Conversation Disentanglement）** | 把一个混杂消息群里的话，拆成"哪几句属于同一个话题／同一个业务事项"。⚠️ 这是群聊场景最难的问题之一。 |
| **Turn-taking（话轮）** | 参与和发言时机的判断：现在该不该说话、该谁说。 |
| **Double Texting（运行中再来输入）** | Agent 还在跑的时候用户又发了新消息怎么办。四种策略：`enqueue`（排队）、`reject`（拒绝）、`interrupt`（打断）、`rollback`（回退图状态）。⚠️ 这是 LangSmith Agent Server／Deployment 的策略，**装开源 LangGraph 不会自动获得**；rollback 也不撤回已发的企微消息。 |
| **Aggregator** | 企业集成模式：定义"多条消息怎么关联成一个聚合结果、完成条件是什么"。对应本项目的"输入聚合"。 |
| **Process Manager** | 企业集成模式：有状态流程管理。对应"编排层"。 |
| **Transactional Outbox** | 在同一个本地事务里同时写业务更新和待发送动作。⚠️ 对外投递**仍可能重复**，不能承诺端到端严格一次。 |
| **task / run** | `task_id`＝持续推进的业务目标；`run_id`＝围绕某任务的一次执行。多个 run 可以先后服务同一 task。 |
| **requirement_revision（需求版本）** | 业务需求版本号。只有影响目标／条件／动作前提的有效变更才递增。 |
| **state_version（技术状态版本）** | 并发控制版本。接管、暂停等状态变更也递增。⚠️ **和需求版本分开保存、分开检查**，不能用行版本冒充需求版本。 |
| **PendingReply（等待回复）** | 机器人问了问题但对方还没答。存：问题对应消息 ID、可接受回复人、缺失信息、提醒时间、截止时间。 |
| **聚合窗口 / 安静窗（debounce）** | 等一会儿看有没有后续碎片消息再一起处理。⚠️ 是**时间启发式**，**不等于"信息够了"**——够不够是业务判断。⚠️ 两版报告参数不同且都标为待校准的实验值：10-01 写"1–3 秒安静窗＋设最大等待"，10-02 写"安静 2 秒后检查、单批最多等 10 秒"。引用时要说清是哪一版。 |
| **就绪检查（readiness）** | 判断是否足够推进下一步。返回 `WAIT` / `CLARIFY`（追问）/ `READY` / `HUMAN_REVIEW`。⚠️ `READY` 只表示"能执行指定的下一步"，能查资料 ≠ 能对外报价。 |
| **槽位（slot）** | 结构化字段：如品类、型号、日期、单位、价格。报告强调：否定词、单位、币种**不能被摘要抹掉**。 |
| **AMBIGUOUS** | 关联不明时的标记。同一人被问两件事后回"可以"，就属于这类——不能执行高风险动作。 |
| **路由 + 按需专家** | 先用轻量判断路由到专门 Agent。⚠️ 报告结论：专家缩短上下文的收益要**超过**路由＋复核＋交接成本才值得。 |
| **广播投票** | 每条消息广播给多个 Agent 再投票。⚠️ 报告列为"不作为日常入口"：多倍上下文＋延迟，而且**一致同错**。 |
| **决策 provider / DecisionProvider** | 可替换的判断接口。换成规则、小模型、Jev 都不改编排层。 |
| **RAG** | 检索增强生成。⚠️ 官方区分两种：固定的"先检索后生成"（调用次数可限定）vs 由 Agent 决定何时检索（不可限定）。 |
| **embedding / 向量库** | 把文本转成向量做语义检索。⚠️ 报告结论：首期**不要求先建向量库**。 |
| **metadata filtering** | 向量库的元数据过滤（如按群隔离）。⚠️ 它**不能替代**群资料授权、版本有效性或发送检查。 |
| **top-k** | 只返回最相关的 k 条。 |

### LangGraph / Temporal / OpenClaw 机制

| 术语 | 解释 |
| --- | --- |
| **checkpoint** | LangGraph 的状态存档点。 |
| **thread_id** | 稳定会话标识，跨恢复保持不变。 |
| **interrupt() / Command(resume=...)** | 暂停等人工输入 / 恢复执行。⚠️ **已核对官方文档**：恢复时从触发 `interrupt()` 的那个**节点开头**重新执行，"从节点开头到 interrupt 的所有代码都将重新执行"，`interrupt` 之前的副作用**会再执行一遍**。官方要求"`interrupt()` 节点必须考虑重执行来设计"。子图同样从调用 `interrupt()` 的父节点开头恢复。恢复值靠**计数器**按顺序匹配（重执行时计数器从 0 开始）。所以发送、写系统等副作用必须挪到 interrupt 之后，或单独隔离并幂等。 |
| **Workflow / Signal / Update / Timer** | Temporal 的持久化流程概念：流程定义 / 发信号 / 传状态 / 持久定时器。⚠️ 协作取消需要执行代码响应，**不等于所有在途动作即时停止**。 |
| **Continue-As-New** | Temporal 的换新 run 续跑机制。⚠️ 消息去重要额外覆盖这种跨 run 情形。 |
| **steer / followup / collect / interrupt** | OpenClaw 处理运行中新输入的动作：中途转向 / 追加后续 / 收集 / 打断。⚠️ 2026-10-04 文档明确：同一条 assistant 消息里**首个串行工具启动前不检查 steering**；并行批次没有检查点。业务取消必须落到每次外部动作的提交授权。 |
| **durable ingress** | 通道级持久入口，机制上独立于框架 session 队列。⚠️ 不能笼统说"队列都不持久"。 |
| **Bot Mode / profile** | Hermes 的隔离模式：不同 profile 有独立的模型、记忆、技能、配置、历史。⚠️ Bot Chat 用永久 canonical 聊天，`/new` 按 `/compact` 处理——不能靠发 `/new` 实现"一任务一会话"。 |
| **记忆（memory）** | 跨会话持久保存的经验。⚠️ 报告强调：长期记忆和 profile 隔离**≠ 业务事项账本**，接管、草稿版本、发送状态仍须结构化保存。 |

### Jev / TypeSafe

Jev 是 TypeSafe AI 的 **System One 模型**：不生成文本，只做**有界结构化判断**。

| 原语 | 问什么 | 返回 |
| --- | --- | --- |
| **Choice** | 从我给的选项里选一个 | 选中项 + 概率分布 + confidence |
| **Score** | 在我定义的有序量表上打几分 | 分数（可小数）+ 分布 + confidence |
| **Noul** | 这个陈述是否为真？ | 0–1 的概率，**无 confidence 字段** |

硬性限制（Context 64k；Choice 最多 255 个选项；不支持图像／音频／视频输入）。

⚠️ 关键限制：
- **confidence ≠ 业务正确率**。官方原文：confidence 是"a statistic computed from the probability distribution"——从分布形状算出的统计量。**确切公式官方未公开**（文档说留待将来的 cookbook）。第三方从官方交互 demo 反推出 `(K·p_max − 1)/(K − 1)` 并与文档示例对上，但那是**逆向工程，不是官方定义**，不要当契约用。
- ⚠️ 因此 confidence 与 p_max **不是同一个刻度**。若按该反推公式，confidence 0.9 在 2 选项时对应 p_max≈0.95，在 10 选项时对应 p_max≈0.91。**同一阈值在不同候选数下含义不同**，换候选数必须重新校准。
- 官方对校准的限定语最关键："These rates describe groups of predictions, **not a guarantee about any single answer**."（校准描述的是**一组预测**的性质，不保证任何单条答案。）
- ⚠️ **校准不会自动穿过组合**：单个判断各自校准，经过阈值、加权、分支之后，整体流程并不校准。本项目有"轻判定→就绪检查→仲裁"多层链路，这条尤其要记住。
- **多个问题在同一请求里是并行独立的**，不能互相看到对方答案。有依赖关系时必须分阶段。
- Choice 的概率总和为 1，所以**必须加一个 other/uncertain 选项**，否则永远有东西"赢"。
- Noul = 0.5 是"是／否各半"，**不是"中等程度"**（那是 Score 的用法）。
- 已知弱项：精确数字运算、日期比较、复杂指代、长无关上下文、对抗性内容。
- 官方文档说**英文效果最佳，CJK 需自测**。

## 五、仲裁、权限与状态

| 术语 | 解释 |
| --- | --- |
| **仲裁（arbitration）** | 所有要发出去的动作的最终把关人。⚠️ **由代码执行**，模型输出只算"待审核意图"。模型无权改目标、无权自行重试。 |
| **影子模式（shadow mode）** | 只判断不发送。用来在不产生外部影响的前提下评测"该不该介入"。⚠️ 影子阶段"不发送"只指新增分支，**不能假定已有的固定回复／定时会自动停止**。 |
| **越权 / 越界** | 请求超出批准范围（如群里要求把其他客户报价发过来）。⚠️ 仲裁必须拒绝。 |
| **人工接管 / 租约（lease）** | 业务员手动接手某事项。⚠️ 接管后采集继续，Agent 不再自动回复。人工完成 ≠ 自动恢复。 |
| **状态机** | 报告建议的事项状态：`OBSERVING → QUALIFYING → BOT_ACTIVE / HUMAN_OWNED → RESOLVED`，外加 `BLOCKED`。 |
| **乐观锁 / CAS** | 靠"版本号一致才写入"来防并发冲突。报告要求**最终校验与领取提交权在同一事务／CAS 中完成**，避免"检查通过后被接管、旧发送仍无条件通过"。 |
| **提交屏障（提交前校验）** | 发送前的最后一道检查：需求版本、状态版本、输入水位、owner、暂停状态、策略、来源健康，全部过才放行。`before_submit` 回调就是这个位置。 |
| **before_submit** | Hook 发送前的授权回调。复用它接入版本检查，不另造原生发送器。 |
| **attempted / submitting** | 本地已尝试提交的状态。⚠️ `attempted` 写在原生 POST **之前**，本身不证明原生调用真的发生了。 |
| **冷却（cooldown）** | 短时间不重复回复的节流。⚠️ **冷却不是延后执行队列**，不能说"稍后补回复"。 |
| **有效窗口** | 消息只有在窗口内才算触发资格。⚠️ 本项目是 120 秒窗口，**不是长期任务收件箱**。 |
| **暂停（pause）** | 按账号／会话暂停。⚠️ 只影响定时任务，**正在处理的一条仍可能提交**。 |

## 六、成本与评测

| 术语 | 解释 |
| --- | --- |
| **输入／输出 token** | 输入＝你发给模型的内容；输出＝模型生成的内容。两者的单价通常差 5 倍以上，所以报告同时算两个数。 |
| **缓存前缀（prompt caching）** | 把固定的策略／schema 放在开头让供应商缓存，命中可打折。⚠️ 是否真优惠要实测，不预设命中率。 |
| **差量摘要** | 只在有新事实时更新摘要，不是每条消息都调模型。 |
| **预算降级** | 达上限后停止开放生成，但继续采集、模板回复和人工待办。⚠️ 不能"以预算耗尽为由漏记关键事件"。 |
| **精确率（Precision）TP/(TP+FP)** | 该动手的都动手了吗——**误报视角**。 |
| **召回率（Recall）TP/(TP+FN)** | 该动手的都抓到了吗——**漏报视角**。 |
| **分母** | ⚠️ 报告最在意的一条。指标必须先说清"分母是什么"，且各方案**不能自选分母**。只报总体 accuracy 会被大量闲聊掩盖。 |
| **N/A** | 不适用／无法判定。⚠️ 零分母要记 N/A，不能记 0 或 1。 |
| **p50 / p95 / p99** | 延迟的 50／95／99 分位。p95 比平均值更能反映"最差那批用户体验"。 |
| **盲测集** | 不参与开发和调参的数据。⚠️ 按群／时间隔离，同一事项的片段不能拆进两组。 |
| **标注** | 人工给测试数据打上"应该怎么处理"。两名标注者独立标歧义样例，分歧裁决后才进盲测。 |
| **合成集 vs 脱敏集** | 伪造数据 vs 真实数据脱敏。⚠️ 必须分开报告，不能互相替代。 |
| **二项上界** | "200 个负例零误介入"的真实误介入率上限约 1.49%（95% 单侧）。⚠️ 要把上界压到 0.1% 以下，需要约 2,995 个独立负例且零错误。真实群消息相关，要按群／时间分块报。 |
| **账本归集** | 把成本按用途分开记：决策、生成、摘要、路由、复核、embedding、OCR／ASR。 |

⚠️ **成本对比的陷阱**（报告 §7 专门讲）：第一版"输入减少 95.70%"是相对于"每条消息都送 2,000 token"的**假设基线**，不是实测收益。第二版各方案共用去重、合并、检索后才比较得 B 相对 A 减少 72.08%。而 C 相对 B 只少 90,000 输入却多 18,600 输出——**不能只看输入数量就说更便宜**。

### ⚠️ 核实结果：Hermes 企微支持

撰写本表时检索到一条流传说法："Hermes Agent 不支持企业微信，是硬伤，建议直接选 OpenClaw"。
**该说法与官方文档不符。** 官方 Hermes 文档站 `Messaging Platforms → Chinese platforms` 下有独立的
[WeCom (Enterprise WeChat)](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/wecom) 与
[WeCom Callback](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/wecom-callback) 两页，
明确记录 AI Bot WebSocket 网关（`wss://openws.work.weixin.qq.com`）、Bot ID/Secret 配置、
`dm_policy`／`group_policy`／per-group allowlist、媒体收发与重连策略。

结论：报告 §10 对 Hermes 通道的引用**成立**；那条"不支持企微"的说法来自非官方资源站，不可采信。
顺带确认报告指出的文档／源码差异仍然存在——在线文档 `dm_policy` 默认写 `open`。

⚠️ 但**通道存在 ≠ 能接本项目的混合群**。报告的核心判断不变：能否加入原目标群、能否收非 @ 消息、
能否覆盖个微成员、回复身份是谁，这些都要单独实机验证，不能从"文档有这一页"推出。

### ⚠️ 更关键的发现：Hermes 的**个人微信**通道对本项目是死路

复核时读到官方 [Weixin (WeChat)](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/weixin)
页（该页有中文版），iLink 的限制写得比报告 §10 的转述严重得多：

1. **iLink bot 身份通常无法像普通联系人一样被邀请进普通微信群** —— 即"进不去群"，不是"进去了收不到"。
2. **iLink 通常不会把普通微信群事件推送到网关**，包括对扫码所用个人账号的 @ 提及。
3. **@ 扫码个人账号 ≠ @ iLink bot**，两者是独立身份，别混为一谈。
4. 实际上大多数情况下**只有发给 iLink bot 的私信（DM）能可靠工作**。
5. 若把 `WEIXIN_GROUP_POLICY` 设成 `disabled` 以外的值，网关启动时会打 WARNING。

**对本项目的直接含义**：业务基线是"个微账号接管的个微／企微混合群"。Hermes 的 WeCom 通道是
bot／应用身份进群，Weixin 通道是 iLink bot 且明确进不了普通个微群。**两条路都不是"用现有那个
个微员工账号继续接管混合群"**。所以报告"优先保持这个账号和群边界"的判断，在 Hermes 上没有捷径——
混合群这件事只能靠自有桥接（WeBridge）或数据库副本路线。这一点报告没有讲透，本表补上。

⚠️ 同时注意：这是**通道侧的身份限制**，不是"Hermes 没实现"。两条路都需要实机验证，只是官方文档
已经明确否定了 iLink 进群这一条。

   未补证。**已改为区分"已确认／待验证"。**
3. **来源不明的数字**。"OpenClaw 20+ 渠道"来自非官方站点，未核实。**已改为"以官方目录为准"**。
4. **把报告当事实源，且只搜了一个文件就下"不存在"的结论**。原样转述了报告"`@chatroom` 后缀门禁"的说法，

5. **犯了报告明确警告过的错**。报告写"不能将旧视图实验外推给这两个接口"，
   我却把旧 `messages` 视图的字符串排序问题安到了 `inbound_messages` 头上。
   实际两处都用 `ORDER BY timestamp, local, m.rowid`。**这是纯粹我的错误。**
6. **把"过期"误判成"错误"**。看到 HEAD 与基线代码不同，就下"报告不可信"的结论。

不是错误，是两份报告没展开但对本项目要命的：
