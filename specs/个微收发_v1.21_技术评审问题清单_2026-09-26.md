# 个微收发 v1.21 技术评审问题清单

修订日期：2026-09-26｜依据：[v1.21 主文](个微收发_v1.21_技术评审修订版_2026-09-26.md)｜配套：[演讲稿](个微收发_v1.21_技术评审演讲稿_2026-09-26.md)

会前用前五节检查准备情况；现场答疑可直接翻第六节，测试安排和会议记录见后文。每个未解决的问题，都记下需要补什么、谁负责、何时复核。表中的“阻断”表示该问题未解决，相应阶段就不能判为通过；“条件”表示只有纳入首期范围或选用相应路径时才需要验收。

## 6. 评委追问与建议回答

下面的回答供现场参考，可按提问深浅展开。资料未对应、没有执行和已经失败分别说明，不把缺证据说成从未做过。

### Q01 已经做过小规模试验，为什么付费产品还是待验证？

前版记录的是项目在小范围内做过的试验，具体用了哪家产品、哪一档、哪个版本，还没有逐条对应起来。因此，可以说已有局部成绩，但不能说某家付费产品已经验收通过。[主文第二、四章](个微收发_v1.21_技术评审修订版_2026-09-26.md)分别列供应商资料和项目证据。

下一步要补每项成绩对应的源报告、运行编号、版本、目标群和收件记录，见 P0-6。

### Q02 现在到底真发成功过没有？

发成功过。[9 月 20 日的记录](../poc/evidence/controlled-send-2026-09-20.md)里，本机出现了消息气泡，操作人也确认收到。但没有记明接收端是个微还是企微，这次也没有验证原生 @。准确的说法是“普通文本在人工控制下发送成功”，还不能说完整自动回复已经跑通。

另一路 Qt/UIA 的结果见[技术报告第二、三节](agent-personal-wechat-mixed-group-feasibility-report-2026-09-16.md)。不同试验的接收记录要分开，不能拼成同一条消息在两类客户端都收到了。

### Q03 文档说有企微提醒，为什么还要再测？

这条成绩目前还是前版摘要，需要找到对应记录，确认当时看到的是普通消息通知，还是原生 @ 提醒。即使旧测试确实通过，换了付费版本或目标群，也要再测一次。

核对时，把同一条任务的成员 ID、@ 参数和企微接收端记录放在一起看。接口里的指定成员参数属于 F5a 的资料依据，企微端实际原生提醒属于 F5b 的实测结果，两者分开记。

### Q04 为什么不能用昵称或 OCR 判断真实 @？

昵称可能重名，也会改；正文里出现“@张三”，也可能只是几个普通字符。OCR 能读出屏幕上的文字，但光靠这些文字，还不能确定微信实际提醒了谁。我们优先用接口中的成员和被 @ 对象字段。其他办法也可以试，但要在目标版本上把身份和误判情况测清楚。

重点测只 @ 本人、本人和他人同时被 @、只 @ 他人、@所有人、文字伪 @ 和自回显。仓库当前 API 路线的被动 @ 回复只接受单独 @ 本人，不能默认覆盖多人情况；业务是否接受这个限制，需要明确。

### Q05 没有登录 API 或服务端回执，就必须淘汰吗？

不一定。可以人工登录，再核对当前账号；桌面方案没有服务端回执，也可以分别记录本地提交和接收方确认。我们要求的是准确发到原群、完成真实 @，并且能可靠停发。这些实际结果仍要验。

同样，是否需要程序化退出看所选路径。退出接口 F8a 可以是条件项，可靠停发 F8b 始终是必需项，不能混成一个勾。

### Q06 加一层 Adapter，能把缺的功能都补上吗？

不能。Adapter 能整理接口数据，也能接上调度、审批和去重。但底层如果没有可靠的身份、消息标识或 @ 语义，补一个字段并不能解决问题。

所以要把三件事分开检查：F3a 能否读到，F3b 能否认清来源，F3c 能否正确处理重投和重复。群成员列表 F2a 也不能代替准确绑定 F2b。每个关键字段都要说明从哪来，拿不到或无法可靠核对时，相应功能不能判为通过。

### Q07 最终每条回复都要人工批准吗？

不需要。初期测试逐条确认；正式业务可以先批准群、联系人、场景和资料范围，符合规则的自动处理，正常的变量替换不用重批。身份不明、超出范围，或者涉及价格、订单和时效承诺时，再交给人。首期不做的事项已列在 P0-3。

这是[业务要求](mixed-group-business-requirements-2026-09-21.md)，两种模式还要在选定通道分别验收。仓库当前 API 配置只接受 mock 模型，独立 M3 试验不能代替这条 API 路线的真实模型接入；它的定时配置也只接受一次性任务，每日循环需要补建。其他路线按各自实现确认。

### Q08 怎么避免重复回复？能保证只发一次吗？

目前还不能承诺端到端“恰好一次”。目标通道要按账号和原消息标识保留处理记录，发送任务也有固定编号，重启后仍能查到。同一消息重复到达，不再生成新任务；两条内容相同但 ID 不同的消息，不能随意删掉其中一条。还要查清 SDK 会不会自己重试。

最难的是请求超时：消息可能已经发出，只是结果没回来。这时记为 unknown，先核对。重投、并发、重启和提交前后崩溃都要测。[A1 离线报告](../poc/evidence/a1-api-agent-offline-2026-09-16.md)已有部分检查，选定真实通道仍要复验。

### Q09 为什么超时不直接重试？停发能撤回在途消息吗？

因为超时只说明没拿到结果，消息有可能已经到了。直接重试，客户就可能收到两条。先暂停受影响的任务，查通道记录和接收端；查不清就保留“结果不明”，交负责人处理。

停发也不等于撤回。退出登录后，已经交给通道的请求仍可能继续完成。因此要停止新提交，取消或冻结排队任务，拦住迟到的模型结果，再逐项核对在途消息。暂停范围和恢复权限在测试前定好。

### Q10 非 @ 消息还读不读？群里有人要求机器人忽略规则怎么办？

会根据授权读取同群里必要的上下文，帮助理解问题。但普通消息不会因此自动获得回复；被动回复仍要满足真实 @ 和批准规则，定时索价则按单独批准的计划执行。

群里有人说“忽略规则”或者“把另一个群的信息发过来”，只能当作一条输入消息，不能让它修改权限。跨群访问和这类提示注入，要安排专门测试。

### Q11 怎样确认已转交给人？事情办完后如何恢复？

先生成业务员能处理的待办，带上群、原消息和转交原因，再确认通知确实送到了负责人。做到这一步，才能说“已转交”。没有负责人就进入统一待办队列，通知失败也要显示出来。

转交成功还不等于事情办完。接管期间，机器人按约定范围暂停回复；业务员确认处理完成后，再按规则恢复，处理结果和恢复时间都要有记录。不能只让模型回复一句“已转交”，后台却没有人收到。

### Q12 33 项模拟测试与历史上百项测试有什么关系？

“33 项”目前只有 v1.20 引用的摘要，还没有和具体清单、代码版本及运行报告对应起来。仓库另一份代理传输报告也出现过 33 项，但数字相同不能证明是同一组测试。A1 等报告里的计数属于各自的历史范围，不能相加计算项目完成率。

判断这些测试说明了什么，要看用例、配置、版本和日期。离线检查可以验证程序逻辑，真实收件、原生 @ 和长期运行还得单独验收。

### Q13 二十条输入、三条 ACK、三十分钟能证明什么？

这是下一轮建议的基本收发检查。二十条输入要分别发送；R2 的三条确认消息覆盖普通文本和两类成员的 @，每条都请两类客户端核对收件。这三条不包含 R3 后续业务测试的发送次数，后者要另行批准。

三十分钟只看约定窗口里的遗漏、重复和异常；事前还得写清应该收到哪些消息、执行哪些任务。按规则实际回复、转人工通知、跨日索价，以及升级和长时间断线恢复，都要分别验证。

### Q14 约 300 个群需要多少账号？多久能交付？

现在还缺少排期和算容量所需的数据。比如，群分布在哪些账号上，最忙时每分钟有多少消息，索价要在多长时间内发完，以及通道允许多快发送。这些没确定，就很难负责任地给出账号数和工期。

这次先落实资料提供人和试点时间。测出单个通道的实际表现后，再安排扩群，并分别统计消息量、发送任务量和模型调用量。

### Q15 为什么不选能力勾最多、价格最低的？

因为有些勾对业务很关键，有些能力可以自己补，而且各家价格包含的东西不一样。比如没有内置定时，我们可以开发；混合群里的企微成员能不能收到原生 @，则必须拿到实际结果。一个复合功能打勾，也不能代替其中每一项的依据。

wechat2ipad 就有一处需要核对：旧报告记录了 AtWxIDList，v1.20 的 F5a 仍为待核。先对应 SKU、版本和文档快照，再复核资料判定，不能直接改成通过，更不能由此推出 F5b 的实测结论。采购比较还要把接入开发和维护费用算全。

### Q16 这些报价现在还能用吗？有哪些容易算错的地方？

可以用来准备询价，但不能直接当今天的成交价。报价表沿用 9 月 24 日资料，本次没有重新核价。wechat2ipad 的未来生效公告和旧价格要问清楚；聚合的组合套餐别重复相加；StarBot 标准版不能当 Pro 报价；WTAPI 没有币与人民币的兑换价，就先不换算。

正式预算把许可、运行资源、开发、模型与人工运营、维护分别列出，确认计费周期、税费和扩容条件。“待报价”的项目也要留在清单里。

### Q17 聊天数据会到哪里？升级或停服后谁负责？

这要看最终买的是托管、本地还是私有部署方案。签约前要沿着消息走一遍：哪些内容到了供应商，哪些送给模型，保存在哪里，谁能看，多久删除。

维护也要拆开问：软件能用多久，微信升级后谁适配，故障由谁处理，停服后如何导出或删除数据。采购要求保留近半年仓库活跃且提供维护支持；历史调查窗口为 2026 年 3 月 22 日至 9 月 22 日，采购前更新核验。仓库活动、实际软件更新和商业支持分别留证；文档更新不能代替适配，闭源核心也不要求公开。

### Q18 这次评审需要决定什么？遇到什么情况先停？

建议先同意一个具体版本的小规模验证，把测试群、允许做的操作、次数、费用上限和负责人写清楚。只要出现错群、@错人、泄露其他群内容、越权承诺或停发失效，就暂停后续测试，先查原因。发送结果不明的任务，也先核对再处理。

这轮通过后，再讨论扩群。采购验收和正式上线，都要根据各自要求另作决定。

## 7. 建议验收表与统计口径

以下安排需经评审确认。ACK 指测试用的确认消息。R2 建议把三条分配为普通文本、@个微、@企微，正文和目标在发送前逐条批准。三条只计入 R2；R3 的规则回复、转人工、定时和故障测试另列真实发送次数、审批方式及停发范围，不能沿用 R2 的批准自动执行。

下表的“通过”均要求完成对应阶段的实际核验；只生成草稿或任务时，仅记录该步骤完成。两个执行日、30 分钟等样本安排、观察时限和费用上限需在评审中确认。错群、@错人、跨群泄露、越权承诺和停发失效始终是阻断项，不因样本量或性能指标调整而放宽。

| 阶段 | 建议用例／分母 | 建议通过条件 | 失败或缺证据时 |
|---|---|---|---|
| P0 | 一个具体交付基线 | SKU、构建、客户端、账号、目标群及成员、审批与多人 @ 规则、各阶段发送次数、观察时限、费用上限及负责人齐全 | 不启动依赖缺失信息的真实动作 |
| R0–R1 | 个微 10 条 + 企微 10 条独立原生消息；绑定及重投变化用例另列 | 20/20 在约定时限内关联；F2b 绑定和 F3a/b/c 分项核对；遗漏、误归群、重复业务任务均为 0 | 保留实际分母和失败样本，修复后独立复验 |
| R2-ACK1 | 1 条普通确认正文 | 原群准确；同条消息在个微和企微端各有收件证据 | 不能用本机气泡代替双端收件 |
| R2-ACK2 | 1 条指定个微成员原生 @ | 两类客户端收到同条消息；指定个微成员有原生提醒 | 文本收到而提醒缺失，分别记结论 |
| R2-ACK3 | 1 条指定企微成员原生 @ | 两类客户端收到同条消息；指定企微成员有原生提醒 | 不把普通通知记作原生 @ |
| R3 业务回复 | 两类成员真实 @ 接管账号；多人 @、@所有人、@他人、伪 @、自回显、重投、历史输入 | 按 P0 规则判正反例；批准范围内完成实际原群回复并核对收件；反例不误发，重复事件不新增任务 | 只生成任务或草稿时，发送与收件仍记未验收 |
| R3 转人工 | 超范围／不确定问题；无负责人、通知失败与处理完成 | 生成可处理待办；通知成功才记录已转交；失败可见；按约定范围暂停，处理完成后由有权人员恢复 | 仅回复“已转交”不算通过；未送达的通知保留待处理状态 |
| R3 故障与停发 | 重名、改名／退群、切号、重启、超时、暂停、在途、越权输入 | 身份未知不发送；unknown 不自动重试；F8b 停止新提交、拦截迟到结果，在途对账；F8a 仅在选用时另测 | 未执行用例不计通过；注入故障与真实发生故障分开记录 |
| R3 周期 | 建议至少两个配置执行日，并覆盖一次错过窗口或重启 | 正常窗口内每群每配置执行日一次索价；原生 @ 和收件可核对；错过窗口按事先规则处置；无双调度重复 | 模拟时间与真实跨日结果分开；当前 API 路线须先补循环能力 |
| R4 短时 | 建议 30 分钟；事先列消息及应执行任务，约定时限和阈值 | 按预期清单核对遗漏、重复和完成情况；无阻断事件；异常与未结任务有记录 | 0 事件窗口不能证明负载表现；未达阈值或仍有未解决 unknown，不判阶段通过 |
| 生产关口 | 约定群数、账号分布、入站峰值、时长、恢复／升级场景 | 先约定漏读、延迟、重复、unknown、恢复时间和完成率阈值，再运行验收 | 未定阈值或未实测，不宣称生产通过 |

**输入统计：** 原始回调次数、去重后事件数、合格触发数分开；用“唯一原生消息 ID／等价可靠标识”与发送端预置清单核对遗漏，不能从收到的样本反推分母。区分合法同文不同消息与同一消息重投。

**任务分母：** 定时任务先列出该窗口内应执行的“账号、群、执行日和时段”，被动回复列出应触发的测试事件。依次核对应生成、实际生成、实际提交及完成的任务；从未生成的漏调度也要记为遗漏，不能只统计系统生成出来的任务。

**发送统计：** 在固定结算时点，互斥记录“待处理／未提交（拒绝或跳过）／明确失败／在途／结果不明／有提交或受理证据但未核验／接收已核验”。状态数量之和等于该阶段生成的任务数；状态变化保留流水，不重复累加为多次成功。桌面提交和服务端 accepted 保留各自语义。接收已核验仍需单列个微收件、企微收件和目标成员原生 @ 三个核验字段；普通文本等不要求 @ 的消息，原生提醒一栏记“不适用”，不计为通过或失败。

**时间统计：** 分别保存事件到达、计划到期、策略完成、发送提交、接收端实际收到以及人工核验的时间。人工稍后确认“收到了”的时间，不能当成实际到达时间。报告延迟时说明起止点；跨设备计算还需确认时钟偏差，没有可靠收件时间则不报端到端送达延迟。各阶段分别报告接收完整率、任务完成率和 @ 验证结果，不合成单一“项目完成率”。

**恢复规则：** 先确认身份与配置未变，处理全部 in-flight／unknown，再由负责人恢复；旧任务是否取消或人工重新批准要逐项记录，不能重启后默认补发。
