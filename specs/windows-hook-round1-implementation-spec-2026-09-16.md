## 1. 本轮决策与完成定义

Windows 客户端 Hook 可以作为独立于 861 上游签发链路的研究路线，但当前没有核实到匹配本机版本、满足原企微/个微混合群要求的现成实现。本轮先完成候选源码核查、版本门禁和最小离线契约验证；只有证据充分时才实现候选专用 decoder，不先搭建假定可用的完整网关。

本轮必须产出明确的 `go` / `blocked` / `reject` 决策，以及可复查的证据。`go` 仅表示具备申请受控真机验证的技术条件，不表示已授权注入或业务验收成功。发现无匹配候选时，以完整阻塞结论结束本轮，禁止为凑交付编造接口或反复运行已有测试。

另设 D 支线：使用已明确提供并授权分析的可读数据库副本或导出数据，验证离线字段解析。D 支线与 Hook 的版本门禁独立：Hook 阻塞时可完成已具备输入的离线验证；D 支线通过不能使 Hook 决策变为 `go`。没有合格输入时记录 `not_run`，不主动扫描聊天目录或获取密钥。

业务最终目标仍为：原测试个人微信账号、原企微外部混合群，真实 @ 被正确识别，人工触发固定文本 ACK，并由个微和企微两端确认收到。主动发送、分别真实 @ 两类成员、AI 和定时任务是后续独立验收项。

## 3. 本轮范围与执行边界

允许的实现范围：公开源码静态审查；本地安装文件的版本、PE 架构和 SHA-256 检查；在项目隔离目录保存研究材料；实现不访问微信进程的版本校验器和离线测试；满足源码核查条件后进行离线构建。

本轮不执行 DLL 注入、进程内存读写、数据库取密钥、客户端降级、微信重启或登录、聊天采样、真实发送。保持零付费，不联系维护方、不提交 Issue、不修改全局 Git 配置、不 commit/push。不得启动 UIA、OCR、看屏或读屏实验，也不修改 861 运行配置和凭据。

这里的“聊天采样”指从真实客户端或活动数据库新增采集。D 支线只处理另行明确提供且获准分析的既有离线材料，不包含活动数据库复制、解密条件获取、原库修改或副本回写。本文是实施范围说明，不代替对具体私密数据输入的授权。

### 3.1 进程接触和风险边界

| 操作 | 是否需要真实微信进程 | 风险与证据边界 |
|---|---|---|
| 源码/程序文件静态分析、版本检查、合成测试 | 否 | 不加载候选 DLL；不能证明运行时兼容 |
| 已有可读副本的隔离分析 | 否 | 不改变微信运行状态；重点控制私密数据留存与输出，不承诺零账号风险 |
| 活动数据库复制 | 不必注入，但会访问客户端正在使用的数据文件 | 不在本轮范围；需另行解决快照一致性、覆盖范围和访问授权 |
| 从进程获取密钥 | 取决于方法，通常涉及进程访问 | 不在本轮范围；副本分析不能抵消此前取密钥动作的风险 |
| DLL 注入、运行时 Hook、内部发送函数调用 | 是 | 存在崩溃、客户端兼容和账号限制风险，不能给出未经验证的概率或安全阈值 |

复制不会自动解除加密。修改独立副本不会向群发送消息；禁止通过回写原库尝试触发发送。测试账号、限频或仅监听也不能作为“不会风控”的证明。

普通 Windows 窗口消息 Hook 不等于微信业务消息接口。本 Spec 研究的是客户端内部消息处理/发送路径的 Hook，不以键鼠监听或窗口事件冒充业务收发。

源码构建前必须检查入口、构建事件、依赖获取和生成步骤；构建脚本若会自动注入、启动微信、安装服务、修改注册表或下载执行未知程序，则分离这些步骤，否则停止构建。下载的二进制只允许做静态校验，不因其有 GitHub Release 就直接执行。

## 4. 实施顺序

### H0：固定本机与仓库基线

1. 阅读适用项目指令，记录 Git HEAD、分支和已有改动；只在当前 checkout 工作并保留无关变更。
2. 读取安装文件版本、PE 架构和 SHA-256；不通过打开微信取得这些信息。
3. 记录候选实际依赖的模块路径、版本及哈希；未确定依赖模块时标记 `unknown`，不能仅凭启动 EXE 版本通过兼容门禁。
4. 检查原有 `Channel`、`ApiMessageV1`、Runtime、Store/outbox 接口，本轮不更改公共事件契约。

### H1：候选筛选与源码审查

优先核查 navysoto/wxhook 的公开 4.x 实现与 aixed 的 4.x 发布源码对应关系；WeChatFerry、wxhelper 用于机制和契约参考。版本不匹配的候选只保留研究价值，不安装旧客户端试跑。

每个候选记录以下内容：

- 仓库、固定 commit/tag、许可证文件及 README 使用声明；有矛盾则记为待明确，不自行推定商用许可。
- 支持的精确客户端版本和 CPU 架构，版本检测逻辑，接收/发送入口所在源码。
- 必要源码、依赖、构建文件是否完整；是否依赖未公开 DLL、授权服务或付费接口。
- 接收事件是否保留稳定消息 ID、群 ID、发送人 ID、本人标记、时间、提及元数据及原始引用关系。
- 文本发送是否调用内部接口；实际返回值说明什么；是否有可关联的发送回执。
- 本地监听地址、认证方式、外连目标、日志内容和异常行为；未确认项保持 `unknown`。
- 混合群、企微成员身份和真实 @ 的证据，分别标记 `source_observed`、`documented`、`not_observed`，不得混用。

发现核心能力仅有未公开接口说明时，不能把接口列表当成可交付源码。未找到 4.1.13.65 适配时，列出缺失模块和可能需要的适配工作，不在本轮扩大为逆向开发。

### H2：实现最小版本门禁

新增纯离线校验器，输入本地文件元数据和已审查候选清单，输出判定，不加载 DLL、不连接服务、不访问进程内存。

建议文件：`poc/wechat_agent_poc/hook_compatibility.py`、`poc/scripts/check_hook_compatibility.py`、`poc/tests/test_hook_compatibility.py`。落地前按仓库实际测试目录调整路径，不复制另一套测试框架。

候选清单最少包含 `schema_version`、候选仓库和 commit、目标客户端精确版本、目标架构、必需模块及其允许哈希、源码完整性、构建验证状态、证据引用。未知值必须显式表达，不用空字符串表示通过。

校验结果固定为 `match` / `mismatch` / `unknown`：全部必需条件有证据且一致才是 `match`；已知条件冲突为 `mismatch`；缺模块、缺哈希、缺可信目标清单为 `unknown`。`match` 只说明静态匹配，不代表注入成功或混合群可用。

证据 JSON 使用 `schema_version=windows-hook-round1.v1`，至少包含：`checked_at`、`candidate_ref`、`client_version`、`client_arch`、`module_checks`、`compatibility_status`、`reason_codes`、`live_receive_verified=false`、`mixed_group_verified=false`、`send_delivery_verified=false`。这些实测字段本轮不得自动改为 true。

### H3：条件性离线构建与 decoder

仅当 H1 确认必要源码可获得且构建入口可安全隔离时执行构建，保存工具链、依赖锁定信息、日志、产物 SHA-256。构建成功与目标版本兼容分别报告。没有完整源码时记录 `not_run` 和原因，不执行不透明预编译组件来代替源码验证。

只有源码揭示了确定的接收数据结构，才添加 `hook_decoder.py` 和对应测试。字段映射必须引用固定 commit 下的文件/函数；文档样例、源码推导样例、合成样例、真机样例分别标记来源。本轮不可能产生真机样例。

如果接收结构尚未确定，交付字段缺口表即可，不创建猜测 schema 的 decoder、HTTP API、完整 `HookChannel` 或后台服务。

### D0：已有副本的输入资格与隔离

输入必须有明确指定的路径、可分析的账号/群范围、来源类型及取得方式。记录副本时间、已知客户端版本、文件清单、大小和 SHA-256；来源或时间未知则如实标记，不从文件修改时间推定完整性。原始路径、账号标识和聊天正文只留在受控本地目录，不写入可提交报告。

原始材料保留不变，在经确认被 Git 忽略的独立目录创建工作副本；处理前后核对原始材料哈希。解析器只连接工作副本，禁止连接微信活动目录、跟随链接进入原目录或写回原库。输入目录与输出目录不得重叠。

对于 SQLite，工作副本使用只读连接，禁用扩展加载；若访问 WAL 需要生成辅助文件，只能发生在隔离工作目录。不得对活动数据库运行 checkpoint、修复或备份命令；不得用 `immutable` 等选项忽略可能存在的 WAL 后宣称数据完整。

可正常查询不等于完整快照。区分以下证据：文件结构检查、SQLite 完整性检查、采集一致性、分片覆盖、时间覆盖和业务语义验证。各项独立记录 `verified` / `unknown` / `failed`。仅有主库且不清楚 WAL 状态、顺序复制期间可能发生写入、缺失关联分片时，最多用于局部 schema 探索，不能验收“完整读取”。SQLite 通用备份文档不证明微信加密库已可使用该机制。

加密或无法识别的输入直接记录 `unreadable`，不自动尝试取密钥、解密工具、网络服务或进程操作。没有现成输入时无需反复询问，完成其他独立工作并报告缺口。

### D1：离线字段与行为验证

先检查实际表结构，再为获准范围读取最少必要记录；禁止默认导出全库。记录消息 ID、群/发送人/本人标识、时间、提及、引用、消息类型各自对应的表/字段及解析依据，不预设数据库 schema。

数据库 decoder 与 Hook decoder 分开：数据库字段不能证明运行时回调有相同结构。需要代码时建议新增 `snapshot_decoder.py` 和独立测试，复用现有归一化契约，不创建在线 Channel。缺失身份或原生 ID 的记录进入离线诊断，不伪造可执行事件。

至少验证稳定 ID 及大整数精度、同正文不同 ID、跨分片重复、未知成员、本人消息、结构化 @ 与纯文本 @、引用旧 @、引用关系缺失和未知历史归属。没有独立标注或可解释的结构化字段时，不把解析器自己的输出当正确答案；真实 @ 语义标记 `unknown`。不能为补齐用例擅自要求或触发真实群消息，缺少的场景使用明确标记的合成夹具测试逻辑，并保留真实样本缺口。

离线记录永不送入生产 Runtime/outbox，不触发发送；可使用隔离测试 Store 或纯函数验证，默认无网络。快照时间不能充当消息发生时间，也不能把快照中的最后一条消息当作未来实时接收的可靠游标。

### D2：独立结论

D 支线结果为 `offline_verified` / `partial` / `unreadable` / `not_run`。`offline_verified` 仅适用于清单指定的数据集及已标注用例：必要字段映射有依据、相关数据一致性与覆盖已确认、测试通过；不得外推为其他群或实时数据完整。任一关键证据不足则为 `partial`。

结果必须保持 `live_receive_verified=false`、`mixed_group_verified=false`、`send_delivery_verified=false`；可另记录 `snapshot_mixed_group_fields_verified`，但不能代替原群真机收发验收。

## 5. 与现有通道的衔接契约

现有实现以 `poc/wechat_agent_poc/api_channel.py` 为准，复用 `Channel`、`ApiMessageV1`、`ChannelEvidence`、`OutboundCommand`、`SubmitResult`。未来 Hook adapter 接入同一个 Runtime、Store 和 outbox，不建立平行业务框架。

| 现有字段/方法 | Hook 路线必须遵守的语义 |
|---|---|
| `native_message_id` | 保留原生稳定 ID 的字符串形式，不经过浮点转换；缺失时拒绝进入可执行事件流，不能用正文哈希伪造原生 ID |
| `account_key` / `conversation_key` / `sender_key` | 来自可核实标识；不依赖昵称匹配，不猜测 `openim` 与 `wxid` 的转换 |
| `identity_status` / `is_self` | 无充分证据时为 `unknown`，不能默认非本人 |
| `mention_status` / `mention_keys` | 明确结构化元数据才是 `structured`；有证据确认无提及才是 `none`；元数据缺失为 `unknown` |
| `reply_to_message_id` | 只保存原生引用关系，没有则为 null |
| `history_status` / `session_epoch` | 未知历史归属不得标为新消息；会话切换显式记录，不能用本地接收时间证明消息新鲜度 |
| `probe()` | 只报告观测到的身份、在线和能力；静态版本匹配不能伪造在线或成员映射 |
| `submit()` | 未调用底层为 `not_submitted`；调用结果不明为 `unknown`；`accepted` 只表示提交受理，不是送达 |

禁止改变已有 `event_key()` 去重规则来掩盖缺失 ID；若候选的 ID 作用域与现有契约冲突，先形成兼容性决策再另轮修改。候选本身存在回调重试/补发保证时也须给出证据，没有则按未知处理。

未来真机桥接默认只监听 loopback，并采用独立凭据；群白名单和发送授权由现有运行层执行。Hook 回调只做有界数据复制/入队，不在微信回调线程运行模型、等待网络或写大文件。队列溢出、持久化失败必须暴露接收缺口，禁止静默丢弃后仍宣称上下文完整。这些是后续实现约束，本轮不启动桥接服务。

后续职责边界固定为“最小 DLL → 本机 IPC → 独立桥接进程 → 现有 Channel”。DLL 只承担版本防护、必要内部调用和有界事件复制；桥接进程承担鉴权、缓冲、连接管理及协议转换；业务层保留审批与 outbox。IPC 的命名管道或 loopback socket 选型待候选约束确定，不强制把 HTTP 服务放入微信进程。需要远程服务时由桥接进程建立受控连接，不由 Hook 回调直接等待远端。

状态必须区分 DLL 加载、初始化、Hook 安装、命令接收、内部发送调用、提交受理与双端送达。通信重连不自动重放结果未知的发送命令；离线副本无法验证这些运行时状态。

### 8.2 V3 最小启动清单

开始真实进程验证前必须具备以下可复查材料，不要求先证明尚待实验的运行时成功：

1. 固定源代码 commit、构建日志、DLL/桥接产物哈希及所需权限；当前客户端/依赖模块版本、架构和哈希符合已审查目标。仅改版本字符串或关闭版本校验不算适配。
2. 明确接收路径的定位依据、参数/对象生命周期、线程与异常处理设计；发送入口即使已实现，也在 V3/V4 保持禁用。所有测试入口默认不发送。
3. 目标 PID/可执行路径与账号范围核对办法；若注入后才能确认账号，身份确认前禁止向业务层输出聊天或执行命令。单纯 DLL 加载如果会自动安装 Hook/采集，也必须按实际副作用授权，不能称为纯加载试验。
4. 已通过离线测试的 IPC/鉴权或等价隔离机制，容量上限、溢出计数、超时及 kill switch；私密日志落在已确认 Git 忽略的本地目录，不回传服务器。
5. 书面的回退办法：如何停用桥接、停止采集以及处理客户端异常。不能假定卸载 DLL 一定安全；若回退需要退出或重启微信，该动作须已获授权，否则不启动实验。
6. 试验单明确持续时间、目标群、采集上限、退出条件和证据位置。建议首次 V3 上限 5 分钟、一次加载尝试；V4 上限 30 分钟/20 条目标样本，以先达到者停止。该建议须在实际试验单中固定，不自动构成执行授权。

若自主适配必须依靠动态调试才能形成第 1、2 项证据，另建“动态适配实验”工作包，列明调试/进程读取/修改的具体范围与风险并获得授权；不能通过降低 V3 门槛将其混入稳定性验收。此分支不要求先证明适配成功，但也不能报告 V3 或业务验收通过。

### 8.3 暂停、回退与重新开启

- 客户端/模块版本或哈希改变：停止依赖旧构建的验证，重新检查兼容性；旧结果仅作为历史记录。
- 账号、群或成员身份不符，真实 @ 元数据不足：关闭业务触发，保留最小脱敏诊断，不尝试猜测映射。
- 客户端崩溃、卡死、退出登录、出现账号异常提示：停止本次实验；按已授权回退方案处理，不自动再次注入、登录或切换规避方式。
- 队列溢出、通信断开、落盘失败：标记接收缺口；完整性未恢复前不进入发送。没有可靠补发机制时明确记录丢失区间，不伪造补齐。
- 发送超时或结果不明：记 unknown，停止自动重试；根据现有收据或双端证据对账。不得为了收集证据再发同一 ACK。
- 有界窗口结束仍未覆盖样本：保存 partial 和缺失场景，停止；只有已有授权明确覆盖后续窗口，或新授权补足后才继续。
