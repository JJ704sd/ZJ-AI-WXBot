## 三、从示例源码得到的实施修正

附件 `webhook-client.py` 使用 `HMAC-SHA256(timestamp UTF-8 + 原始请求体)`，请求头为 `X-Webhook-Signature` 与 `X-Webhook-Timestamp`。这是示例端校验实现，不是固定20250822网关已验证的签名契约。

该示例存在当前任务不宜直接照搬的行为：默认监听 `0.0.0.0:8000`；硬编码示例secret；验签前记录请求头和部分body；验签后格式化记录整个消息；没有看到持久化去重、水位、时间窗口校验或重放拦截。老用户指南虽称“缓存避免历史消息风暴”，示例本身不足以兑现该能力。

现有 `pad_auth.py` 含MAX元数据HMAC公式，`pad_decoder.py` 含文档v1解码器；不得套到legacy。现有 `pad_cli.py` 自述P1离线观察器，拒绝live probe/发送验收；不能靠修改状态标志宣称已有861在线适配器。

## 四、最小实现结构

```text
固定861网关 → 单路有界接收 → Legacy861解码/身份映射
                               ↓
                       现有观察库/去重/水位
                               ↓
                    人工审核 → 现有ApiRuntime/outbox
                               ↓
                    Legacy861 Channel → 固定文本发送
```

复用 `api_channel.py` 的 Channel、ApiMessageV1、OutboundCommand、SubmitResult，以及 `api_runtime.py`、`api_store.py`。保留 `pad_store.py` / observer 的证据用途，不新增另一套业务runtime。

以下模块现已存在；后续应核对实现、补齐真实契约，不能重新按空白项目开发：

- `pad_legacy_channel.py`：在线探针、原群/成员解析、固定文本提交；不自动登录或生成key。
- `pad_legacy_transport.py`：loopback目标、超时、凭据脱敏；可注入假transport用于测试。
- `pad_legacy_decoder.py`：仅接受实际取得的861样本结构；不明确的真实@/历史/身份标为unknown。
- `pad_legacy_receive.py`：单消费者、有界数量与时长、停止及水位；第一版只观察。

上述能力中仅离线实现和边界验证已交付，真实在线探针、接收字段及发送效果未验收。公共配置 legacy 入口默认关闭，不削弱已有 fake、MAX 观察器或其他 provider 的保护。详见已有 offline-adapter 与 g1-watermark 证据；历史测试数字不能当本轮复跑。水位是 ID 集合，`ordering=unknown`、`monotonic_id=false`、`replay_cursor=false`，不承诺按最大消息 ID 回放。

复核现有 `prepare_pad_861_device.py`、`reconcile_pad_861_devices.py`、授权传输脚本的副作用和已保存收据；先读本地证据，不执行旧脚本整套重放。

### G2：登录与原群绑定（条件满足后预算1–2小时）

按20250822实际Swagger选择登录路由，不套MAX Mac流程；用户完成扫码/确认。登录动作需核对既有明确授权，缺失时仅提出必要的一次具体请求。

采用 README 中同账号复用原设备 key、保持设备和网络稳定的建议。先核对已有 key 与账号匹配，不为登录问题重新生成。分别核验扫码/登录状态及 `GetInItStatus` 初始化状态；二维码生成成功不能替代登录完成。验证码与掉线按实际状态处理，不自动反复扫码，也不把“三个月稳定”等文案作为承诺。首轮不引入新代理，不照搬 `/api/login/qr/newx` 等路由。

分别核验在线状态、本人身份、原群稳定标识和目标成员映射；本地旧绑定仅是核验输入。优先指定原群，避免全量联系人扫描。群名截图不是程序稳定绑定证据。无法区分群会话/成员/企微标识则停止发送。

通过条件：输出脱敏绑定报告，明确唯一账号、唯一原群、成员映射及证据时间。

### G3：单路接收与真实@（预算3–4小时）

先研究 `POST /message/HttpSyncMsg?key=<device-key>`，body显式指定正数Count，建议首轮10；空body/Count=0按文档可能取全量，禁用。一次有界观察建议120秒；轮询频率须依据实际消费语义和限流确定，首次保守2–3秒。

不得同时启用HTTP、WS与Webhook抢消费。必须验证Count确实限量、消息是否出队/重放、初始化历史和当前新消息如何区分。若轮询缺少判据，停止该消费者后再调查legacy Webhook。

Webhook备选仅绑定loopback、原始body验签、持久化后ACK；未知签名/未知消息进入隔离观察，不触发业务。签名公式以固定网关实际样本验证，不能直接信任示例。秘密、原始数据留gitignored，报告脱敏。

当前 adapter 仍拒绝 Webhook；上述为条件方案，不代表已支持。README 的 `/v1` 前缀不可直接套用，固定 Swagger 的 `/webhook/Update` 操作键异常为 `t`，与 README 的 PUT 冲突，必须先解决契约疑点。`GET /webhook/Test` 有外发回调效果，不作为只读探针。历史缓存一小时、批次20、15秒同步均不得替代实测，也不能使 HTTP ID 集合变成有序游标。

取得至少20条人工标注样本，覆盖：真实@本人、普通文本@昵称、@他人、引用旧@、普通新文本、本人发送、历史、重复投递、同一分钟重复正文、断线重连以及企微成员发言。新消息必须有基线和时间证据；去重使用真实稳定消息ID，不用正文+分钟数替代。

通过条件：20条分类与人工标签一致；历史/重复/自己/伪@不触发；缺字段必须unknown且拒绝自动触发。真实@证据不足则只报告“能收消息”，不得进入自动回复验收。

### G4：人工固定回复（预算1–2小时）

单独核实发送授权、目标和文本后，复用现有outbox/在线探针/锁/额度。请求体按基线的 `SendMessageModel.MsgItem`，元素使用 `ToUserName`、`TextContent`、`MsgType=1`、`AtWxIDList`；字段存在不等于已验证原生@。

先人工触发一条固定ACK；记录提交时间、业务结果、消息ID及双端显示证据。当前 Channel 状态为 accepted/not_submitted/unknown；accepted仅表示提交被接受，不代表送达。超时记unknown，不自动重发。

随后再按明确授权测试原生@，不能把文本拼接@昵称当成功。错误群、过期消息、未映射成员必须拒发。

### G5：AI和定时能力（G0–G4通过后，第二天剩余时间）

先让AI生成待审批草稿，人工确认后发；再按明确业务触发范围启用自动回复。复用现有预算、时限与幂等约束，不为演示放宽历史过滤。免费模型或现有获准模型可用性单独核实，不擅自购买API额度。定时任务不得补发过期触发，重启不回放。
