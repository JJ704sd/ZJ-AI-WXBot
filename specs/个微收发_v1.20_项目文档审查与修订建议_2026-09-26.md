# 个微收发 v1.20 项目文档审查与修订建议

审查日期：2026-09-26｜源码基准：`3441e692ac888a5c2308027ce16851af82517ea9`｜主文：[v1.20](个微收发_v1.20_紧凑连续版_2026-09-24.md)

> 后续落实：本报告的 D01–D08 已纳入 [v1.21 主文](个微收发_v1.21_技术评审修订版_2026-09-26.md)及其配套演讲稿、问题清单，具体位置见主文附录 B。下文保留审查时的发现与建议。

## 审查结论

项目文档已经能说明目标场景、候选产品和主要风险，但功能表与实现状态还需要进一步对齐。最先要改的是：把退出接口与可靠停发分开；明确准确身份绑定的验收位置；把每日周期的实现缺口写清楚。否则评审可能把“有接口”“有历史样本”理解成“只差补一份验收报告”。

本次保留用户提供的 v1.20 Markdown 和 4 页 PDF，未改写其中的供应商判定或价格。两份 Markdown 的正文已核对一致。以下审查覆盖主文、业务需求、技术及采购报告、项目入口和配套汇报稿；依据现有文档与静态源码，不代表新增实机验证或供应商核价。旧资料的日期仍按原记录保留。

## 一、建议优先处理的内容

### D01：退出登录与可靠停发应分开

**位置：** v1.20 第 1.2 节 F8 行、第 2.2 节 F8 列。

第 1.2 节写明“退出 API 条、可靠停发必”，但供应商矩阵又合成“退出／可靠停发 条”，其中一些候选记为 ✔。这样既把必需结果写成了条件项，也容易让人把 logout 接口当作可靠停发的依据。

建议拆成：

| 功能 | 必须性 | 要核对的内容 |
|---|---|---|
| F8a 退出／注销接口 | 选择需要程序化退出的路径时必须 | 目标版本是否提供接口；退出后有哪些状态变化 |
| F8b 可靠停发 | 必须 | 停止新提交；取消或冻结排队任务；处理迟到模型结果；列出在途及结果不明任务；恢复时不自动重发 |

现有合并列中的勾不能直接复制给 F8b。退出后仍可能有已经提交的消息在处理。[API runtime 的 stop()](../poc/wechat_agent_poc/api_runtime.py) 第 247–265 行也分别返回 `in_flight` 和 `unknown`，说明停发与在途结果需要分别记录。

### D02：准确绑定必须有验收入口，复合功能不能只看一个勾

**位置：** v1.20 第 1.2 节 F2、F3、F11，第 2.1 节供应商矩阵。

F2b 准确绑定是必需项，但供应商表只有条件项 F2a“群／成员列表”。拿到列表还不能证明重名、改名、退群或切号后仍能把消息发给正确的人。F3 又把“读取、来源、去重”放在一个格子里，无法看出官方资料究竟覆盖哪一部分。

建议保留 F1–F12 主编号，细分如下，不据此新增供应商通过结论：

| 子项 | 供应商资料需要说明 | 项目需要验收 |
|---|---|---|
| F2a 列表／查询 | 群与成员查询接口、范围及刷新方式 | 选用该路径时核对列表完整性 |
| F2b 准确绑定 | 账号、群和成员标识的含义与失效条件 | 重名、改名、退群、切号、重启后不误绑 |
| F3a 收取消息 | 事件输入方式及消息类型 | 目标混合群两类成员的独立消息可读取 |
| F3b 来源识别 | 账号、群、发送者、消息标识、方向与时间语义 | 来源正确，自消息和历史输入可区分 |
| F3c 重投与去重 | 重投、补收、顺序及消息 ID 的作用范围 | 重复事件不重复处理；合法同文消息不误删；重启不失去去重记录 |

F11 的“可由 Adapter 补齐”建议改为：

> 我方可用 Adapter 统一已有接口和字段，并建设策略、调度、去重及状态管理。底层缺少可靠身份、消息标识或真实 @ 语义时，不能通过格式转换补成已验收能力，仍需补证据或更换实现路径。

每个 ✔ 最好对应“具体 SKU／版本、文档段落或字段、记录日期”。现有来源索引只有产品级入口，不足以解释全部复合判定；本轮未逐个重新访问供应商网站，因此不直接重判各家勾叉。

### D03：每日执行有实现缺口，不能只写“补周期证据”

**位置：** v1.20 第 4.1 节 B 行、第 4.3 节 R3。

当前 [api_config.py](../poc/wechat_agent_poc/api_config.py) 第 266–270 行只接受 `once_after`，并明确拒绝 `schedule_kind=recurring`。[已有配置测试](../poc/tests/test_api_config.py) 第 42–44 行也表达了拒绝循环配置的预期；本轮未运行测试。这里至少对仓库这条 API 路线而言，包含待开发工作。

建议替换为：

> 历史摘要记录了单次定时；现有 API 路线仅支持一次性任务。按执行日循环、时区、执行窗口、漏调度检测及重启防重，需要补建并验收。供应商自带调度或其他路线另按实际交付确认，不能直接继承本路线的结论。

同样，`api_config.py` 第 17、258–262 行的模型配置只接受 `mock`。独立 M3 文本生成和发送试验有记录，但不能据此认为已经接进这条 API Agent 路线。主文宜增加“实现现状”一列，分别写资料支持、已有代码、离线验证和真实验收。

### D04：历史摘要与可追溯实测应分开列

**位置：** v1.20 第 4.1 节与末尾“项目证据边界”。

主文引用 v1.18／v1.19 的摘要，但当前 `specs/` 没有对应版本文件。两群读取、单次定时、企微提醒及“33 项模拟测试”也没有逐项附原记录。建议把摘要旁的 ✔ 改成“历史摘要，待补原记录”，以免与已验收混淆。缺少来源不等于原试验没有做过。

可补入以下证据表：

| 条目 | 当前可追溯依据 | 可以说明什么 | 仍缺什么 |
|---|---|---|---|
| OCR 单次受控文本发送 | [9 月 20 日记录](../poc/evidence/controlled-send-2026-09-20.md) | 本机气泡、输入框清空，操作人确认收件 | 接收端类型未说明；不证明双端、原生 @ 或自动触发 |
| 编号消息生成草稿 | [9 月 20 日触发记录](../poc/evidence/controlled-trigger-2026-09-20.md) | 恢复后根据真实快照重放生成草稿 | 观察存在中断；未填入、未发送 |
| API Agent 离线处理 | [A1 离线报告](../poc/evidence/a1-api-agent-offline-2026-09-16.md) | 对应版本的 fake 通道和模型桩检查 | 目标供应商通道、真实模型接入与两类客户端收件 |
| 两群读取、单次定时、固定回复和企微提醒摘要 | v1.20 第 4.1 节；原 v1.18／v1.19 待补 | 目前只能按原文转述 | 原文、运行编号、版本、群类型及接收依据 |
| “33 项模拟测试” | v1.20 第 4.1 节引用，来源尚未建立对应关系 | 不能据数量判断覆盖范围 | 测试清单、代码提交、报告和执行日期 |

仓库另有[代理传输诊断报告](../poc/evidence/pad-861-proxy-diagnosis-2026-09-16.md)第 57 行的“33 项”记录，且明确未重跑 Agent 全量回归。数量相同不能证明是主文所指的同一组测试。

### D05：R3 要验实际业务结果，也要写清多人 @ 的规则

**位置：** v1.20 第 4.3 节。

三条人工批准 ACK 能验证指定发送，但不能单独证明按规则自动回复、每日索价和人工接管。主文中的 R3 可按下表展开；配套问题清单已包含多数执行细节：

| 项目 | 建议写入主文的要求 |
|---|---|
| R2 与 R3 的发送范围 | 三条 ACK 只计 R2；R3 另列发送次数、审批方式和停发范围 |
| 批准范围内回复 | 两类成员分别真实 @ 接管账号，完成原群回复并核对收件；生成任务或草稿只记该步骤完成 |
| 转人工 | 待办包含群、原消息、原因和负责人；通知成功后才说已转交；通知失败可见；业务处理完成与恢复另留记录 |
| 每日索价 | 在约定执行日和窗口执行；实际指定成员 @ 与收件可核对；模拟时间与真实跨日结果分开 |
| @ 边界 | 分别测只 @ 本人、本人和他人同时被 @、只 @ 他人、@所有人、文字伪 @、自消息回显 |
| R4 观察 | 事先列测试消息与应执行任务、观察时限和通过阈值；漏生成的任务也计遗漏；30 分钟不替代长期运行 |

当前 [api_runtime.py](../poc/wechat_agent_poc/api_runtime.py) 第 817–820 行的被动 @ 回复判定要求结构化提及列表恰好为本人，并排除 @所有人。因此“同时 @ 本人和别人”目前会被这条路线拒绝。项目需要明确是否保留该规则，或列为待改功能；不能一面宣称所有真实 @ 都会触发，一面仅测单人 @。

### D06：把已有业务边界和采购要求补回主文

**依据：** [业务需求](mixed-group-business-requirements-2026-09-21.md)第 9–15、31 行。配套讲稿已有相关说明，但主文不应依赖讲者口头补齐。

第一章建议增加：

> 首期每群在每个配置执行日索价一次，优先使用批准模板；被真实 @ 后只处理批准范围内的问题。不催收、不判断是否收齐，不做价格表解析入库、比价或自动报价；价格、订单及时效承诺转人工。普通非 @ 消息可在授权范围内提供必要同群上下文，不因此触发被动回复。

第三章采购清单建议增加：

> 沿用近半年仓库活跃且提供维护支持的要求。原调查窗口为 2026-03-22 至 2026-09-22；正式采购前更新核验。仓库活动、实际交付的软件更新和商业支持分别留证，不用 README 更新代替适配证明，也不要求闭源商业核心公开。使用期、适配更新期和故障支持期分别写入报价或合同。

### D07：两份文档对 wechat2ipad 指定成员 @ 的判定需要解释

**位置：** v1.20 第 2.1 节 F5a；[技术报告](agent-personal-wechat-mixed-group-feasibility-report-2026-09-16.md)第 115、124 行。

技术报告记录了 `MessageItem.AtWxIDList` 字符串数组；v1.20 则把 wechat2ipad 的 F5a 记为 △，同时规定存在明确“指定成员 @”接口或参数即可在资料层面记 ✔。目前没有说明这是交付版本不同、旧快照不适用，还是表格尚未衔接。

建议加注：

> 旧报告记录了 `MessageItem.AtWxIDList`。需先对应到同一 SKU、服务版本和文档快照，再复核 F5a 的资料判定。未完成对应前保留待核，不解释为实测失败；F5b 企微成员实际原生提醒仍需目标群实测。

本轮不直接把 △ 改成 ✔，也不推断该接口当前仍有效。

### D08：文档入口需要明确版本和适用范围

`poc/README.md` 原来以“综合报告 v1.3”链接到已经更新为 v1.13 的文件，读者无法通过该链接查看固定的 v1.3。另有“最新”描述指向同日较早阶段，容易盖住后来单次发送成功的记录。

本轮已修正链接文案和阶段标识，并将旧 CLI 的 modes 与默认离线用法标明为对应入口的能力，避免读者把它当成所有 API、OCR 或独立工具的共同状态。顶层 README 增加本审查入口。
